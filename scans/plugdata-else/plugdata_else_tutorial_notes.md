# Live Electronics Tutorial — Reading Notes

Notes on the Live Electronics Tutorial by Alexandre Torres Porres, the author
of the ELSE library, as bundled with plugdata 0.9.3 in
`~/Documents/plugdata/Documentation/12.live-electronics-tutorial`
(581 patches in 12 parts). Read on 2026-10-02.

**How these notes were made.** The comment text and a list of up to 30 boxes
were extracted from every tutorial patch. Four reading sub-agents then read
all of that text, one group of parts each, and wrote the items below. Nothing
here was tested in Pd or in Max, and nothing is from memory. Every item names
the patch it came from; paths are relative to the tutorial folder.

**How to read them.** The reader is assumed to know Max and not Pd. "Vanilla"
means plain Pd without ELSE. Object names are spelled as the tutorial spells
them. Where the tutorial's own text contradicts its boxes, the item says so
instead of picking one.

**Two conventions that run through every filter formula below.** The tutorial
calls feedforward coefficients `a0 a1 a2` and feedback coefficients `b1 b2`,
and its difference equations ADD the feedback terms. Pd's `biquad~` takes its
list in the order `fb1 fb2 ff0 ff1 ff2`. Max's `biquad~` refpage gives
`y[n] = a0*x[n] + a1*x[n-1] + a2*x[n-2] - b1*y[n-1] - b2*y[n-2]`, with the list
in the order `a0 a1 a2 b1 b2`. So a coefficient list moved from Pd to Max needs
reordering, and its two feedback values need their signs flipped.

**The tutorial almost never mentions Max.** Two places were found: a remark
that Max's control resolution is 2 ms by default (Part 01), and a remark that
Max's `udpsend` / `udpreceive` work much like `osc.send` / `osc.receive`
(Part 04). Neither claim was checked.

The short digest of what matters most to a Max patcher is in
`plugdata_else_insights.md`, Part 3. This file is the long form.

## Part 01 — The Basics

### 01 Pd Quickstart (kept brief; another scan covers Pd vanilla)

- **All numbers are 32-bit floats, shown to 6 digits** — Pd has no integer type. A number is shown with 6 significant digits and switches to exponent form (`1e+06`) past that. Anything that is not a number is a symbol. `(source: Part.01-The.Basics/01-Pd.Quickstart/2.Syntax/01.Basic.Syntax/2.Atoms.pd)`
- **Depth-first message order, with one exception** — a branch runs to its end before the next branch starts. `[delay]` breaks this: its output comes later even when the delay time is 0. `(source: Part.01-The.Basics/01-Pd.Quickstart/2.Syntax/2.Message.Order.pd)`
- **Fan-out order is undefined without `[trigger]`** — one outlet wired to several boxes has no defined order. `[trigger]` is what fixes the order, right to left. `(source: Part.01-The.Basics/01-Pd.Quickstart/2.Syntax/2.Message.Order.pd)`
- **A semicolon in a message box acts as a send** — text before the first semicolon goes out the outlet. After a semicolon, the next symbol is a send address and nothing more goes to the outlet. A comma after that splits messages to the same address. `(source: Part.01-The.Basics/01-Pd.Quickstart/2.Syntax/3.Send-Receive/3.More.on.messages.pd)`
- **`$0` is the per-patch ID, and it only works in object boxes** — each open patch or abstraction copy gets its own number. Use it in send/receive names, array names and `[value]` names to keep copies apart. In a message box `$0` just becomes 0. `(source: Part.01-The.Basics/01-Pd.Quickstart/2.Syntax/5.Locality/1.Locality.pd; Part.01-The.Basics/01-Pd.Quickstart/2.Syntax/6.Escape/1.Locality.pd)`
- **Trap: a GUI receive name saved from `$0-x` is saved expanded** — setting a GUI's receive name to `$0-x` stores the expanded number, so it breaks on reload. A backslash before the `$` keeps it literal so it is saved unexpanded. But an escaped literal does not match a real `[receive $0-x]`; for that you need the expanded symbol from `[symbol $0-x]`. `(source: Part.01-The.Basics/01-Pd.Quickstart/2.Syntax/6.Escape/1.Locality.pd; .../6.Escape/2.More.Examples.pd)`
- **`set` pairs two GUIs without a loop** — a `set` message changes a number box, slider or message box without output. That is how two controls mirror each other without a feedback loop. `(source: Part.01-The.Basics/01-Pd.Quickstart/2.Syntax/8.Set/1.Messages.GUIs.pd)`
- **`sinesum` / `cosinesum` fill an array from harmonic amplitudes** — the first number is the table size (the array is always resized), then one amplitude per harmonic. `cosinesum` takes a DC term first. `normalize` rescales to a target (1 by default). `(source: Part.01-The.Basics/01-Pd.Quickstart/2.Syntax/8.Set/2.Arrays.pd)`
- **`fast-forward` renders faster than real time** — sending `fast-forward <ms>` to Pd computes that much audio as fast as the CPU allows. The example records noise to a file with `[writesf~]` this way. `(source: Part.01-The.Basics/01-Pd.Quickstart/3.fast-forward.pd)`
- **Key auto-repeat must be turned off in the OS** — otherwise held keys show up as repeated release and press events in `[key]` / `[keyup]`. `(source: Part.01-The.Basics/01-Pd.Quickstart/4.Interaction.pd)`
- **How the tutorial loads ELSE** — ELSE ships as separate binaries, so the tutorial uses `[declare -path else]` in each patch instead of a global path. `[declare]` also takes priority over the user search paths, which matters when two libraries share an object name. ELSE and this tutorial are built into plugdata. `(source: Part.01-The.Basics/01-Pd.Quickstart/5.Externals.pd)`
- **`out~` is the tutorial's standard output** — an ELSE abstraction around `[dac~]`, stereo, with a gain slider. Dragging the slider turns DSP on. A mono input goes to both speakers. A multichannel input is summed to one channel. `setdsp~` turns DSP on or off with a toggle and can force the state when the patch opens. `(source: Part.01-The.Basics/01-Pd.Quickstart/6.Audio.DSP.Pd/1.[adc~].[dac~].pd; .../3.Multichannel.pd)`
- **Multichannel cords exist in Pd 0.54** — one cord can carry many channels. `[snake~ in]` packs channels and `[snake~ out]` unpacks them. ELSE adds tools: `nchs~` (count channels), `sum~`, `merge~`, `pick~`, `get~`, `sigs~`, `unmerge~`, `slice~`, `repeat~`, `lace~`, `delace~`. `sine~ -mc 440 880` makes a two-channel oscillator. `(source: Part.01-The.Basics/01-Pd.Quickstart/6.Audio.DSP.Pd/3.Multichannel.pd)`
- **Block size is 64 and fixed for `[adc~]` / `[dac~]`** — at 44.1 kHz one block is about 1.45 ms. `[block~]` changes the block size for the window it sits in, so it goes in a subpatch. A bigger block adds latency equal to block size minus 64 samples. `(source: Part.01-The.Basics/01-Pd.Quickstart/6.Audio.DSP.Pd/4.AudioXControl-Rate/2.Audio.Block.pd)`
- **`[switch~]` can compute a single block on a bang** — it is `[block~]` plus a local DSP on/off. Banged while it is off (and global DSP is on), it runs exactly one block. The tutorial suggests this for one-shot jobs like precomputing a waveform. `(source: .../4.AudioXControl-Rate/2.Audio.Block.pd)`
- **Pd has no fixed control rate; Max is said to default to 2 ms** — the author says Max/MSP has a default control resolution of 2 ms that can go down to 1 ms, and SuperCollider's is one block (about 1.45 ms at 44.1 kHz / 64). Pd control objects are not clocked, but a control value can only affect audio once per block, so in practice the block is Pd's control rate too. `(source: .../4.AudioXControl-Rate/3.Control.Rate.pd)`
- **Not every Pd audio object has signal inlets for its parameters** — `[bp~]` takes centre frequency and Q as control data only. `(source: .../4.AudioXControl-Rate/3.Control.Rate.pd)`
- **Mouse, key and MIDI events are always aligned to a block edge** — a click lands on a multiple of 64 samples. `[metro]` and `[delay]` are not limited this way and can be sample-exact (`[metro 1 1 samps]`, `[delay 0 1 samps]`). `(source: .../4.AudioXControl-Rate/4.Convert.Audio2Control.pd)`
- **Signal to control: `[snapshot~]` only gives the last sample of the block** — `[vsnapshot~]` gives the exact sample. ELSE's `sig2float~` (short name `s2f~`) polls at a rate given as an argument and can take any sample in the block through an offset. It also turns a multichannel signal into a list, which vanilla cannot do. `(source: .../4.Convert.Audio2Control.pd; .../6.multichannel.conversion.pd)`
- **Control to signal: `[sig~]` takes one value per block, `[vline~]` is sample-exact** — with a metro firing every sample, `[vline~]` puts a new value on every sample and `[sig~]` keeps only the last. ELSE's `float2sig~` (`f2s~`) is a `[vline~]` wrapper with a ramp time argument. `float2imp~` turns a float or bang into a one-sample impulse, sample-exact, even several per block. `(source: .../5.Convert.Control2Audio.pd)`
- **Going back from signal to bang loses timing** — `trig2bang~` and vanilla `[threshold~]` output bangs on block edges, so a 500 ms pulse does not measure as exactly 500 ms with `[timer]`. Staying in the signal domain (`status~` makes an impulse on each 0/non-0 change, `detect~` measures the time between impulses) gives the exact figure. `(source: .../7.Control.Rate2.pd)`
- **Feedback needs a one-block delay, and a subpatch does not hide a loop** — a direct signal loop stops the DSP chain with "DSP loop detected". Pairs that add one block of delay and make feedback legal: `[send~]/[receive~]`, `[tabsend~]/[tabreceive~]`, `[throw~]/[catch~]`, `[delwrite~]/[delread~]`. If the send/receive pair is inside a subpatch but the loop is still cabled in the parent, it still fails. `(source: Part.01-The.Basics/01-Pd.Quickstart/6.Audio.DSP.Pd/5.DSP-Feedback.Loop.pd)`
- **One-sample feedback recipe** — put the loop in a subpatch with `[block~ 1]` (or `[switch~ 1]`). The one-block delay is then one sample. Before Pd 0.54 `send~/receive~` and `throw~/catch~` only worked at block size 64. `(source: .../5.DSP-Feedback.Loop.pd)`
- **`send~` / `receive~` may add a block of delay even with no feedback** — it depends on creation order. To force the order, put the sender and the receiver in two subpatches and join them with a dummy `[outlet~]` to `[inlet~]` cord. The same trick works for `tabsend~`, `throw~` and delay lines. `(source: Part.01-The.Basics/01-Pd.Quickstart/6.Audio.DSP.Pd/6.Execution.Order.pd)`
- **`[pd~]` runs a patch in a second Pd process** — this spreads load over CPU cores. Each `[pd~]` opens one patch. `-ninsig` / `-noutsig` set the signal ports. ELSE's `abs.pd~` wraps it so it opens like an abstraction and passes MIDI. `meter` reports CPU use of the current process. `(source: Part.01-The.Basics/01-Pd.Quickstart/6.Audio.DSP.Pd/7.pd~.pd)`

### 02 Digital Audio

- **Foldover formula** — above Nyquist the heard frequency is `Nyquist - (f - Nyquist)`. It folds again at 0 Hz. At 44.1 kHz, asking for 40 kHz gives 4.1 kHz. ELSE's `fold` does this maths and `nyquist~` reports Nyquist. `(source: Part.01-The.Basics/02-Digital.Audio/1.SampleRate/1.Aliasing.Foldover.pd)`
- **Decimator = sample-and-hold driven by an impulse train** — `downsample~` takes a rate in Hz and holds each value. The longer recipe is `sh~` triggered by `impulse~`; the impulse rate is the new sample rate. The real sample rate does not change, so energy still shows across the whole spectrum; what you hear is aliasing. `(source: Part.01-The.Basics/02-Digital.Audio/1.SampleRate/2.Decimator(SR-Reduction).pd)`
- **`downsample~` can interpolate instead of hold** — an `interp` message (or second argument) switches to linear interpolation between held values. The vanilla version uses `[vsnapshot~]` to grab values and `[vline~]` to draw the lines. `(source: Part.01-The.Basics/02-Digital.Audio/1.SampleRate/3.Interpolation.pd)`
- **Real resampling is the third argument of `[block~]`** — arguments are block size, overlap, resampling ratio. The ratio must be a power of two (up or down). The `[inlet~]` and `[outlet~]` of that subpatch do the actual resampling, and their argument picks the fill method: `pad` (zeros, the default), `hold`, or `lin`. `(source: Part.01-The.Basics/02-Digital.Audio/1.SampleRate/4.Resampling.pd)`
- **Usable output resolution is put at roughly 24 bits** — Pd audio is 32-bit float, which has finer steps near zero. The author estimates about 24 bits between -1 and 1. He also says sound cards sold as 24-bit do not really reach it; 20 to 21 bits (about 120 dB) is more realistic. `(source: Part.01-The.Basics/02-Digital.Audio/2.Bit-Depth/1.Bit-Depth.pd; .../2.SNR.pd)`
- **6.0206 dB per bit** — 16 bits gives about 96.33 dB of dynamic range, 24 bits 144.5 dB. `(source: Part.01-The.Basics/02-Digital.Audio/2.Bit-Depth/2.SNR.pd)`
- **Bit-crusher recipe** — round the signal to a step size: `rint(x*n)/n` in `[expr~]`. ELSE's `quantizer~` takes the step and has several rounding modes (nearest by default, truncate, floor, ceil). For bit crushing it uses "mode 4": floor for negative values, ceil for positive. The step for b bits in the example is 1 / 2^b. `(source: Part.01-The.Basics/02-Digital.Audio/2.Bit-Depth/3.Bit-Crush.pd)`
- **`crusher~` = `quantizer~` + `downsample~`** — an ELSE abstraction with two 0 to 1 controls (crush, decimate). 0 leaves the sound alone. `crusher.m~` is the same as a MERDA module. `(source: .../3.Bit-Crush.pd; .../4.crusher.m~.pd)`
- **MERDA module conventions** — MERDA ("Modular EuroRacks Dancing Along") is a set of ELSE abstractions that look like Eurorack modules; names end in `.m~`. Signal modulation inputs go through an "attenuverter" knob: noon is zero, clockwise scales 0 to 1, anticlockwise scales 0 to -1 (inverts). The modulation is added to the knob value and clipped. Knobs save their state, and `presets.m` manages presets. `(source: Part.01-The.Basics/02-Digital.Audio/2.Bit-Depth/4.crusher.m~.pd)`

### 03 Intervals and Tuning

- **Equal division of any interval** — one step of interval x divided in y parts is x^(1/y). Semitone = 2^(1/12), about 1.05946. Cents = 1200 * log2(ratio). ELSE: `ratio2cents`, `cents2ratio`. `(source: Part.01-The.Basics/03-Intervals-Tuning/1.Musical.Intervals.pd; .../2.Cents.pd)`
- **`eqdiv`, `gmean`, `amean` build scales** — `eqdiv 13 3` gives the Bohlen-Pierce scale (ratio 3 in 13 steps, about 146 cents each, 0 to 1901.95 cents) as a list of cents. `gmean` does the same as ratios (geometric steps). `amean` makes arithmetic steps. `(source: Part.01-The.Basics/03-Intervals-Tuning/3.[eqdiv].[gmean].[amean].pd)`
- **Fractions as input** — the boxes show `frac2dec` and `frac2cents`, so a list like `1 9/8 5/4 3/2 2` can be typed as fractions. The comment text names `frac2cents` twice; from the boxes, one of them should be `frac2dec`. A just fifth (3/2) is about 702 cents against 700 tempered. `(source: Part.01-The.Basics/03-Intervals-Tuning/4.Just.Intervals.vs.Tempered.pd)`
- **MIDI cents** — fractional MIDI pitch is used as a cents scale: 0.01 = 1 cent. Convert cents to MIDI cents by dividing by 100. Many ELSE oscillators take MIDI pitch directly (`sine~ -midi 60`). `(source: Part.01-The.Basics/03-Intervals-Tuning/5.MIDI-&-MIDIcents.pd)`
- **mtof with a different A4** — formula: `2^((m-69)/12) * A4`. ELSE's `midi2freq` and `freq2midi` take the A4 value as an argument and convert lists. To keep using vanilla `[mtof]`: turn the ratio newA4/440 into cents, divide by 100, add that to the MIDI pitch. `(source: Part.01-The.Basics/03-Intervals-Tuning/6.[midi2freq].[freq2midi].pd)`
- **Autotune to an equal-step scale** — subtract a base pitch (60), divide by the step in MIDI cents, round, multiply back, add the base. `quantizer` shortens this. For uneven scales `autotune` takes a list of cents and finds the nearest step; it is less efficient than the rounding recipe for equal steps. `autotune2` retunes cents values directly. `scala` imports Scala tuning files. `(source: Part.01-The.Basics/03-Intervals-Tuning/7[autotune]-[autotune2].pd)`
- **`retune` maps keys, `autotune` snaps pitch** — with steps wider than a semitone (Bohlen-Pierce), snapping makes two neighbouring keys land on the same pitch; with narrower steps (octave in 13) some steps are never reached. `retune` instead maps each key above the base to the next scale step: base+3 always plays step 3. `(source: Part.01-The.Basics/03-Intervals-Tuning/8.[retune].pd)`

### 04 Amplitude and dB

- **Trap: Pd's `[rmstodb]` / `[dbtorms]` are a 0 to 100 scale, and the name misleads** — reference is 1e-05, so amplitude 1 = 100 dB. Inputs below 1e-05 clip to 0 dB; `[dbtorms]` of 0 dB gives 0, not 1e-05. The author notes the names wrongly suggest "rms" means "linear". `[env~]` reports on this same 0 to 100 scale. `(source: Part.01-The.Basics/04-Amplitude-dB/2.Linear-dB.pd; .../5.Peak-RMS.pd)`
- **Use `db2lin` / `lin2db` for dBFS** — ELSE objects, 0 dB = amplitude 1. `db2lin` treats -100 dB as silence (outputs 0), so a -100 to 0 slider reaches true zero. An argument sets another floor, down to `-inf`. Signal versions: `db2lin~`, `lin2db~`. `(source: Part.01-The.Basics/04-Amplitude-dB/3.dBFS.pd)`
- **Peak vs RMS** — for a sine, RMS reads about 3 dB under peak. ELSE: `rms~` and `peak~` (both built on `[env~]`, linear or dBFS output), and `mov.rms~`, a moving RMS that gives a new value every sample. `(source: Part.01-The.Basics/04-Amplitude-dB/5.Peak-RMS.pd)`
- **Clipping happens at the converter, not inside Pd** — signals can exceed ±1 inside a patch. Pd's `[vu]` is only a display; ELSE's `vu~` does the analysis (RMS left, peak right). `meter~`, `meter2~`, `meter4~`, `meter8~` bundle both. `maxpeak~` holds the highest peak seen and bangs when it passes 0 dB. `(source: Part.01-The.Basics/04-Amplitude-dB/6.VU-Clipping.pd; .../7.[maxpeak~].pd)`

### 05 Gain Adjustment

- **Anti-click: ramp every gain change, about 10 ms** — muting with a raw 0/1 multiply clicks. Use `[line~]` with `$1 10`, or `f2s~ 10`. `numbox~` has its own ramp setting (10 ms by default), so it needs no extra smoothing. `(source: Part.01-The.Basics/05-Gain.Adjustment/1.Mute.Unmute.pd; .../2.dB.pd)`
- **Quartic gain curve as the default fader law** — raising a 0 to 1 control to the 4th power is offered as an alternative to dB. It gives more audible level at low slider positions than the dB curve. ELSE's `gain~` and `out~` use quartic by default and can switch to dB or linear. `(source: Part.01-The.Basics/05-Gain.Adjustment/3.Quartic.[gain~].[out~].pd)`
- **Gain objects** — `dbgain~` takes dB directly. `level~` is a GUI wrapper for it, from minus infinity to +12 dB. `gain2~` is stereo; `out4~`, `out8~`, `out.mc~` are multi-speaker outputs. `vca.m~` is a MERDA VCA with a meter and ±12 dB master. A VCA is just `[*~]`. `(source: Part.01-The.Basics/05-Gain.Adjustment/4.[out.mc~].[out4~].[out8~].[gain2~].pd; .../5.Gain.Adjustment.pd; .../7.[vca.m~].pd)`

### 06 Oscillators (basics)

- **Phase is 0 to 1, not radians, at signal rate** — `[phasor~]` outputs 0 to 1 and `[cos~]` (vanilla) and `sin~` (ELSE) take 0 to 1 as one cycle. `[phasor~]` + `[cos~]` is what `[osc~]` is; `[phasor~]` + `sin~` is what ELSE's `sine~` is. Control-rate `[sin]` / `[cos]` take radians; ELSE's `pi` outputs pi. `(source: Part.01-The.Basics/06-Oscillators/1.Sine-Cosine.pd; .../2.Phasor.pd; .../3.Oscillator.pd)`
- **`[phasor~]` accepts negative frequency** — the phase then runs backwards. `(source: Part.01-The.Basics/06-Oscillators/3.Oscillator.pd)`
- **Radians per sample** — Hz * 2pi / sample rate. ELSE: `hz2rad`, `rad2hz`. `(source: Part.01-The.Basics/06-Oscillators/4.Frequency.pd)`

### 07 Phase

- **Polarity inversion is not a 180° phase shift** — multiplying by -1 flips sign; a phase shift is a time shift. They match only for waves whose second half mirrors the first (sine, triangle, 50% square). For a sawtooth, only the polarity flip cancels the original. The author calls "phase invert" on audio gear a misnomer. `(source: Part.01-The.Basics/07-Phase/3.Polarity-Inversion.pd)`
- **Two saws, half a cycle apart** — summed, they give double the frequency, not silence. Flip the polarity of one as well and the sum is a square wave. `(source: Part.01-The.Basics/07-Phase/5.Modulate_Phase2.pd)`
- **Phase offset by adding to the phasor, smoothed** — add an offset to `[phasor~]` before the sine function. A sudden offset clicks, so it is ramped with `float2sig~ 50`. During the 50 ms ramp the pitch shifts briefly, then returns. `(source: Part.01-The.Basics/07-Phase/4.Modulate_Phase.pd)`
- **ELSE oscillator inlet layout** — second inlet resets phase, third inlet is phase modulation. Vanilla `[osc~]` has reset (control only) and no phase modulation. Reset and phase modulation are separate things. `(source: Part.01-The.Basics/07-Phase/6.Reset_Phase.pd; .../4.Modulate_Phase.pd)`
- **Lissajous check for phase** — feed two sines to the two inlets of `scope~`; a diagonal line means in phase. `(source: Part.01-The.Basics/07-Phase/4.Modulate_Phase.pd)`

## Part 02 — Basic Processing

### 08 Sum and Subtract

- **Cords into one signal inlet sum** — as in Max, so `[+~]` is often redundant. `[throw~]` / `[catch~]` is a named summing bus. `(source: Part.02-Basic-Processing/08-Sum.Subtract/1.Mix.pd; .../2.[throw~](Bus).pd)`
- **Beating rate = frequency difference** — 400 Hz + 401 Hz beats at 1 Hz. `(source: Part.02-Basic-Processing/08-Sum.Subtract/4.Beatings.pd)`

### 09 Fade in / out — six families of smoother

- **`fader~`: seven fade curves on a 0 to 1 input** — names seen in the patch: `lin`, `quartic`, `sin`, `sqrt`, `hann`, `hannsin`, `linsin`. (The comment text spells it `fade~` once; the box is `fader~`.) `(source: Part.02-Basic-Processing/09.Fade.in.out/1.Fade-in-out.[fader~].pd)`
- **`autofade~` / `autofade2~`: gate in, fade out** — a gate above zero starts a fade in, zero or below starts a fade out. The gate's value sets the top gain. Arguments: fade time in ms, number of signal inputs. The `2` version has separate in and out times. `.mc~` versions exist. `(source: Part.02-Basic-Processing/09.Fade.in.out/2.[autofade~].[autofade2~].pd)`
- **`glide~`: fixed-time ramp, optional curve** — like `[line~]` but driven by a float or a signal. Linear by default; `-exp 4` gives a quartic shape. `glide2~` has separate up and down times. Meant for portamento. `(source: Part.02-Basic-Processing/09.Fade.in.out/3.[glide~].[glide2~].pd)`
- **`lag~`: a lowpass used as a smoother** — similar use to `glide~`, but the curve differs going up and down. `lag2~` has separate times. `smooth~` is described as like `lag~` but with a settable curve (`-curve`), linear by default. `(source: Part.02-Basic-Processing/09.Fade.in.out/4.[lag~].[lag2~].pd; .../5.[smooth~].[smooth2~].pd)`
- **`slew~`: fixed speed, not fixed time** — the limit is amplitude units per second, not per sample, so the per-sample step depends on the sample rate. `slew2~` has separate up and down limits. `(source: Part.02-Basic-Processing/09.Fade.in.out/6.[slew~].[slew2~].pd)`
- **Vanilla `[slop~]` does both jobs** — slew limiting uses inlet 3 (down) and inlet 5 (up), in amplitude per sample, so divide a per-second limit by the sample rate. Lowpass smoothing uses inlet 4 (down) and inlet 6 (up), in Hz; convert a time with 1000 / ms. `(source: Part.02-Basic-Processing/09.Fade.in.out/7.[slop~].pd)`

### 10 Signal Routing

- **Linear crossfade = constant voltage, -6 dB in the middle** — gains are x and 1-x and always add to 1. `(source: Part.02-Basic-Processing/10-Signal-Routing/1.Crossfade/1.Linear.Equal-Voltage.Crossfade.pd)`
- **Equal-power crossfade recipe** — use the first quarter of a cycle: position 0 to 1, divided by 4, into `[cos~]` and `sin~`. The squares of the two gains add to 1, and the middle is about -3 dB. `xfade~` does this by default; `-lin` makes it linear; its argument is the channel count per source. `(source: Part.02-Basic-Processing/10-Signal-Routing/1.Crossfade/2.SinCos-EqualPower-Crossfade.pd; .../3.[xfade~].[xfade.mc~].pd)`
- **Three pan laws and the curve for each** — 6 dB: linear, or `hann` (half a cosine cycle). 3 dB: sine/cosine, or square root. 4.5 dB (the compromise): `linsin` and `hannsin`, which average the two. All are in `fader~`. The author's view: pick what feels right. `(source: Part.02-Basic-Processing/10-Signal-Routing/2.Pan/2.Pan.Law.pd)`
- **No pan law gives full level to both speakers at centre** — to send mono equally at full level, just duplicate the signal. `(source: Part.02-Basic-Processing/10-Signal-Routing/2.Pan/2.Pan.Law.pd)`
- **`pan2~` runs -1 to 1** — equal power; the bipolar range is chosen so an audio signal can drive it. `pan4~` is two `pan2~` stages (x for left/right, y for back/front), best driven from a 2D slider. `(source: Part.02-Basic-Processing/10-Signal-Routing/2.Pan/1.Equal.Power.Pan.pd; .../3.[pan4~].pd)`
- **`pan~`: circular panning over N speakers with a spread control** — position is 0 to 1 and wraps (an azimuth). Spread 1 is normal. Above 1 the signal reaches more neighbours; the text gives the neighbour gain at spread 2 as the square root of 0.5. Below 1 the overlap narrows; at 0.5 there is no crossfade and both neighbours are silent at the midpoint. `(source: Part.02-Basic-Processing/10-Signal-Routing/2.Pan/4.[pan~].[pan.mc~].pd)`
- **`balance~`** — equal-power balance for a stereo pair (left times cosine, right times sine of the position). `(source: Part.02-Basic-Processing/10-Signal-Routing/3.[balance~].pd)`
- **Cheap stereo widening** — (1) Haas effect: copy the mono signal and delay one side; 7 to 21 ms is given as a good range (the patch uses `ffdelay~`). (2) Invert the polarity of one side. The patch does both at once. `(source: Part.02-Basic-Processing/10-Signal-Routing/4.Stereo.Widening.pd)`
- **`spread~` and `rotate~`** — `spread~ 3 2` places 3 inputs evenly across 2 outputs with equal-power panning and a spread inlet. Rotation of a stereo pair is two pans with opposite positions; `rotate~` does it for any channel count. `(source: Part.02-Basic-Processing/10-Signal-Routing/5.[spread~].[spread.mc~].pd; .../6.[rotate~].[rotate.mc~].pd)`
- **Click-free switching objects** — `xselect~ 4 1000` picks one of 4 inputs with a 1000 ms crossfade. `xgate~` is the reverse: one input to one of N outputs. `mtx~` is a matrix with equal-power fades, driven by the `mtx.ctl` grid. `xselect2~` / `xgate2~` take the channel as a signal, so you set the crossfade point yourself. `select~` switches with no fade. `.mc~` versions exist. `(source: Part.02-Basic-Processing/10-Signal-Routing/7.Routing1.pd; .../8.Routing2.pd; .../9.Multichannel.routing.pd)`

### 11 Dynamics

- **Noise gate recipe** — `mov.rms~` (running RMS) → compare with the threshold using `op~ >` (gives 1 or 0) → `glide~ 10` to smooth → multiply the input. The glide time is the attack and release; `glide2~` separates them. ELSE's `noisegate~` is built this way. `(source: Part.02-Basic-Processing/11-Dynamics/1.Noise-Gate.pd)`
- **Live normalizer recipe** — gain = target amplitude / running RMS (`mov.rms~ -lin`), then multiply. This is `norm~`. Put a noise gate before it, or it lifts the noise floor to the target. `(source: Part.02-Basic-Processing/11-Dynamics/2.Normalizer.pd)`
- **Soft clipping** — `tanh(x * gain)`. It always distorts a little and approaches hard clipping at high gain. `tanh~` is cheaper than `[expr~]`. `drive~` does the same by default and has two other modes; `drive.m~` is the module, gain knob 0.1 to 1000. `(source: Part.02-Basic-Processing/11-Dynamics/4.Soft.Clipping.pd)`
- **Compressor recipe with numbers** — level in dB (`mov.rms~`) minus threshold gives the overshoot. Gain change in dB = -overshoot * (1 - 1/ratio), limited with `[min~ 0]` so it never boosts. Example: 10 dB over at ratio 3 gives -6.67 dB, leaving 3.33 dB over. `glide2~` smooths the gain: the downward ramp is the attack, the upward ramp the release. Then `db2lin~` and a make-up gain. Fast attack and ratio about 10 make a limiter. This is the basis of `compress~`. `(source: Part.02-Basic-Processing/11-Dynamics/5.Compressor.pd)`
- **Peak mode = RMS window of 1** — taking the absolute value (`[abs~]`) is the same as `mov.rms~` with a window of one sample. It reacts faster. `compress~` gets this mode with window size 1. `(source: Part.02-Basic-Processing/11-Dynamics/6.Ducking.pd)`
- **Ducking (side-chain)** — same structure, but the level is measured on a second "control" signal and the gain is applied to the input. ELSE's `duck~` can also mix the two. `(source: Part.02-Basic-Processing/11-Dynamics/6.Ducking.pd)`
- **Expander** — same patch with the subtraction reversed (threshold minus level), so gain drops below the threshold. High ratio (about 10) with fast times makes it a noise gate. The box is `expand~`; the comment says "basis of `compress~`", which looks like a leftover from the compressor patch. `(source: Part.02-Basic-Processing/11-Dynamics/7.Expander.pd)`

## Part 03 — Sound Generators

### 12 Oscillators

- **`[osc~]` is cheaper; `[phasor~]` + `[cos~]` allows phase modulation** — ELSE's `sine~` and `cosine~` give both reset and a phase-modulation inlet. `(source: Part.03-Sound.Generators/12-Oscillators/1.Waveforms/1.Sine.Cosine.pd)`
- **`[tabosc4~]` needs power-of-two tables plus 3 guard points** — `sinesum` makes exactly that (e.g. 512 + 3), so it suits `[tabosc4~]` only. The 4 in the name is 4-point Lagrange interpolation. A negative partial amplitude inverts that partial. `(source: Part.03-Sound.Generators/12-Oscillators/1.Waveforms/2.Wavetable/1.[tabosc4~].pd)`
- **`wavetable~` takes any table size and no guard points** — it adds the guard copies itself, so a `sinesum` table is the wrong input for it. It can load a single-cycle file (via `sfload`). Default interpolation is 4-point `spline`; also `lagrange`, `lin`, `cos` (half-cosine between points) and `none`. `(source: .../2.Wavetable/2.[wavetable~].pd; .../2.Wavetable/3.[tabgen].interpolation.pd)`
- **`tabgen` instead of `sinesum`** — it fills a table of any size and allows non-integer partial ratios and a start phase per partial. The example message is `sin 1 0 1 2 0 0.5 3 0 -0.5`; the exact meaning of each number is not explained in the text. It can also fill a table with noise or a Gaussian. `(source: .../2.Wavetable/3.[tabgen].interpolation.pd; .../6.[gaussian~].pd; .../9.[oscnoise~].pd)`
- **Partial recipes for the classic waves** — saw: amplitude 1/p. Second saw shape (`saw2~`): 1/p with every even partial inverted; it sounds the same. Square: 1/p, odd partials only. Triangle: 1/p², odd only, with every partial where p mod 4 = 3 inverted. Impulse: all partials equal, as a sum of cosines. `(source: .../3.Saw-Tri/1.Sawtooth.pd; .../3.Saw-Tri/2.Sawtooth-2.pd; .../3.Saw-Tri/3.Triangular.pd; .../4.Square.pd; .../5.(Im)Pulse/1.Impulse.pd)`
- **ELSE's plain `saw~`, `tri~`, `square~` are "perfect", so they alias** — they are the ideal shapes with all harmonics. `saw~` is a falling ramp. `square~` has a pulse-width inlet (0 to 1, default 0.5). `(source: .../3.Saw-Tri/1.Sawtooth.pd; .../4.Square.pd; Part.03-Sound.Generators/12-Oscillators/3.Band.Limited(Anti-Aliased)/1.[bl.osc~].wavetables.pd)`
- **`vsaw~`: one width control from saw to triangle** — width 0 and width 1 are the same wave with opposite polarity. `(source: .../3.Saw-Tri/4.[vsaw~].pd)`
- **Vanilla triangle from a phasor** — the patch uses `[phasor~]`, a second branch `[*~ -1]` `[+~ 1]`, `[min~]`, `[-~ 0.25]`, `[*~ 4]`, and resets the phasor to 0.25 so the triangle starts at zero. The text does not spell out the wiring; this is read from the box list. `(source: .../3.Saw-Tri/3.Triangular.pd)`
- **Impulse and pulse objects** — `impulse~` (short `imp~`): one sample of 1 at the start of each period; used as an audio-rate "bang". `pulse~`: 0/1 gate wave with a width. `impulse2~`: adds a -1 impulse placed by the width value. At width 0 `square~` and `pulse~` shrink to a single high sample. `(source: .../5.(Im)Pulse/1.Impulse.pd; .../2.Pulse-Train.pd; .../3.Bipolar-Pulse.pd; .../4.Square.pd)`
- **Parabolic wave from a saw** — square a sawtooth: `x² * 2 - 1` (and the inverted form). It looks like a sine but has odd partials. `parabolic~` is the oscillator. `(source: .../7.Parabolic.pd)`
- **`function~`: a breakpoint waveform read by a phasor** — a list of levels and segment lengths defines the shape; `[phasor~]` scans it. The `function` GUI lets you draw it. Segments can be curved: a symbol like `^2` sets an exponent (2 on all four segments matches `parabolic~`), and `curve hann` / `curve sin` / `curve lin` set shapes. `(source: .../8.[function~].pd)`
- **Noise as a wavetable** — fill a table with random values and read it with `[phasor~]` + `[tabread4~]`, with table length = sample rate / frequency. `oscnoise~` does this; a bang makes a new table. `(source: .../9.[oscnoise~].pd)`
- **Hard sync needs an audio-rate reset** — the reset inlets of vanilla `[osc~]`, `[phasor~]`, `[tabosc4~]` are control rate and too coarse. Every ELSE oscillator can be reset by an impulse signal. Recipe: master `impulse~` at the master frequency into the slave's sync inlet. `(source: Part.03-Sound.Generators/12-Oscillators/2.Sync/1.HardSync.pd)`
- **Vanilla hard-sync trick** — take the master phasor, multiply its phase by slave/master frequency ratio, `[wrap~]`, then `[cos~]`. `(source: .../2.Sync/1.HardSync.pd)`
- **How sync sounds** — slave lower than master: the cycle is cut short. Slave higher: part of a cycle repeats; much higher gives several cycles per reset and a sharper tone. `(source: .../2.Sync/1.HardSync.pd)`
- **Soft sync, two versions** — (1) Keep the slave from going below the master with `[max~]`, so a cycle is never cut. (2) Reverse direction instead of resetting: multiply the slave's frequency by a square wave at half the master frequency, so the sign flips each master period. No jump, so no click. ELSE oscillators do version 2 with a `-soft` flag. Listed as having it: `pimp~`, `sine~`, `cosine~`, `bl.saw~`, `bl.saw2~`, `bl.vsaw~`, `bl.square~`, `bl.tri~`, `blip~`, `bl.osc~`, `wavetable~`, `bl.wavetable~`. `(source: .../2.Sync/2.Soft-sync_1.pd; .../2.Sync/3.Soft-sync_2.pd)`
- **Sync sound from a table** — a table holding a non-whole number of sine cycles (`tabgen` with `sin 1.3`) has a jump at the wrap, which is the same result as hard sync. `(source: .../2.Sync/4.[tabgen].pd)`
- **Band-limiting by partial count, with numbers** — at 44.1 kHz the limit is 10 partials at 2 kHz and 100 at 200 Hz. So one table per waveform is not enough: use more partials for low notes, fewer for high. `(source: Part.03-Sound.Generators/12-Oscillators/3.Band.Limited(Anti-Aliased)/1.[bl.osc~].wavetables.pd)`
- **`bl.osc~`** — built on `wavetable~` with internal band-limited tables. Arguments: waveform (`saw`, `saw2`, `tri`, `square`, `imp`), number of partials, frequency, phase. Changing waveform or partial count has no crossfade and can click. It has sync and phase-modulation inlets, but hard sync still aliases here. `(source: .../1.[bl.osc~].wavetables.pd)`
- **DSF oscillator** — Discrete Summation Formulae give the sum of many cosines as a ratio of two simpler signals, so cost does not grow with partial count. In this Pd version it only pays off when the partial count is high. A "spectral multiplier" m scales each next harmonic (m = 0.5 gives 1, 0.5, 0.25…; m = 1 gives an impulse-like wave). Naming is unclear: the patch file and box are `blip~`, the comment text calls the object `gbuzz~` (based on a Csound opcode). `(source: .../3.Band.Limited(Anti-Aliased)/2.[blip~].DSF.pd)`
- **Oversample-and-filter recipe** — in a subpatch: `[block~ 64 1 16]` (16x), make the wave, lowpass with a 10th-order Butterworth (`brickwall~`) at 3/4 of the original Nyquist, then leave the subpatch to downsample. Each filter order gives 6 dB per octave, so 60 dB per octave here. Result is "quasi" band-limited. It costs a lot of CPU. `(source: .../3.Band.Limited(Anti-Aliased)/3.Oversampling.pd)`
- **Oversampling works for anything that aliases** — any waveform with jumps, hard sync, and also phase or frequency modulation. `bl.wavetable~` is an abstraction that uses this method and reduces aliasing from sync and phase modulation too. `(source: .../3.Band.Limited(Anti-Aliased)/4.Oversampling2.[bl.wavetable~].pd)`
- **BLIT, BLEP, PolyBLEP — which ELSE object uses which** — all three fix the jumps in a waveform. BLIT: a train of lowpassed impulses (sinc shapes); integrating a unipolar train gives a saw, a bipolar train a square, integrating twice a triangle. BLEP: a band-limited step, often from a table. PolyBLEP: the step drawn by a polynomial, no table. ELSE uses PolyBLEP for `bl.saw~`, `bl.vsaw~`, `bl.tri~`, `bl.square~`, and BLIT for `bl.imp~`, `bl.imp2~`. The `bl.` versions keep the same inlets as the plain ones. `(source: .../3.Band.Limited(Anti-Aliased)/5.BLIT.BLEP&more.objects.pd)`
- **Hard sync of a `bl.` oscillator still uses a plain `impulse~`** — the trigger must be the non-band-limited impulse. `(source: .../5.BLIT.BLEP&more.objects.pd)`
- **`damp.osc~`: a decaying sine "ping"** — takes frequency (Hz or MIDI) and decay time in ms; triggered by a zero to non-zero signal or by a list. Left outlet starts at cosine phase and so clicks hard; right outlet starts at sine phase. `(source: Part.03-Sound.Generators/12-Oscillators/4.[damp.osc~].pd)`
- **`vco.m~`** — MERDA oscillator module: several waveforms, pitch in MIDI, modulation inputs for frequency, phase and pulse width, and a sync input (impulses) with a soft-sync toggle. `(source: Part.03-Sound.Generators/12-Oscillators/5.vco~.m.pd)`

### 13 Noise and Chaos

- **Seeds: vanilla `[noise~]` vs `white~`** — `[noise~]` starts from the same seeds every run (each copy gets its own). `[expr~]`'s random uses C's `rand()` and cannot be seeded. `white~` seeds from the clock, so each run differs; you can also set a seed. `[noise~]` uses a non-standard linear congruential generator; ELSE's random objects all use a Tausworthe generator, the one SuperCollider uses. The author says the quality gap is not audible. `(source: Part.03-Sound.Generators/13-Noise-Chaos/1.Noise.pd; .../2.[white~].pd)`
- **Clip noise is louder, not different** — `white~ -clip` outputs only -1 or 1. It sounds the same as white noise, but RMS is 0 dB against about -5 dB for normal white noise. `(source: Part.03-Sound.Generators/13-Noise-Chaos/2.[white~].pd)`
- **`pink~`: Voss-McCartney, octave count settable** — a sum of white noises band-limited to different widths, falling 3 dB per octave. 1 octave is plain white noise. The default count depends on sample rate so the lowest band starts near 20 Hz (12 octaves at 44.1 kHz); the maximum is 40. `(source: Part.03-Sound.Generators/13-Noise-Chaos/3.[pink~].pd)`
- **Brown noise as a random walk** — scale white noise to ±0.125 and add it to the previous output; fold at ±1 (1.02 becomes 0.98). Falls 6 dB per octave. Bigger steps sound whiter, smaller steps darker. The vanilla version is one `[fexpr~]`. `brown~` is the object. `(source: Part.03-Sound.Generators/13-Noise-Chaos/4.[brown~].pd)`
- **`gray~`** — flips one random bit at a time (gray code), after a SuperCollider class. Harsh and glitchy; its spectrum sits between brown and pink. `(source: Part.03-Sound.Generators/13-Noise-Chaos/5.[gray~].pd)`
- **Low-rate noise objects** — `lfnoise~` is white noise through a downsampler, with an impulse inlet to reset phase. `stepnoise~` holds values; `rampnoise~` interpolates. Downsampled noise is not truly band-limited: the spectrum is mirrored and copied, with dips showing at half and quarter rate. `(source: Part.03-Sound.Generators/13-Noise-Chaos/6.BandLimited.noise.pd)`
- **`velvet~` and `dust2~`** — sparse random ±1 impulses. `velvet~` places one per period at a random spot; `dust2~` has no period. Both keep a flat spectrum at any rate. At the top rate `velvet~` becomes clip noise and `dust2~` becomes white noise. `(source: Part.03-Sound.Generators/13-Noise-Chaos/7.[velvet~].[dust2~].pd)`
- **`perlin~`** — 1-D Perlin noise: at regular intervals it picks a new random slope through zero. So zero crossings come at a steady rate, unlike other low-rate noises. Works up to Nyquist. `(source: Part.03-Sound.Generators/13-Noise-Chaos/8.[perlin~].pd)`
- **Chaotic generators taken from SuperCollider** — `gbman~` runs `y[n] = 1 + |y[n-1]| - y[n-2]` at a rate in Hz (default Nyquist), with start values 1.2 and 2.1 that can be changed. Others in the patch: `standard~`, `cusp~`, `quad~`, `henon~`, `logistic~`, `crackle~`, `ikeda~`, `latoocarfian~`, `lincong~`, `lorenz~`. The map generators sound pitched and unstable, not like noise. A vanilla build of any such equation uses `[fexpr~]`. `(source: Part.03-Sound.Generators/13-Noise-Chaos/9.Chaotic.pd)`

## Part 04 — Control

### 14 — Trigger, LFO, LFNoise

- **Impulse vs gate, defined at signal rate** — A signal trigger is one non-zero sample in a stream of zeros; it acts like a bang. A gate is a signal that stays non-zero while "on". An impulse is described as the shortest possible pulse. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/1.Impulse&Gate.pd)`
- **"Trigger" in ELSE means impulse or gate** — Many ELSE objects fire on a zero to non-zero transition, so either an impulse or the rising edge of a gate triggers them. Objects that need one kind specifically say "impulse" or "pulse" in their name. `[rand.i~]` is given as an example that fires on a transition, not on an impulse only. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/1.Impulse&Gate.pd)`
- **Signal and control twins** — ELSE ships control-rate versions of its signal trigger generators: `[impulse]` sends bangs, `[pulse]` sends gates, and `[randpulse]`, `[randpulse2]`, `[gatehold]`, `[gaterelease]` exist beside the `~` forms. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/1.Impulse&Gate.pd)`
- **Gate shaping objects** — `[gatehold~]` keeps a gate open for a set time (ms) after it closes. `[gaterelease~]` closes a gate a set time after it opened. `[trighold~]` holds the value of an impulse or gate. `[gatedelay~]` delays only the gate-on edge; the gate-off passes at once. The tutorial suggests chaining these for complex gate handling. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/1.Impulse&Gate.pd; 2.trig.gate.delay.pd)`
- **Two trigger delays that differ on retrigger** — `[trig.delay~]` restarts its delay when a new impulse arrives before the delayed one is sent. `[trig.delay2~]` ignores the new impulse instead. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/2.trig.gate.delay.pd)`
- **Random trigger sources** — `[dust~]` and `[dust2~]` send impulses at random times with random values. `[velvet~]` sends impulses at random positions inside a regular period. `[randpulse~]` sends random gate values and `[randpulse2~]` flips between 0 and 1 at irregular times. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/1.Impulse&Gate.pd)`
- **Control-rate LFO for control-only inlets** — Vanilla `[bp~]` takes its centre frequency as control messages only, so a signal LFO cannot drive it directly. The tutorial uses ELSE's control-rate `[lfo]`, or converts a signal with `[sig2float~]`. `[rescale]` / `[rescale~]` map the range (for instance -1..1 to 500..1500) and can map with exponential curves. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/3.LFO.pd)`
- **`[pimp~]` = phasor plus impulse** — `[pimp~]` outputs a phase ramp and also an impulse at each period wrap. ELSE also has a control-rate `[phasor]`. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/3.LFO.pd)`
- **Impulse to gate** — `[toggleff~]` flips its state on each impulse. `[timed.gate~ 500]` turns an impulse into a gate of fixed length in ms. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/4.Impulse-Pulse.conversion.pd)`
- **Gate to impulse** — `[status~]` sends an impulse out its left outlet when a signal goes from zero to non-zero and out its right outlet when it returns to zero. `[gate2imp~]` just converts a pulse to an impulse. `[trig2bang~]` turns impulses or pulses into bangs. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/4.Impulse-Pulse.conversion.pd)`
- **Bang to impulse: use `[float2imp~]` for timing** — Both `[float2imp~]` and `[impseq~]` (default sequence "1") turn a bang into an impulse. The tutorial says `[float2imp~]` is the more accurately timed of the two. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/4.Impulse-Pulse.conversion.pd)`
- **Analysis objects that output impulses** — `[changed~]` fires when the signal changes by more than a threshold (default 0). `[changed2~]` fires when the signal changes direction. `[zerocross~]` has three outlets: up-crossings, down-crossings, both. `[above~]` fires left on rising past a threshold and right on falling back. `[schmitt~ lo hi]` outputs 1 at or above the high level and 0 at or below the low level. `[match~]` works like a signal `select`. `[pulsecount~]` counts triggers. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/5.Trigger.analysis.pd)`
- **Pd `[metro]` argument seen as a clock divider** — With the default 1 ms unit, the first argument is a count of units, so it divides a 1000 Hz base rate. With the unit set to `permin` (same as BPM) the right inlet still divides: 2 is half speed, 0.5 is double speed. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/1.[metro].divider.multiplier.pd)`
- **Trap: divider change vs tempo change take effect at different times** — A new interval/divider sent to `[metro]`'s right inlet only applies after the next bang. A `tempo` message applies at once, for the rest of the current period. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/1.[metro].divider.multiplier.pd)`
- **No separate clock multiplier needed** — A multiplier is the divider inverted (`[expr 1/$f1]`). Unlike most hardware clock modules, the factor can be any float, not only an integer. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/1.[metro].divider.multiplier.pd)`
- **Bang divider with a rest outlet** — `[bangdiv 4]` passes one bang in four and sends the others out a second outlet, which the tutorial uses for rhythm patterns. The hand-made version is a counter into `[select]`. Signal counterparts: `[pulsediv~]`, or `[pulsecount~]` into `[match~]`. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/2.[bangdiv].[pulsediv~].pd)`
- **`[tempo]` / `[tempo~]` with swing** — ELSE's `[tempo]` is built on `[metro]`, works in BPM by default (ms optional), and has a multiplier that, like `[metro]`'s divider, only applies after the next bang; change the BPM for an immediate change. `[tempo~]` outputs impulses. Flags seen: `-on`, `-mul 4`, `-div 4`. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/3.[tempo].[tempo~].pd; 19-Sequencing/2.[rec].[store].pd; 19-Sequencing/3.[list].[array].[text].text/6.Signal.rate.array.pd)`
- **What the swing number means** — Swing is a percent of allowed random deviation per beat. At 60 BPM and 100 % swing, a beat can be anywhere from twice as fast (120) to twice as slow (30). `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/3.[tempo].[tempo~].pd)`
- **Tempo helpers** — `[bpm]` converts between BPM and ms. `[tap]` gives a tempo from two taps. `[speed]` produces an accelerando or ritardando: a message such as `90 4` gives one BPM value per beat until it reaches 90 after 4 beats, and the right outlet gives the total time in ms. A `set` message arms it to wait for a bang. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/4.[bpm].[tap].[speed].pd)`
- **Trap: two free-running clocks drift when one changes ratio** — Changing the divider or multiplier of one of two `[metro]` or `[tempo]` objects easily puts them out of step, and changing it back does not fix it. ELSE's `[clock]` solves this: slave clocks carry the `-s` flag and a multiplier, which may be a fraction such as `4/3`, and always stay locked to the main `[clock]`. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/5.[clock].[polymetro].pd)`
- **`[polymetro]` for polyrhythm** — An abstraction built from `[clock]` objects (for instance `[polymetro 90 3/2]`). Its main feature is that it outputs beat numbers. `[polymetro~]` is the signal version, built on `[pimp~]` and `[pimpmul~]`, and outputs impulses. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/5.[clock].[polymetro].pd; 8.[polymetro~].pd)`
- **`[metronome]` knows time signatures** — A compiled object that takes `timesig` messages, including compound ones (`timesig 3/4 + 3/8`, `timesig 15/8 3`), syncs to `[clock]`, and reports beat, bar count and a 0–1 phase. The tutorial suggests using the bar count with `select` to fire sequences, like a DAW timeline. `[metronome~]` makes click tracks. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/6.[metronome].pd; 19-Sequencing/5.Rhythmic/8.[metronome].pd)`
- **Signal-rate synced clock: multiply the phase, not the frequency** — Two LFOs lose sync when one frequency is multiplied, same as two metros. `[pimpmul~]` multiplies (or divides) the phase of a `[phasor~]` or `[pimp~]`, so the result stays locked. Its right outlet gives an impulse at each wrap, so it works as a synced clock multiplier at signal rate, and fractions give polyrhythms. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/7.[pimpmul~].Phase.Sync.pd)`
- **A phase ramp is a general driver** — The same master phase can read a table with `[tabreader~]` to make waveforms, envelopes or sample playback, all in sync with the impulse clock. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/6.clock.metronome/7.[pimpmul~].Phase.Sync.pd)`
- **Low-frequency noise as a random control** — `[rampnoise~]` gives random ramps, `[stepnoise~]` random steps, and `[lfnoise~]` does both. Control versions `[lfnoise]`, `[stepnoise]`, `[rampnoise]` exist. The vanilla ramp-noise recipe shown is `[metro]` → `[random]` → `[pack float 500]` → `[line]`. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/7.LFNoise-Random.pd)`
- **Seeds: ELSE differs from vanilla** — ELSE random objects pick a new unique seed each time the patch opens; vanilla objects do not. Set a seed with a `-seed` flag or a `seed <n>` message; a bare `seed` message asks for a unique one again. Two objects with the same seed give the same sequence. Vanilla `[noise~]`, `[random]` and `[array random]` also take `seed`. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/8.Seed.pd)`
- **Downsampled noise as a seeded random source** — Sending `[pink~]`, `[brown~]`, `[gray~]`, `[white~]` or `[noise~]` through `[downsample~]` turns it into a low-rate random generator at signal rate. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/8.Seed.pd)`
- **Chaotic generators are not random and have no seed** — Objects such as `[lorenz~]`, `[henon~]`, `[logistic~]` take an initial state instead. They can run at a rate in Hz, so they can stand in for low-frequency noise, but the tutorial stresses they are not random generators. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/8.Seed.pd)`
- **Multichannel triggers as an LFO bank** — `[imp~ -mc 0.25 0.5 1 2]` outputs one multichannel signal with an impulse train per listed frequency. `[dust~ -ch 2 50]` sets the channel count with `-ch`. `[rand.i~]` and `[rand.f~]` accept multichannel triggers. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/9.Multichannel.pd)`

### 15 — Sample and Hold

- **How vanilla `[samphold~]` triggers** — It samples when the control input is smaller than its previous value. That is true once per cycle of a `[phasor~]` (positive frequency below Nyquist), which is what it was designed to be driven by. ELSE's `[sh~]` is triggered by impulses or pulses instead and is called more flexible. `(source: Part.04-Control/15-Sample_and_Hold/1.[samphold~].[sh~].pd)`
- **S&H of an LFO makes patterns** — Sampling one LFO at a rate set by another trigger gives stepped melodic patterns; the two rates together decide the pattern. Adding `[glide2~]` after `[sh~]` gives portamento between held values (in the example, on rising values). `(source: Part.04-Control/15-Sample_and_Hold/1.[samphold~].[sh~].pd)`
- **Trap: `[sh~]`'s default mode is a gate, not a latch** — By default `[sh~]` passes the input while the trigger signal is above a threshold (default 0). With an impulse that behaves as sample and hold, but with a long pulse the input just passes through while the pulse is high. `(source: Part.04-Control/15-Sample_and_Hold/3.Gate.pd)`
- **`[sh~ -tr]` for edge-triggered hold** — In "trigger" mode it samples once when the trigger rises above the threshold and will not sample again until the trigger has dropped below it. `thresh <value>` sets the threshold. `(source: Part.04-Control/15-Sample_and_Hold/3.Gate.pd)`
- **Smooth a gated pass-through** — When using `[sh~]` in gate mode, a glide after it removes the jump when the gate reopens. `(source: Part.04-Control/15-Sample_and_Hold/3.Gate.pd)`
- **Other things that count as sample and hold** — `[downsample~]` is treated as a fixed-rate S&H. S&H of `[white~]` gives stepped random values. The refresh rate of the control `[lfo]` is also a kind of S&H. `(source: Part.04-Control/15-Sample_and_Hold/2.[downsample~].pd; 4.[lfo].pd)`

### 16 — Lines

- **Pd `[line~]` is block-bound** — It can only start a ramp at the start of an audio block and end it at the end of a block, so its timing is coarse. `(source: Part.04-Control/16-Lines/1.[line].[line~].[vline~].pd)`
- **`[vline~]` is sample-accurate and schedulable** — It can start and stop at any time and takes a third number, a start delay in ms. One message box can hold several comma-separated segments, each with its own start time, such as `0, 1 1000 500, 0 1000 2000, 1 500 3000`. `(source: Part.04-Control/16-Lines/1.[line].[line~].[vline~].pd)`
- **Control `[line]` grain** — Control `[line]` outputs a value every 20 ms by default; the second argument or third inlet changes that. A single float makes any of the line objects jump at once, which is how a start point is set (`0, 1 1000`). `(source: Part.04-Control/16-Lines/1.[line].[line~].[vline~].pd)`
- **Line objects compared** — Pd's line family is linear only. `[glide~]` takes a ramp time and can be linear or exponential (`exp <n>` message, `-exp` flag). `[lag~]` takes a time but is a low-pass filter, so its curve is non-linear and differs between rising and falling. `[slew~]` takes a speed (amplitude per second) rather than a time. All three can also follow a signal target, not just a message. `(source: Part.04-Control/16-Lines/2.[glide~].[lag~].[slew~].[slop~].pd)`
- **The "2" suffix means separate up and down settings** — `[glide2~ 500 250]`, `[lag2~ 500 250]`, `[smooth2~ 500 250]`, `[slew2~]` take one value for rising and one for falling. (The text shows this by use; it does not state the naming rule in this part.) `(source: Part.04-Control/17-Envelopes/2.Classic.Types/03.ASR/3.[glide2].[lag2~].[smooth2~].[autofade2~].pd)`
- **Control-rate versions exist** — `[slew]`, `[slew2]`, `[glide]`, `[glide2]`, `[smooth]`, `[smooth2]` make the same lines at control rate. `(source: Part.04-Control/16-Lines/3.[slew].[slew2].[glide].[glide2].pd; 4.[smooth~].[smooth~].pd)`
- **`[smooth~]`** — Takes a time, is linear by default, and takes a `curve <n>` message for an exponential shape. Its curve number is the same one used by `[asr~]`, `[adsr~]` and `[envgen~]`. `(source: Part.04-Control/16-Lines/4.[smooth~].[smooth~].pd; 5.[envgen~].pd)`
- **`[envgen~]` list syntax is the reverse of Pd's line** — Segments are pairs of *duration, target* (Pd's line family uses target, time). An odd-length list uses its first number as the start value. A single float is treated as a gate. A duration of 0 jumps at once. `(source: Part.04-Control/16-Lines/5.[envgen~].pd)`
- **`[envgen~]` only runs when triggered** — Unlike the line family, sending the list does not start it; it needs a bang or a gate (the examples send `…, bang`). `(source: Part.04-Control/16-Lines/5.[envgen~].pd)`
- **`[envgen~]` curve options** — `curve <float>` is the `[smooth~]`-style exponential factor. `curve ^4` is a power curve, the same as an exponent of 4 in `[rescale~]` or `[glide~]`. `curve lag` is a one-pole filter like `[lag~]`. `sin` and `hann` shapes also exist. It can loop (`loop 1`). `(source: Part.04-Control/16-Lines/5.[envgen~].pd)`
- **`-legato` flag** — `[envgen~ -legato]` does not jump back to the start point when retriggered. `(source: Part.04-Control/16-Lines/9.Control.Example.pd)`
- **`[function]` is the breakpoint GUI** — It draws or displays the same list `[envgen~]` takes and can send it. Fed with a float from a `[line]` it reads out the curve at control rate. `(source: Part.04-Control/16-Lines/6.[function].pd)`
- **`[function~]` is a breakpoint table read by a signal** — It has the same syntax and curve options as `[envgen~]` and is read by a 0–1 signal: a `[phasor~]` to loop it, or an `[envgen~]` ramp `0 <ms> 1` for one pass. `(source: Part.04-Control/16-Lines/7.[function~].[function].pd)`

### 17 — Envelopes

- **`[decay~]`: one-stage exponential envelope** — Starts at full level on a trigger and decays to 0; the argument is the time in ms. Triggered by bangs, floats or signal impulses, and the trigger value sets the peak. The tutorial says it is cloned from SuperCollider. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/1.Decay/1.[decay~].pd)`
- **Decay from any up/down smoother** — Set the upward time to 0 and the downward time to the decay: `[lag2~ 0 2000]` fed with impulses is said to be basically the same one-pole filter as `[decay~]`. `[autofade2~ sin 0 1000]`, `[glide2~ -exp 4 0 1000]`, `[smooth2~ -curve 1 0 1000]` and `[slew2~ -1 1]` give other decay shapes. The slew versions are linear. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/1.Decay/1.[decay~].pd; 4.other.objects.pd)`
- **Damped oscillator = oscillator × decay** — A sine or cosine multiplied by `[decay~]` imitates ELSE's `[damp.osc~ 440 2000]`. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/1.Decay/1.[decay~].pd)`
- **Clicks matter less on noise** — The tutorial notes that a hard-start envelope on a noisy or percussive source needs little care about clicks. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/1.Decay/1.[decay~].pd)`
- **`[adsr~]` and `[asr~]` argument order and input** — `[adsr~ A D S R]` with times in ms and sustain as a ratio of the gate value; `[asr~ A R]`. They take a signal gate, or a float scaled as MIDI velocity, and also bangs or impulses for a one-shot. The fourth inlet of `[adsr~]` sets decay. A right outlet reports status (when the envelope is done). `(source: Part.04-Control/17-Envelopes/2.Classic.Types/03.ASR/6.[asr~].[adsr~].pd; 1.Decay/3.[asr~].[adsr~].pd)`
- **Their default curve is exponential, factor 1** — Same curve as `[smooth~]`. `-lin` makes it linear (curve 0) and `-lag` uses a one-pole filter like `[lag~]`. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/04.ADSR/1.ADSR.pd; 2.[vline~].[slop~].pd)`
- **Reduced forms of `[adsr~]`** — Decay only: `[adsr~ 0 2000 0 0]` or `[asr~ 0 2000]`. Attack/release: `[adsr~ 50 450 0 0]` or `[asr~ 50 450]`. ASR: decay 0 and sustain 1. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/1.Decay/3.[asr~].[adsr~].pd; 2.AR.pd; 03.ASR/6.[asr~].[adsr~].pd)`
- **Retrigger inlet** — While `[adsr~]` or a gated `[envgen~]` is sustaining, an impulse in the second (right) inlet restarts the envelope without closing the gate. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/04.ADSR/1.ADSR.pd; 5.AHDSR.pd)`
- **Fixed-length note from an impulse** — `[timed.gate~ 500]` in front of `[adsr~]` turns a bang or impulse into a gate of known length, giving an ADSR with a fixed sustain time. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/04.ADSR/1.ADSR.pd)`
- **Sustain point in `[envgen~]`** — `-suspoint <n>` marks the breakpoint where a gated envelope waits until the gate closes. Examples: `[envgen~ -suspoint 1 -curve 1 150 1 750 0]` (ASR) and `[envgen~ -curve 1 -suspoint 2 50 1 50 0.5 200 0]` (ADSR). Without a sustain point, a fixed sustain is made by repeating the same target (`50 1 450 1 500 0`). `(source: Part.04-Control/17-Envelopes/2.Classic.Types/03.ASR/2.gate.pd; 04.ADSR/1.ADSR.pd; 03.ASR/1.[envgen~].[vline~].pd)`
- **AHDSR and DAHDSR need `[envgen~]`** — Hold is one more segment at the peak value. Delay is a first segment that stays at 0 (`0 250 0 …`). For a real gate, put `[gatedelay~ 250]` or `[trig.delay~ 250]` before the envelope instead. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/5.AHDSR.pd; 6.DAHDSR.pd)`
- **A pulse through a smoother is an envelope** — `[pulse~ 4]` (125 ms on, 125 ms off) into `[lag~ 125]` gives attack/release; a shorter lag time leaves a flat top, so it becomes ASR. `[glide~]`, `[lag2~]`, `[glide2~]` work the same way. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/03.ASR/4.[pulse~].pd)`
- **Trap: a slew limiter fixes speed, not time** — With `[slew~]`, start with a speed of twice the pulse frequency for an AR shape; higher gives ASR. But if the gate level is not 1 the shape changes: at 4 Hz, a gate of 0.5 with speed 8 gives the same shape as a gate of 1 with speed 16. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/03.ASR/4.[pulse~].pd)`
- **Vanilla exponential envelopes with `[slop~]`** — For a gated ASR, feed the gate to `[slop~]` and set its two rates from the attack and release times with `1000/ms`. For ADSR, work out the sustain level from the gate value and use different downward rates for decay and release. This is offered for people who want no externals. `(source: Part.04-Control/17-Envelopes/2.Classic.Types/03.ASR/5.[vline~].[slop~].pd; 04.ADSR/2.[vline~].[slop~].pd)`
- **Custom shapes** — `[envgen~]` handles shapes such as a second attack before the release (`-suspoint 2 50 1 50 0.5 200 1 100 0`), and `[function]` can draw the breakpoints for it. `(source: Part.04-Control/17-Envelopes/3.Custom.pd)`
- **Envelope tables: hann and half-sine** — A hann window is an inverted cosine scaled to 0–1; the "sine" window is the first half of a sine cycle. Both are also the shapes in `[fader~]`. The vanilla way records an oscillator into a table sized from the wanted ms. `[tabgen]` makes them in one message (`hanning`, `sin 0.5`) and can also apply a window to data already in an array. `(source: Part.04-Control/17-Envelopes/4.Tables/1.Tables.[tabgen].pd)`
- **Hann with `cosinesum`** — The array message `cosinesum 1024 0.5 -0.5` builds a hann table: a DC term of 0.5 plus a first cosine partial of -0.5. The size must be a power of two. `(source: Part.04-Control/17-Envelopes/4.Tables/2.[tabread4~].pd)`
- **Guard points when reading with `[tabread4~]`** — `cosinesum` adds extra guard points for interpolation. To read only the real data of a 1024-point table, ramp the index from 1 to 1025 (the patch sends `1 <ms> 1025` to `[envgen~]`). One table then serves any duration. `(source: Part.04-Control/17-Envelopes/4.Tables/2.[tabread4~].pd)`
- **`[tabreader~]` avoids the index maths** — Its index input is 0–1 by default, it needs no guard points (and `[tabgen]` writes none), and it treats phase as circular, so 1 equals 0, which suits looping. Default interpolation is spline; the lagrange type used by `[tabread4~]` is an option. A control `[tabreader]` exists. `(source: Part.04-Control/17-Envelopes/4.Tables/3.[tabreader~].pd)`
- **Gaussian envelope** — With input fixed at -1..1, sigma must be under 0.25 for the curve to reach near zero at the ends. Or fix sigma at √0.5, which reduces the formula to `exp(-x²)`, and change the input range to set the width; the tutorial says ELSE's `[gaussian~]` works this way. `[tabgen]` also makes gaussian tables (`gauss <sigma>`). `(source: Part.04-Control/17-Envelopes/4.Tables/4.gaussian.pd)`
- **`[envelope~]`: ready-made shapes read by a 0–1 signal** — Shapes named: hann, sin, triangular, variable saw, gaussian, trapezoid. `[function~ -curve hann 0 1 1 1 0]` and `[envgen~ -curve sin 0 250 1 250 0]` give the same results. `(source: Part.04-Control/17-Envelopes/4.Tables/6.[envelope~].[envgen~].[function~].pd)`
- **Triangle, trapezoid and skewed saw as `[function]` lists** — With a total length of 1: `0 0.5 1 0.5 0` (triangle), `0 0.25 1 0.5 1 0.25 0` (trapezoid), `0 0.8 1 0.2 0` (variable saw). `(source: Part.04-Control/17-Envelopes/4.Tables/5.[function~].[function].pd)`
- **Looped envelope = LFO = grain window** — Reading an envelope table with a `[phasor~]` instead of a one-shot ramp gives amplitude modulation or rhythmic patterns, and the tutorial calls this the basis of the granular techniques it covers later. Control-rate form: `[phasor]` into `[function]`. `(source: Part.04-Control/17-Envelopes/4.Tables/7.Loop.pd)`
- **Oscillators used directly as envelopes** — `[vsaw~ 2 0.5]` rescaled to 0–1 is a looping attack/release; `[pulse~ 2]` into `[glide~ 150]` gives ramps with pulse width as the duty; `[gaussian~ 2]` is another option. `(source: Part.04-Control/17-Envelopes/4.Tables/8.LFO.pd)`
- **Envelopes are just lines** — The chapter closes by driving `[rotate~]`'s rotation with `[adsr~ -lin 1500 0 1 1000]`, to make the point that an envelope can control anything. `(source: Part.04-Control/17-Envelopes/5.Control.Example.pd)`

### 18 — MIDI, CV, OSC, Network

#### MIDI

- **Pd treats note-off as velocity 0** — `[notein]` turns a real Note Off, with any release velocity, into a note with velocity 0. `[makenote]` accepts any float as pitch, not only 0–127. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/1.MIDI.note.pd; 7.Anatomy.of.MIDI.Messages.pd)`
- **Getting release velocity** — ELSE's `[note.in -rel]` outputs real Note Off messages with their release velocity, and `-both` puts on and off velocities in one list. The example maps release velocity to an envelope's release time (`[rescale 10 1000]`), and treats a velocity-0 Note On as a Note Off with release velocity 0. The tutorial notes controllers rarely send it but MIDI files often contain it. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/7.Anatomy.of.MIDI.Messages.pd)`
- **`[stripnote]` when the envelope needs no gate** — Dropping note-offs is right for trigger-only envelopes, such as `[asr~]` used as a one-shot. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/2.[stripnote].pd)`
- **`[makenote2]`** — An ELSE version of `[makenote]` that can take the duration in beats. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/1.MIDI.note.pd)`
- **Mono synth note handling** — `[mono]` / `[mono~]` remember the held notes. A new note always plays; releasing it returns to the last note still held. `[mono~ 50]` has glide built in but then needs an extra outlet to retrigger envelopes; with `[mono]` the example adds `[glide~]` by hand. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/3.Monophony.Polyphony/1.Monophonic.pd)`
- **Poly voice allocation** — `[voices 4]` outputs lists of *voice number, pitch, velocity*. That matches what Pd's `[clone]` expects (first number picks the copy), so it connects straight in; `[route 0 1 2 3]` is the alternative. A second argument of 1 (`[voices 4 1]`) turns on voice stealing. It is said to be inspired by vanilla `[poly]` with more features. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/3.Monophony.Polyphony/2.Polyphonic.pd)`
- **`[synth~]` wraps the whole thing** — It combines `[clone]`, `[voices]` and `[mono]`: it loads a voice abstraction and does mono or poly handling. The abstraction must follow a set template, and with no argument it loads a built-in example. The voice abstraction shown routes `noteon noteoff pressure slide`. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/3.Monophony.Polyphony/3.[synth~].pd; voice-abs.pd)`
- **Polyphony over a multichannel cord** — `[voices~ 4]` puts each voice on its own channel of one multichannel connection, so a single `[sine~ -midi]` and `[adsr~]` process all voices and no `[clone]` is needed. The stated cost is somewhat more CPU. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/3.Monophony.Polyphony/4.[voices~].pd)`
- **`-midi` flag on oscillators** — Oscillators such as `[bl.saw~ -midi]`, `[bl.tri~ -midi]`, `[sine~ -midi]` take pitch as MIDI note numbers, so no `mtof` is needed. (Seen in the boxes; `[plaits~]`'s text confirms the idea for that object.) `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/3.Monophony.Polyphony/1.Monophonic.pd; 2.CV/5.[plaits~].pd)`
- **Keyboard split** — `[spread 65 72 77]` sends notes to different outlets by pitch range, like a row of `[moses]` objects. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/4.Keyboard-split.pd; 20-Stochastic/2.Weighted.random.[chance].pd)`
- **Sustain pedal logic** — While the pedal is down, note-offs are held back and sent when it lifts. Vanilla recipe: with the pedal on, pass notes through `[stripnote]` into `[bag]`, then `flush` the bag when the pedal goes off. ELSE's `[suspedal]` does this with more features. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/5.Sustain.pd)`
- **ELSE MIDI objects work on raw bytes** — `[note.in]`, `[ctl.in]`, `[bend.in]`, `[pgm.in]`, `[touch.in]`, `[ptouch.in]`, `[sysrt.in]` and the `.out` forms can take or give raw MIDI bytes, so they plug into `[midi]` (the MIDI file player) and can change channel. `[midi.in]` / `[midi.out]` give "cooked" data instead. `[midi.learn]` helps bind a controller. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/6.MIDI.objects.pd)`
- **Numbering differences to watch** — Vanilla `[pgmin]` outputs 1–128; ELSE `[pgm.in]` outputs 0–127. `[bend.in]` outputs -1 to 1, or 0–16383 with `-raw` (the tutorial gives 8191 as the midpoint). `[ptouch.in]` outputs pitch first, the opposite order from vanilla's poly-touch object. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/7.Anatomy.of.MIDI.Messages.pd)`
- **Status byte table** — 128–143 note off, 144–159 note on, 160–175 poly aftertouch, 176–191 control change, 192–207 program change, 208–223 channel aftertouch, 224–239 pitch bend; each block is channels 1–16. Program change and channel aftertouch have one data byte, the rest two. Bend value = first byte + 128 × second byte. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/7.Anatomy.of.MIDI.Messages.pd)`
- **System bytes** — 240 sysex start, 241 time code, 242 song position, 243 song select, 246 tune request, 247 sysex end, 248 clock, 250 start, 251 continue, 252 stop, 254 active sensing, 255 reset. `[sysexin]` and `[midirealtimein]` are the only vanilla objects that receive these. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/7.Anatomy.of.MIDI.Messages.pd)`
- **Errors in the tutorial text (do not copy)** — One sentence gives the 14-bit bend range as "0 to 1383" where others say 16383. The note-off subpatch says "129 is channel 1", while the main text says 128 is channel 1. One line says 127 controllers per channel although the range given is 0–127. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/7.Anatomy.of.MIDI.Messages.pd)`

#### CV

- **Three kinds of CV** — Trigger (an impulse), gate (a pulse) and continuous CV. In Pd these are `[imp~]`, `[pulse~]` and any signal. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/2.CV/1.Introduction.pd)`
- **Volt per octave, mapped to Pd's -1..1** — The one fixed rule is 1 V = one octave; the absolute pitch at 0 V is tuned per module. The tutorial sets 0 V = middle C (MIDI 60) and treats -1..1 as -5 V..+5 V, so the range is MIDI 0–120. Signal to MIDI: `× 5 × 12 + 60` (that is, `× 60 + 60`). `(source: Part.04-Control/18-MIDI-CV-OSC-Net/2.CV/2.V-per-oct.pd)`
- **MIDI to CV** — `(pitch − 60) / 60` gives the -1..1 signal for a ±5 V range; `(pitch − 60) / 12` gives true volts per octave. Cents convert to V/oct by dividing by 1200. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/2.CV/4.MIDI-CV.pd; 2.V-per-oct.pd)`
- **Voltage facts** — Common ranges are ±5 V bipolar and 0–5, 0–8, 0–10 V unipolar; signals stay within ±10 V. Triggers and gates usually jump from 0 to about +5 V. A 10 V span is 10 octaves (20 Hz up to 20.48 kHz); MIDI covers 10 octaves and a fifth. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/2.CV/2.V-per-oct.pd)`
- **Hardware needed** — Sending or receiving CV needs a DC-coupled audio interface or a dedicated module, and calibration in both directions. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/2.CV/4.MIDI-CV.pd; 2.V-per-oct.pd)`
- **CV-to-MIDI converter recipe** — Scale the CV by an attenuator, add 1 first if it should be unipolar, multiply by 60, add the base note, take the integer. Use the gate's edges (`[status~]` → `[trig2bang~]`) to sample pitch and velocity with `[snapshot~]` and send note on and note off. The CV could come from `[adc~]`. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/2.CV/3.CV-MIDI.pd)`
- **`[plaits~]` pitch input modes** — ELSE's port of the Eurorack module takes Hz by default, MIDI with `-midi`, or a -1..1 "CV" with `-cv` where 0 is middle C. The text says it is the only ELSE object with this kind of CV pitch input. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/2.CV/5.[plaits~].pd)`
- **MERDA modules: CV without V/oct** — MERDA is ELSE's set of ready-made modules (`[vco.m~]`, `[vcf.m~]`, `[vca.m~]`, `[adsr.m~]`, `[lfo.m~]`, `[seq8.m~]`, `[plaits.m~]`, `[presets.m]`). Pitch input is MIDI. Signal inlets are CV inputs in -1..1 that add to the knob value, scaled by an "attenuverter" knob that inverts when turned left of centre. The ADSR module outputs 0–1. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/2.CV/6.MERDA.pd; 5.[plaits~].pd)`

#### OSC and network

- **Vanilla OSC chain** — Send: `[oscformat <address parts>]` → `[netsend -u -b]` (UDP, binary) after a `connect localhost 12001` message. Receive: `[netreceive -u -b 12001]` → `[oscparse]` → `[list trim]` → `[route …]`, one `[route]` per address level. `[oscformat -f ff note]` forces the type tags (two floats), which some receivers need. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/3.OSC/1.Vanilla.pd)`
- **Vanilla OSC limits** — No bundles and no time stamps. The tutorial points to the `mrpeach` library (`[packOSC]`, `[routeOSC]`) for a fuller implementation. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/3.OSC/1.Vanilla.pd)`
- **Multicast address in the example** — One example connects to `238.200.200.200` port 3005 and the receiver uses `listen 3005 238.200.200.200`. The text only calls it "using the IP address"; it does not explain that address. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/3.OSC/1.Vanilla.pd)`
- **ELSE OSC objects** — `[osc.send <port>]` (address optional) and `[osc.receive <port>]` wrap the net objects and take messages written with real slash addresses (`/slider/2d $1 $2`). `[osc.route /slider]` strips one address level. The tutorial says these are still simpler than mrpeach. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/3.OSC/2.ELSE.pd)`
- **Talking to Max** — The tutorial says Max's built-in `udpsend` and `udpreceive` behave much like `[osc.send]` and `[osc.receive]`: give host and port. It also ships SuperCollider and Processing examples in the same folder. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/3.OSC/3.Software.Connection.pd)`
- **FUDI** — Pd's own message protocol, used internally between its GUI and DSP processes. `[fudiformat -u]` and `[fudiparse]` with the UDP net objects send plain Pd messages between Pd instances, including between plugdata and vanilla. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/4.Network/1.FUDI.pd)`
- **`[pdlink]` / `[pdlink~]`** — Link Pd instances, versions or forks over the network using only a shared name (`[pdlink control]`, `[pdlink~ sig]`). `[pdlink~]` carries audio. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/4.Network/2.[pdlink].[pdlink~].pd)`

### 19 — Sequencing

- **`[midi]` plays and records MIDI files as raw bytes** — `[midi -loop bach.mid]` outputs raw MIDI, so `[note.in]` after it extracts the notes. It also records, and it imports and exports text files in the `[text sequence]` format, so a MIDI file can be edited as text and saved back. `(source: Part.04-Control/19-Sequencing/1.MIDI.Files.pd; 6.[qlist].[text].[score].[score2]/6.[text]-&-[midi].pd)`
- **`[rec]` and `[store]`** — `[rec 3]` records any messages on several tracks with timing and plays them back; its saved text starts each line with a wait time, roughly like `[text sequence]`, but tracks are stored one after another. `[store]` keeps messages in order and outputs the next one on each bang. `(source: Part.04-Control/19-Sequencing/2.[rec].[store].pd)`
- **Basic step sequencer and its shortcut** — Clock → counter → modulo → `get $1` into `[list store]`. ELSE's `[count 8]` replaces the counter and modulo. Sending stop also resets the counter to 0. `(source: Part.04-Control/19-Sequencing/3.[list].[array].[text].text/1.[list store].pd)`
- **Array sequencer in one `[expr]`** — `[expr i = (i + 1) % 16; mtof(rint(sequencer[i] + base))]` advances an index held in a `[value]`, reads the array by name, adds a transposition variable, rounds to a semitone and converts to Hz. `(source: Part.04-Control/19-Sequencing/3.[list].[array].[text].text/2.Array-Sequencer.pd)`
- **Rests as non-numbers** — A sequence stored in `[text]` can hold symbols; a `.` passes nothing through `[route float]`, so it acts as a rest. `(source: Part.04-Control/19-Sequencing/3.[list].[array].[text].text/3.[text].pd)`
- **`[sequencer]` vs `[list.seq]` vs `[sequencer~]`** — `[sequencer]` (abstraction on `[text]`) has its own syntax: `-` is a rest or joins items sent together as a chord (the tutorial states both uses without showing the exact rule), a `|` appears in the example lists (its meaning is not explained in this part; it looks like a bar line), and items can be note names (`C#4`, `Eb4`) or fractions. `[list.seq]` is simpler and does not loop unless given `-loop`. `[sequencer~]` is compiled, floats only, and steps on impulses. `(source: Part.04-Control/19-Sequencing/3.[list].[array].[text].text/4.[list.seq].[sequencer].[sequencer~].pd; 5.Rhythmic/7.[pattern].[sequencer].pd)`
- **Step mutes** — Keep a second array of 0/1 per step. Read it with the same index and let `[sel 1]` bang the pitch through only when the step is on. `(source: Part.04-Control/19-Sequencing/3.[list].[array].[text].text/5.Toggle.array.pd)`
- **Signal-rate step sequencer recipe** — `[tempo~ -mul 4 60]` → `[pulsecount~ 16]` → `[-~ 1]` for a 0-based index → `[tabread~]` on the pitch array and the mute array. `[changed~]` on the index gives an impulse per step; multiply it by the mute value to get a trigger only on active steps. Use that trigger on `[sh~]` so the pitch only updates on active steps. `(source: Part.04-Control/19-Sequencing/3.[list].[array].[text].text/6.Signal.rate.array.pd)`
- **Drum grid** — `[drum.seq]` is a clickable grid of tracks × steps. Send it a step number; it outputs *track, value* pairs, so `[route 1 2]` then `[sel 1]` fire each sound. An `import` message loads patterns with `||` between tracks. The hand-made version is one 0/1 table per track. `(source: Part.04-Control/19-Sequencing/5.Rhythmic/2.[drum.seq].pd; 1.Drum.sequencer.pd)`
- **Euclidean rhythms** — `[euclid 16 5 0]` takes steps, hits and rotation; send it a step number and it answers hit or rest. The example loops over all steps to fill a `[drum.seq]` track. `(source: Part.04-Control/19-Sequencing/5.Rhythmic/3.[euclid].pd)`
- **Impulse sequencers** — `[impseq~ 1 0.5 0.25 0 …]` outputs the next value as an impulse on each bang or signal trigger; 0 is a rest, and the values act as accents (the example drives `[asr~]` with them). `[phaseseq~ 0.2 0.3 0.5 0.7 0.9]` is driven by a phase ramp and fires an impulse of 1 as the phase passes each listed point, giving uneven rhythms inside one cycle. `(source: Part.04-Control/19-Sequencing/5.Rhythmic/4.[impseq~].[phaseseq~].pd)`
- **Rhythm as a list of durations** — Feed each duration to `[delay]`, whose output asks for the next one. Durations can be fractions of a whole note: convert with `[frac2dec]`, `× 4`, then multiply by the beat length from `[bpm]`. `(source: Part.04-Control/19-Sequencing/5.Rhythmic/5.Duration.sequence.pd)`
- **`[pattern]`: rhythm written as fractions** — Durations are fractions of a whole note (1/4, 1/8). Tuplets use the matching fraction: 1/6 is a quarter-note triplet, 1/15 a quintuplet inside a triplet. Negative values are rests. A `|` separates groups in the examples and the object reports a bar number, so it appears to be a bar line; the text does not say so outright. The right outlet reports `stop`, `start`, `bar`, `dur`. With `-i` it outputs step indexes to read pitches from a separate `[sequencer]`, so rhythm and pitch lists are independent. `(source: Part.04-Control/19-Sequencing/5.Rhythmic/6.[pattern].pd; 7.[pattern].[sequencer].pd)`
- **`[qlist]` format, and it is called obsolete** — Each line is *delta time in ms, receive name, message* (`500 note 60;`). A last line with only a time (`3000;`) is a pause before the "done" bang, which the example uses to loop. The tutorial says to use `[text sequence]` instead. `(source: Part.04-Control/19-Sequencing/6.[qlist].[text].[score].[score2]/1.[qlist].pd; seq.txt)`
- **`[text sequence]` flags** — `-g` sends each line to the receive name it starts with (qlist style). `-w 1` says the first number of each line is a wait time. `-t 60 permin` sets the tempo so waits are counted in beats. `[text define -k]` saves the text in the patch. `line 0, auto` rewinds and plays. `(source: Part.04-Control/19-Sequencing/6.[qlist].[text].[score].[score2]/2.[text]-1.pd; 3.[text]-2.pd)`
- **Local names inside a text score** — Write `$1` in the lines of the text and send `args $0` to `[text sequence]`; each `$1` then becomes the patch's unique number, so the score can use patch-local send names. The tutorial says this was much harder with `[qlist]`. `(source: Part.04-Control/19-Sequencing/6.[qlist].[text].[score].[score2]/2.[text]-1.pd)`
- **Wait-time rules** — The wait is the time *before* that line is sent. Lines with wait 0 sound together with the line before, which is how chords are written. A line with only a wait outputs a bang (an empty list), useful as a final rest before looping. `(source: Part.04-Control/19-Sequencing/6.[qlist].[text].[score].[score2]/3.[text]-2.pd; 4.[text]-3.pd)`
- **Polyphony without a voice allocator** — Prepend a cycling `[count 7]` to each line from `[text sequence]` and send it to `[clone 8 …]`: plain round-robin. Each line carries pitch, amplitude, attack+sustain ms and release ms, and the voice builds an `[envgen~]` message from them (`30 $1 $2 $1 $3 0`). `(source: Part.04-Control/19-Sequencing/6.[qlist].[text].[score].[score2]/4.[text]-3.pd; voice1.pd)`
- **Make durations follow tempo** — Store note lengths in beats and convert to ms from the current tempo with `[bpm]` before `[makenote]`, then use `[voices]`. Otherwise notes keep the same length at every tempo. The example halves each length for a staccato feel. `(source: Part.04-Control/19-Sequencing/6.[qlist].[text].[score].[score2]/5.[text]-4.pd)`
- **`[score]` format** — Built on `[text]`. Lines give the *beat position inside the bar*, not a wait: `1` is the start of beat 1, `2.75` is beat 2 plus three sixteenths. `|;` starts a bar, `timesig 2/4;` and `tempo 80;` are lines in the file, and the tempo comes out the middle outlet. Commas split simultaneous events, each with its own length (`1 72 1 0.5, 48 0.5 0.5;`). `(source: Part.04-Control/19-Sequencing/6.[qlist].[text].[score].[score2]/7.[score].pd; fantasia.txt)`
- **`[score2]` format** — Uses `[pattern]`-style durations with note names: `1/4 F2, C4;` and `-1/8;` for a rest, with `|;`, `timesig`, `tempo` lines. It replaces `[pattern]` plus `[sequencer]` and is easier to write, but suits monophonic lines or chords; `[score]` is better when simultaneous notes need different lengths. Keeping `[pattern]` and `[sequencer]` separate still helps when mixing rhythm and pitch phrases at random. `(source: Part.04-Control/19-Sequencing/6.[qlist].[text].[score].[score2]/8.[score2].pd; score2.txt)`
- **Presets as sequence steps** — `[presets]` (on `[text]`) takes receive names as arguments and stores the state of those objects; stepping through preset numbers with a counter or random values makes a sequence of whole states. Its file keeps one preset per line with `||` between objects. `(source: Part.04-Control/19-Sequencing/7.[presets].pd; p1.txt)`

### 20 — Stochastic

- **No-repeat random (tone rows)** — `[rand.u 12]` outputs 0–11 in random order with no repeats until all are used, then bangs its right outlet. A `size` message changes the count. `(source: Part.04-Control/20-Stochastic/1.Random.pd)`
- **Weighted choice** — Vanilla: `[random 100]` into stacked `[moses]` objects. ELSE: `[spread 50 75]` for many thresholds at once, or `[chance 50 25 25]`, where each outlet fires with the weight of its argument. `(source: Part.04-Control/20-Stochastic/2.Weighted.random.[chance].pd)`
- **Weights are counts, not percents** — `[chance]` and `[chance~]` arguments need not add to 100. `30 60 20` means 30, 60 and 20 chances out of 110. `(source: Part.04-Control/20-Stochastic/3.[chance~].pd)`
- **`[chance~]` routes impulses** — Each incoming impulse goes to one outlet chosen by weight and keeps its value, so random impulse levels from `[randpulse~]` pass through as accents. `[chance~ 80]` alone leaves a 20 % chance of a rest. `(source: Part.04-Control/20-Stochastic/3.[chance~].pd)`
- **Learn a distribution from playing** — Count each played pitch into a 128-point array (read, add 1, write). `[array random]` then outputs an index with probability set by those counts. `(source: Part.04-Control/20-Stochastic/4.[array random].pd)`
- **`[rand.hist]`, `[histogram]`, `[rand.list]`** — `[rand.hist 4 1 3 2 1]` picks indexes 0–4 with those weights. `[histogram]` builds the counts and can `export` them to it; the example fills it from a MIDI file so notes come out as often as in the tune. With `-u` it plays through the whole weighted set without replacement, then bangs. `[rand.list]` picks uniformly from a list; repeat an item to weight it. `(source: Part.04-Control/20-Stochastic/5.[histogram].[rand.hist].pd)`
- **Random from a drawn probability curve** — `[rand.dist <array> lo hi]` treats an array as a probability density (positive floats allowed) and rescales the result (default 0–127). A float input returns the quantile, since it is built on `[array quantile]`, so any random source, such as `[rampnoise]`, can drive it. The example uses a gaussian table from `[tabgen]`. `(source: Part.04-Control/20-Stochastic/6.[rand.dist].pd)`
- **`[markov]` learns from input** — Feed it notes; it counts each transition. `create` builds the chain, `clear` forgets, and bangs then step through it. Example given: if 60 was followed by 67 seven times and by 65 three times, 67 follows 60 with 70 % chance. `(source: Part.04-Control/20-Stochastic/7.Markov.Chain/1.[markov].pd)`
- **Markov order** — Order 2 means the next note depends on the last two. Higher order sounds closer to the source; for the "Happy Birthday" file, order 5 plays back the original tune. The chain must be rebuilt after the order changes. `(source: Part.04-Control/20-Stochastic/7.Markov.Chain/2.MIDI-File.pd)`
- **Hand-made Markov chain in `[text]`** — One line per pitch: the pitch, then every note that ever followed it, repeats included. To step, find the line for the current pitch, take its length, and pick a random item; repeats supply the weighting. The tutorial notes `[markov]` itself uses a different algorithm. `(source: Part.04-Control/20-Stochastic/7.Markov.Chain/2.MIDI-File.pd)`
- **Random walks** — `[drunkard]` / `[drunkard~]` step a random amount within a set range from the last value. `[brown]` / `[brown~]` differ in that up and down are equally likely and values fold back at the bounds. `[brown~]` with a signal connected takes impulses to make each step; otherwise it is the brown-noise generator. `(source: Part.04-Control/20-Stochastic/8.Drunkard's.walk.pd; 9.[brown].[brown~].pd)`

### 21 — Basic Signal Analysis

- **Envelope followers** — Vanilla `[env~]` and ELSE `[rms~]` both report RMS level; they differ only in output scale (`-lin` gives linear). `[mov.rms~ -lin 4096]` is a moving-window version at signal rate. (The text names `[mov.avg~]` but the patch box is `[mov.rms~]`.) `(source: Part.04-Control/21-Basic-Signal-Analysis/1.Envelope.following.pd)`
- **`[sigmund~]` for pitch** — Left outlet is pitch as MIDI, right outlet is level on the same scale as `[env~]`. Window and hop defaults match `[env~]`. The example gates low levels with `[moses]` and converts level with `[- 100]` → `[db2lin]` to drive an oscillator's amplitude. `(source: Part.04-Control/21-Basic-Signal-Analysis/2.Pitch.[sigmund~].pd)`
- **Onsets with `[sigmund~ … notes]`** — The `notes` output reports a pitch only when a new attack is found. It needs a clean monophonic pitched input and is not fully reliable. Its output is late by the analysis window; the example delays the dry signal with `[ffdelay~ -samps 256]` to compare. Flags shown: `-npts 2048 -hop 256`. `(source: Part.04-Control/21-Basic-Signal-Analysis/3.Onset.[sigmund~].pd)`
- **`[bonk~]` and `[beat~]`** — `[bonk~]` is recommended for attack detection on percussive material (`minvel 50` sets a floor). ELSE's `[beat~]`, built on the aubio library, reports the tempo of a rhythmic input in BPM. `(source: Part.04-Control/21-Basic-Signal-Analysis/4.Onset.[bonk~] .pd; 5.[beat~].pd)`

## Part 05 — Synthesis (Basic)

### 22 — Wavetable

- **`osc~` is a table lookup, not a cosine calculation** — Vanilla `osc~` and `cos~` share one stored 512-point cosine table. ELSE's `sine~` and `sin~` use a 16384-point sine table, so they have more resolution. `(source: Part.05-Synthesis(Basic)/22-Wavetable/1.Wavetable.pd)`
- **Guard points in Vanilla tables** — A table made with `sinesum` gets 3 extra points: one at the start and two at the end. So a `phasor~` into `tabread4~` must be multiplied by the table size and then have 1 added. `(source: Part.05-Synthesis(Basic)/22-Wavetable/1.Wavetable.pd)`
- **ELSE avoids guard points** — `tabgen` fills a table with a waveform (`tabgen 16384 <table> sin`) and `tabreader~` reads it with no guard points to manage. `(source: Part.05-Synthesis(Basic)/22-Wavetable/1.Wavetable.pd)`
- **`tabreader~` input convention** — It takes a 0–1 phase straight from `phasor~`. With the `-index` flag it takes a point index instead. For oscillator use it must be in loop mode (`-loop`) either way. `(source: Part.05-Synthesis(Basic)/22-Wavetable/1.Wavetable.pd)`
- **Wavetable scanning recipe** — One 4096-point table holds 4 frames of 1024 points. A scan value 0–3 is split with `trunc~` (which frame) and `wrap~` (how far to the next). Two readers get index = phasor × 1024 + frame × 1024, one for frame n and one for n+1, and `xfade~ -lin` crossfades them by the fractional part. `(source: Part.05-Synthesis(Basic)/22-Wavetable/2.Wavetable.scan.pd)`
- **Why Vanilla cannot do this cleanly** — Each slice would need its own guard points inside the table. The author says a full Vanilla version is not sane or elegant. `(source: Part.05-Synthesis(Basic)/22-Wavetable/2.Wavetable.scan.pd)`
- **`wavetable~` (alias `wt~`) scans frames itself** — The `-n <frames>` flag says how many frames the table holds, and the rightmost inlet scans them with a 0–1 value. With 4 frames, 0 is frame one and moving to 0.25 crossfades into frame two. `(source: Part.05-Synthesis(Basic)/22-Wavetable/2.Wavetable.scan.pd)`
- **Vector synthesis** — Four sources are mixed by a 2D linear crossfade: X fades inside pair 1–2 and pair 3–4, Y fades between the two pairs. The text credits the 1986 Prophet VS. A 2D slider or two `rampnoise~` objects drive it. `(source: Part.05-Synthesis(Basic)/22-Wavetable/3.Vector.Synthesis.pd)`
- **2D wavetable scanning** — A 16384-sample file is treated as an 8 × 8 grid: 8 rows of 2048 points, each row 8 frames of 256 points. The patch does two horizontal crossfades (current row and next row) and one vertical crossfade between them. `(source: Part.05-Synthesis(Basic)/22-Wavetable/4.2D.scanning.[wt2d~].pd)`
- **`wt2d~` does 2D scanning in one object** — `wt2d~ -n 8 8 <table>` sets columns and rows. It is like `wavetable~` with one more inlet for the vertical crossfade. The example table is a Plaits wavetable; the text says ELSE also has a `plaits~` port (engine mode 5 uses such tables). `(source: Part.05-Synthesis(Basic)/22-Wavetable/4.2D.scanning.[wt2d~].pd)`

### 23 — Additive Synthesis

- **Why a bank beats a summed table** — A `sinesum` table can only hold harmonic partials and cannot set their phases. Separate oscillators allow detuned ratios, own amplitudes and own phases. The text notes that changing a partial's phase changes the waveform but not what is heard. `(source: Part.05-Synthesis(Basic)/23-Additive.Synthesis/1.Example1.pd)`
- **Gain compensation by voice count** — Sixteen oscillators are summed and divided by 16. The same patch is then rebuilt with `clone` loading an abstraction 16 times, each instance picking a random frequency on a bang. `(source: Part.05-Synthesis(Basic)/23-Additive.Synthesis/2.Example2.pd)`
- **Two detuned oscillators per partial** — Each partial is a pair of close oscillators, each with its own slow random pitch drift from `rampnoise~`. The partial ratios in the boxes are inharmonic (1, 1.9, 2.8, 4.1, 5.2, 5.9, 6.7). `(source: Part.05-Synthesis(Basic)/23-Additive.Synthesis/4.Example3.pd)`
- **Per-partial envelope and pan** — The next step gives each oscillator pair its own envelope, its own pan, and an attack delayed by a random time. `(source: Part.05-Synthesis(Basic)/23-Additive.Synthesis/5.Example4.pd)`
- **`oscbank~`** — A bank of `sine~` oscillators. It takes a frequency multiplier and `partial`, `amp` and `phase` lists. The partial list can be ratios of a fundamental, or direct frequencies with the multiplier left at its default of 1 (the multiplier then transposes). It can output one channel per oscillator. `(source: Part.05-Synthesis(Basic)/23-Additive.Synthesis/6.[oscbank~].pd)`
- **`sine~` is itself a bank** — It accepts a multichannel signal and makes one oscillator per channel, so each can be hard-synced, frequency-modulated and phase-modulated, which the other bank options cannot do. The text says all ELSE oscillators are multichannel-aware. The boxes use `sigs~ 200 300 400 500 600` and `rampnoise~ -ch 5 <rate>` as multichannel sources. `(source: Part.05-Synthesis(Basic)/23-Additive.Synthesis/7.[sine~].and.others.pd)`
- **Wave stacking** — Summing complex waveforms (three saws at one frequency with different phase and amplitude) instead of sines. Warning: shifting a saw's phase is not the same as inverting its polarity. A second example adds a saw an octave up, detuned by 0.5 Hz, to a square, using band-limited `bl.saw~` and `bl.square~`. `(source: Part.05-Synthesis(Basic)/23-Additive.Synthesis/8.Wave.stacking.pd)`

### 24 — Modulation Synthesis: AM / RM

- **AM versus RM is only the DC offset** — Classic AM uses a modulator shifted to 0–1. Ring modulation uses a modulator that swings −1 to 1, and a negative modulator flips the carrier's polarity. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/1.AM_RM/2.RM.pd)`
- **What each does to the spectrum** — AM keeps the carrier and adds one sideband above and one below, each at half the carrier's amplitude, spaced by the modulator frequency. RM removes the carrier and leaves stronger sidebands. Sliding the modulator's offset and amplitude moves between the two. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/1.AM_RM/3.DC_Offset.pd)`
- **`rm~` and the 0 Hz trap** — `rm~` ring-modulates with an internal `osc~`; frequency comes from the argument or the right inlet. It treats 0 Hz as bypass. The reason given: a stopped oscillator sits at whatever value its phase left it, usually not 1, so you would get an unwanted gain change. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/1.AM_RM/4.Sample.[rm~].[rm.m~].pd)`
- **AM or RM on a recording** — Sidebands appear around every partial of the input. AM keeps the original partials, so the sidebands clash with them; the text says AM is therefore mostly used slow, as tremolo. RM removes the originals and is the more interesting effect. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/1.AM_RM/4.Sample.[rm~].[rm.m~].pd)`
- **Complex modulators** — A richer modulator waveform adds more partials in AM and RM. The text says sine is usually enough, and FM/PM is the more efficient way to get complex spectra. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/1.AM_RM/5.Other.Oscillators.pd)`
- **Tremolo depth** — Depth 0–1 rescales the LFO so depth 0 leaves gain at 1 and depth 1 is full AM. `tremolo~` (box: `tremolo~ 5 0.75`, rate and depth) wraps this, and like `rm~` treats 0 Hz as bypass. Raising the rate into audio range turns it into plain AM. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/1.AM_RM/6.[tremolo~].pd)`

### 24 — Modulation Synthesis: FM and PM

- **Basic FM wiring** — Modulator oscillator × deviation, added to the carrier frequency, into an oscillator's frequency input. With carrier 400, deviation 100 and modulator 1 Hz the frequency swings 300–500 Hz. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/1.FM/1.Introduction.pd)`
- **"Index" is often really deviation** — The text warns that the modulator's amplitude in Hz is commonly called "modulation index", which is not accurate. The real index is deviation divided by modulator frequency (see classical FM below). `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/1.FM/1.Introduction.pd)`
- **Sidebands and harmonicity** — FM makes many sidebands spaced by the modulator frequency; more index, more partials. A simple carrier-to-modulator ratio gives a harmonic sound, otherwise inharmonic. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/1.FM/2.Basic.FM.pd)`
- **Band-limit the carrier, not the modulator** — In the mixed-waveform patch the modulators are ideal (non-band-limited) shapes, and only the oscillator receiving the modulated frequency is band-limited (`bl.tri~`, `bl.saw~`, `bl.square~`). `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/1.FM/3.Other.Oscillators.pd)`
- **Modulator as a ratio of the carrier** — Setting the modulator frequency as carrier × ratio leaves one pitch input and keeps the timbre the same across pitches. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/1.FM/4.Ratio.pd)`
- **Exponential FM** — Add the modulation to a MIDI pitch and convert with `mtof~`, so deviation is in semitones, not Hz. The modulation becomes asymmetric and sounds different. ELSE oscillators can take MIDI pitch directly (`sine~ -midi`). The ratio is set as a semitone offset (the example adds 7.05, about a fifth); `ratio2cents` divided by 100 gives that offset from a ratio. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/1.FM/5.Exponential.pd)`
- **Frequency and phase are the same signal in two forms** — `phasor~` turns frequency into phase; phase is the integral of frequency. So you can add two frequencies before one `phasor~`, or add the outputs of two `phasor~` objects, and get the same result. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/2.Frequency_x_Phase/1.Sum_Freq_Phase1.pd)`
- **Negative frequency and phase wrapping** — A negative frequency makes `phasor~` ramp downward, so 300 Hz plus −100 Hz gives 200 Hz. Summed phases run 0–2, but `cos~` and `cosine~` wrap their input by themselves, so no `wrap~` is needed. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/2.Frequency_x_Phase/2.Sum_Freq_Phase2.pd)`
- **ELSE oscillators have a phase inlet** — The right inlet of `cosine~` (and other ELSE oscillators) is a phase input. Feeding a `phasor~` there adds its frequency to the oscillator's own, so `phasor~ 440` into `cosine~ 0` is a 440 Hz oscillator. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/2.Frequency_x_Phase/3.[cosine~].pd)`
- **True PM structure** — The modulating oscillator goes straight into the phase input, not through a `phasor~`. In Vanilla: `phasor~` → add modulator × index → `cos~`. In ELSE: modulator into the phase inlet of `cosine~`. This is not equivalent to FM with the same numbers. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/3.PM/1.Introduction.pd)`
- **Things labelled FM are often PM** — The text names the DX7 as the known case: sold as FM, built as PM. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/3.PM/1.Introduction.pd)`
- **`pm~`** — A phase-modulation pair in one object. The comment gives the arguments as carrier, ratio, index (box: `pm~ 220 2.01 0.75`). `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/3.PM/1.Introduction.pd)`
- **PM index scale** — In PM the index is a phase deviation where 1 is a full cycle, so useful values are usually 0–1, far smaller than FM deviations. An index of 0.25 swings the phase between +0.25 and −0.25. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/3.PM/2.Basic.PM.pd)`
- **Enveloped index** — A PM voice with one `envgen~` on amplitude and another on the index; the ratio comes from cents through `cents2ratio` (705 cents in the example). `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/3.PM/3.Ratio.pd)`
- **Which waveform in FM equals which in PM** — Integrating the frequency signal gives the phase signal: square → triangle, sawtooth → parabola, triangle → parabolic wave (ELSE `parabolic~`), cosine → sine (a −90° shift). `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/4.FM_x_PM/1.Waveforms/5.Revision.pd; details in 1.Square_Tri.pd, 2.Saw_Parabolic.pd, 3.Triangular.Parabolas.pd, 4.Cosine-Sine.pd in the same folder)`
- **Converting a sine PM index to FM** — FM deviation = PM index × 2π × modulator frequency, and the FM modulator must be a cosine where the PM modulator is a sine. The key point: in PM the modulator frequency scales the effective deviation; in plain FM it does not. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/4.FM_x_PM/2.Examples/1.Cosine-Sine.pd)`
- **Conversion factors for other shapes** — Saw FM equals parabola PM (the patch squares the saw with `pow~ 2`), factor 4 × modulator frequency. Triangle FM equals `parabolic~` PM, factor 8 × modulator frequency, with a start phase of 0.75 on `parabolic~`. Square FM equals triangle PM, factor 4 × modulator frequency, with `tri~` at phase 0.75. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/4.FM_x_PM/2.Examples/2.Saw-Parabolic.pd, 3.Tri-Parabolic.pd, 4.Square-Tri.pd)`
- **Classical FM and the real index formula** — Peak deviation = index × modulator frequency; index = peak deviation ÷ modulator frequency. Building FM this way makes it track PM's behaviour (exact match would still need the 2π). ELSE `fm~` is built this way; box `fm~ 200 0.5 5` sits beside controls labelled carrier, ratio, index. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/5.Classical.FM.pd)`
- **Is PM preferred?** — The text does not say "prefer PM" outright. What it says: matching PM with FM is done only for teaching and is not practical, so use PM if PM is what you want; and the DX7 and the `pm2~`/`pm4~`/`pm6~` synths are PM. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/5.Classical.FM.pd)`
- **Operator chains** — Four oscillators in series with slightly off ratios (boxes show 2.01, 3.01, 0.501, 1.01) give a near-harmonic sound with beating. The same chain is built from four `sine~` or from two `pm~`. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/6.Multiple.Oscillators.pd)`
- **Feedback PM needs a one-sample loop** — The oscillator's output goes back to its own phase through `send~`/`receive~` inside a subpatch with `block~ 1`, because a Pd feedback loop always costs one block. Trap: a one-sample delay is a different time at a different sample rate, so the sound changes with sample rate. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/7.Feedback.Cross.Modulation/1.Feedback.pd)`
- **Taming feedback noise** — Feedback PM gets noisy. The fix shown is a two-sample average filter in the loop (`mov.avg~ 2`), which the text says appears in Yamaha patents and in FM8. Oversampling with filtering is named as another option. ELSE `fbsine~` is a feedback-PM oscillator with the filter built in. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/7.Feedback.Cross.Modulation/1.Feedback.pd)`
- **Cross modulation** — Two oscillators modulate each other, giving two outputs. `xmod~` does this with separate frequency and index per oscillator; the `-pm` flag selects phase modulation, and the FM example uses it without the flag. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/7.Feedback.Cross.Modulation/3.Cross.Modulation(PM).pd and 4.Cross.Modulation(FM).pd)`
- **`xmod2~`** — Cross frequency modulation with a cheaper sine approximation, described as giving more chaotic sounds. The comments beside it read freq1, index1, freq2, index2 (box: `xmod2~ 170 555 120 666`); the extracted text does not confirm that this is the argument order. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/7.Feedback.Cross.Modulation/4.Cross.Modulation(FM).pd)`
- **`pm2~`, `pm4~`, `pm6~`** — PM synths with 2, 4 or 6 sine operators. Each operator has a ratio to the input frequency, a detune, a level and a pan. A modulation matrix sets every index: the diagonal is self-feedback, the off-diagonal cells are operator-to-operator. Messages seen: `ratio1`, `detune1`, `vol1`, `pan1`, `1to1`, `1to2`, `2to1`, `2to2`; flags `-ratio`, `-detune`, `-pan`. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/7.Feedback.Cross.Modulation/5.[pm2~].[pm4~].[pm6~].pd)`
- **DX7 algorithms** — The DX7 has 6 sine operators and 32 fixed routings. The patch rebuilds routing 6 from `sine~` objects plus one `xmod~` for the feedback pair. The text says one `pm6~` can make any of the 32, and more. `pm6.m~` is the ready-made module version with a matrix on its face. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/8.DX7.pd and 9.[pm6.m~].pd)`
- **PWM is also sideband synthesis** — Modulating the width of `bl.square~` or `bl.vsaw~` above about 20 Hz makes sidebands around every partial, spaced by the modulator frequency, growing with depth, much like FM/PM. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/3.PWM/1.PWM-1.pd and 2.PWM-2.pd)`

### 25 — Waveshaping

- **Table lookup shaper** — The input (−1 to 1) is rescaled to table indices and read with `tabread4~`. ELSE `shaper~ <table>` does the rescale itself. `(source: Part.05-Synthesis(Basic)/25-Waveshaping/1.Introduction.pd)`
- **What `shaper~` adds** — It wraps input that goes past the table range, includes a DC filter, and uses a different interpolation from `tabread4~`. The Vanilla version needs each step by hand: rescale to 0–1, `wrap~`, × 4096 + 1 for the guard point, `tabread4~`, `hip~ 5`. `(source: Part.05-Synthesis(Basic)/25-Waveshaping/6.Wavetables.pd)`
- **Input level is part of the sound** — Stated more than once: in waveshaping the input amplitude changes the result, so an envelope on the input sweeps the timbre. `(source: Part.05-Synthesis(Basic)/25-Waveshaping/6.Wavetables.pd)`
- **Breakpoint transfer functions** — `function~` (drawn with the `function` GUI) is used as a transfer function after rescaling the input to 0–1. A sign function, `expr~ if($v1 > 0, 1, -1)`, turns any input into a square while keeping its pitch. `(source: Part.05-Synthesis(Basic)/25-Waveshaping/2.[function~].pd)`
- **Trig functions as shapers** — `sin~` folds the wave back because it wraps. `cos~` returns 1 for a silent input, so it makes DC and needs a highpass (`hip~ 5`). `tanh` is the soft clipper; the text gives its useful input range as −7.6 to 7.6, with hard clipping beyond. `asin` turns a sine into a triangle (the text calls it "inverse hyperbolic sine", but the box is `expr~ asin($v1)`). `(source: Part.05-Synthesis(Basic)/25-Waveshaping/3.Trig_functions.pd)`
- **Power shaping with negative input** — Vanilla `pow~` outputs 0 when a negative value is raised to a non-integer power. ELSE `power~` returns −(−a)^b instead, so the sign is kept and it works as a shaper. The `expr~` equivalent shown is `copysign(pow(abs($v1), $v2), $v1)`. Exponents below 1 distort harshly. `(source: Part.05-Synthesis(Basic)/25-Waveshaping/4.[power~].[drive~].pd)`
- **`drive~` modes** — Mode 0 is tanh. Mode 1 is a power function. Mode 2 passes values under a threshold (the drive, 0–1) and soft-clips above it; at 1 it hard-clips at ±1. The patch gives `expr~` formulas for modes 1 and 2; the mode 2 formula is the one testing `abs($v1) <= $v2`. `(source: Part.05-Synthesis(Basic)/25-Waveshaping/4.[power~].[drive~].pd)`
- **Folding and wrapping** — `fold~` reflects the signal at its limits and `wrap2~` wraps it around. Both default to −1…1, take a range as arguments (`fold~ -0.5 0.5`) and handle multichannel signals. `(source: Part.05-Synthesis(Basic)/25-Waveshaping/5.Fold.wrap.pd)`
- **Chebyshev shaping** — Polynomial Tn turns a full-level sine into its nth harmonic. T0 gives DC and T1 passes the input. A weighted sum of T0…T11 makes a transfer function with chosen harmonic levels. The box for T10 is 512x¹⁰ − 1280x⁸ + 1120x⁶ − 400x⁴ + 50x² − 1. `(source: Part.05-Synthesis(Basic)/25-Waveshaping/7.Chebyshev.polinomials/1.Chebyshev.pd)`
- **`shaper~` builds Chebyshev functions from a list** — Give it harmonic weights as arguments, starting at T1 (`shaper~ 0.5 0.7 0.2 0.5 0.5 0.3`). The harmonics match the weights only when the input peaks at exactly 1; other levels give other spectra. `(source: Part.05-Synthesis(Basic)/25-Waveshaping/7.Chebyshev.polinomials/2.[shaper~].pd)`
- **FM/PM seen as waveshaping** — With the carrier at 0 Hz, the oscillator is just a sine transfer function and the modulator is the signal being shaped. The preset shows the index conversion in numbers: PM index 0.5 with a 200 Hz modulator equals FM deviation 628.319 (0.5 × 2π × 200). `(source: Part.05-Synthesis(Basic)/25-Waveshaping/8.FM-PM/1.FM-PM.pd)`
- **A 0 Hz `wavetable~` is a shaper** — Feeding audio into the phase input of a `wavetable~` at 0 Hz gives the same output as `shaper~` on the same table. The text says this is for teaching more than use. `(source: Part.05-Synthesis(Basic)/25-Waveshaping/8.FM-PM/2.[wavetable~].pd)`
- **Phase distortion (Casio)** — Bend the phase ramp before it reaches the sine lookup. Shown three ways: a `vsaw~` with modulated width used as the phase into `sin~`; a drawn `function~` reshaping a `phasor~`; or a distorted phase into the phase inlet of a 0 Hz oscillator. The last one uses `bl.tri~`, which is band-limited, so the result does not alias. `(source: Part.05-Synthesis(Basic)/25-Waveshaping/9.Phase.Distortion.pd)`

### 26 — Subtractive Synthesis

- **Default filter choices** — `lowpass~ <freq> <Q>` is the resonant lowpass used on `bl.saw~`. `bandpass~ <freq> <Q>` on `noise~` with very high Q (the box uses 50) gives a clear pitch. `(source: Part.05-Synthesis(Basic)/26-Subtractive.Synthesis/1.Filtering.pd)`
- **Sweeps** — LFOs or random sources (`stepnoise~`, `rampnoise~`) pass through `rescale~ <lo> <hi>` to drive cutoff and Q of `vcf~`, `svfilter~`, `bob~`, `lowpass~`, `bandpass~`. `(source: Part.05-Synthesis(Basic)/26-Subtractive.Synthesis/2.Filter.Sweep.pd and 3.Random.pd)`
- **Envelope filter** — A second envelope, separate from the amplitude one, drives the cutoff through `rescale~`. The text says this matches Pd's own example J08.classicsynth. `(source: Part.05-Synthesis(Basic)/26-Subtractive.Synthesis/4.Envelope-Filter-1.pd)`
- **Release-only filter envelope** — An `asr~ 0 750` on the cutoff (through `rescale~ -in 0 1 500 3500`) makes the sound darken as the note is released. The `-in` flag sets the expected input range. `(source: Part.05-Synthesis(Basic)/26-Subtractive.Synthesis/5.Envelope-Filter-2.pd)`
- **Acid-style voice** — A decay-only `adsr~ 0 500 0 0` on the cutoff of `lowpass~`, then `drive~` and a gain trim. A `glide~ 10` on the gate serves as a 10 ms attack/release amplitude envelope. `(source: Part.05-Synthesis(Basic)/26-Subtractive.Synthesis/6.Envelope-Filter-3.pd)`

## Part 06 — Filters (Basic)

### 27 — Filter types

- **`lop~` facts** — One-pole lowpass. It is about 3 dB down at the cutoff and then falls 6 dB per octave. Its curve changes shape above about 5 kHz (at 44.1 kHz). Also used to smooth control data and as an envelope follower. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/1.Low-High_Pass/1.[lop~].pd)`
- **A two-sample average is a high-cut** — `mov.avg~` averaging two samples only removes the very top of the spectrum, so the text calls it a "high cut" more than a lowpass. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/1.Low-High_Pass/2.Average-filter.pd)`
- **`hip~` facts** — Also 6 dB per octave. It is imperfect: at high cutoff settings it boosts high frequencies. A highpass can be made by subtracting a lowpass's output from the input, and that is how `lop~` can remove DC. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/1.Low-High_Pass/3.[hip~].pd)`
- **`lop2~` fixes `lop~`** — It is `lop~` plus a two-sample average. Still 6 dB per octave, but the curve keeps its shape above 5 kHz. With the cutoff at Nyquist it passes the input unchanged. The text adds that a setting of about 7020 Hz behaves like the two-sample average alone. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/1.Low-High_Pass/4.[lop2~].pd)`
- **Q and bandwidth formulas** — Q = f0 ÷ (f2 − f1), where f1 and f2 are the −3 dB points. Centre f0 = √(f1 × f2). Bandwidth in octaves = log2(f2/f1). From the boxes: Q = 1 ÷ (2 × sinh(BW × ln2 ÷ 2)) and BW = asinh(1 ÷ (2Q)) × 2 ÷ ln2. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/1.Q-Bandwidth.pd)`
- **`bp~` is lopsided** — Control-rate frequency and Q, cheap, but it cuts more above the centre than below. The text says it is really a resonant lowpass with gain adjusted so the peak sits at 0 dB; at Q = 1 it is close to `lop~`. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/2.Bandpass/1.[bp~].pd)`
- **`vcf~`** — Signal-rate centre frequency, control-rate Q. Two outlets because it is a complex filter (real and imaginary). The right outlet resembles `bp~`. Not symmetric at low Q, and it misbehaves above about 7 kHz. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/2.Bandpass/2.[vcf~].pd)`
- **`bandpass~`** — Signal-rate control of both frequency and Q, resonance can be given as bandwidth instead, and the response is symmetric across the spectrum, unlike `bp~` and `vcf~`. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/2.Bandpass/3.[bandpass~].pd)`
- **Constant gain versus constant skirt** — A constant-gain bandpass always peaks at 0 dB. A constant-skirt one gets louder at the centre as resonance rises. `resonant~` is constant-skirt. By habit "bandpass" means the first and "resonant" the second. `resonant~` takes resonance as Q, bandwidth or t60. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/2.Bandpass/4.[resonant~].pd)`
- **t60 as a resonance unit** — t60 is the time in ms for the ringing to fall 60 dB. `resonator~` is the same filter as `resonant~` / `lowpass~` / `highpass~` but with resonance given as t60. Default mode is bandpass; messages `lop`, `bp`, `hip` switch it. Its input goes in the middle inlet. Box: `resonator~ 500 1500`, pinged by `imp~ 1`. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/6.resonator/1.[resonator~].pd)`
- **`resonator2~` is for pinging, not filtering** — A variant of `vcf~` whose gain grows with resonance (t60), with the signal in the middle inlet. Warning: on steady input it gets very loud unless resonance is kept low, so use it on impulses. It is the basis of `damp.osc~`. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/6.resonator/2.[resonator2~].pd)`
- **Resonant lowpass and highpass** — `lowpass~` and `highpass~` boost at the cutoff and take resonance as Q, bandwidth or t60. The text compares `lowpass~` to `bp~`/`vcf~` as constant-skirt to constant-gain. An unnamed "resonant filter" usually means a resonant lowpass. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/5.Lowpass/1.[lowpass~].pd and 6.[highpass~].pd)`
- **`bob~`** — Vanilla's Moog-style resonant lowpass. Takes signals for both cutoff and Q. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/5.Lowpass/3.[bob~].pd)`
- **`bandstop~`** — Band reject; with a narrow width it is a notch. Takes Q or bandwidth like a bandpass. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/4.[bandstop~].pd)`
- **Allpass made audible** — `allpass.2nd~ <freq> <Q>` changes only phase. At its centre frequency the shift is 180°, so adding the output back to the dry input cancels there, like a notch. Q sets how steep the phase change is, which here sets the notch width. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/7.[allpass.2nd~].pd)`
- **`svfilter~`** — One object, four resonant outputs: lowpass, highpass, bandpass, bandstop. The resonance control is labelled 0–1. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/8.[svfilter~].pd)`
- **`eq~`** — A peak/dip filter with frequency, Q and gain. With a deep cut it acts like a notch. `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/2.Resonant/9.[eq~].pd)`
- **Shelving filters** — `lowshelf~` and `highshelf~` boost or cut below or above a frequency, with a slope setting for steepness and a gain in dB (box: `lowshelf~ 500 1 12`). `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/3.Shelving/1.[lowshelf~].pd and 2.[highhelf~].pd)`
- **Coefficients for `biquad~`** — `bicoeff` is a clickable response graph that outputs `biquad~` coefficients for nine types from the Bristow-Johnson cookbook: allpass, bandpass, highpass, lowpass, resonant, bandstop, highshelf, lowshelf, eq. Drag sideways for frequency, drag the vertical lines for bandwidth or slope, drag up/down for gain on the three types that have it. `bicoeff2` does the same with no GUI (box: `bicoeff2 eq 500 10 24`). `(source: Part.06-Filters(Basic)/27-Filters.types/2.Filter.Types/4.[biquad~].[bicoeff].pd)`
- **`biquads~`** — Several biquad sections in series in one object. Each section is 5 coefficients, the same as Vanilla `biquad~`; join the lists to add sections. `(source: Part.06-Filters(Basic)/27-Filters.types/3.Cascade.Parallel/2.[biquads~].pd)`
- **Series and parallel** — Two `lop~` in series give 12 dB per octave. A `lop~` then a `hip~` make a rough bandpass. Parallel means feed several filters and sum them. `(source: Part.06-Filters(Basic)/27-Filters.types/3.Cascade.Parallel/1.Cascade-Paralell.pd)`
- **Filter banks** — `bpbank~` is parallel `bandpass~` filters (`bpbank~ 4 -freq … -q …`). `resonbank~` and `resonbank2~` are banks of `resonator~` and `resonator2~`, meant for synthesis by excitation (`resonbank~ -ratio … -decay … -amp …`). All can put each filter on its own channel. `(source: Part.06-Filters(Basic)/27-Filters.types/3.Cascade.Parallel/3.Filterbanks.pd)`

### 28 — Filter FX

- **Wah** — A filter sweep with a minimum and maximum frequency, here from an LFO through `rescale~ 500 2000` into `vcf~`, followed by `drive~`. `(source: Part.06-Filters(Basic)/28-Filter.FX/1.Wha-wha/1.Wah-wah.pd)`
- **Auto-wah** — An envelope follower replaces the LFO: `mov.rms~ 256` gives level in dB, `rescale~ -in -40 -5 100 4000` maps −40…−5 dB to 100…4000 Hz, into the cutoff of `lowpass~ 0 5`. `(source: Part.06-Filters(Basic)/28-Filter.FX/1.Wha-wha/2.Auto-Wah.pd)`
- **Crossover** — Built by hand as three `lop~` in series beside three `hip~` in series at one cutoff. ELSE `crossover~` is a ready-made one, but a third-order Butterworth, so not identical. Chain two `crossover~` objects for three bands. `(source: Part.06-Filters(Basic)/28-Filter.FX/2.Multiband-Processing/1.Crossover.pd and 2.Multiband.Processing.pd)`
- **Graphic EQ and multiband compression** — A 4-band EQ uses `lowshelf~` and `highshelf~` at the ends and two `eq~` in the middle, with gains in dB. The compression example splits into 4 bands and gives each its own `compress~`. `(source: Part.06-Filters(Basic)/28-Filter.FX/2.Multiband-Processing/3.Graphic.Equalizer.pd and 4.Multiband.Compression.pd)`
- **Analysis filter bank** — 24 bands in a `clone`, centres spaced a minor third apart (3 per octave) starting at MIDI 20. Each band is two `bandpass~` in series followed by `env~`. (The text says minor thirds; the box that generates the pitches reads `loop -step 4 -offset 20 24`. The mismatch is in the source.) `(source: Part.06-Filters(Basic)/28-Filter.FX/2.Multiband-Processing/5.Vocoder/1.Filterbank.Analysis.pd and filter.pd)`
- **Vocoder construction** — 28 bands in a `clone`. In each band the synth input passes through `bandpass~` and is multiplied by the level of the speech input, measured with `mov.rms~ -lin 512` (a running mean of the last 512 samples). Centres are set as MIDI pitch from a bottom note and a semitone step; one Q serves all bands. The extracted text does not show whether the speech is band-filtered before `mov.rms~`. `(source: Part.06-Filters(Basic)/28-Filter.FX/2.Multiband-Processing/5.Vocoder/2.Vocoder.pd and vocoder.band.pd)`
- **Normalize after a vocoder** — Output level changes with Q, so the patch ends with `norm~`. ELSE `vocoder~` is based on this patch. `(source: Part.06-Filters(Basic)/28-Filter.FX/2.Multiband-Processing/5.Vocoder/2.Vocoder.pd)`

## Part 07 — Sampling, Delay, Granulation

### 29 — Sampling (buffer)

- **File players** — Vanilla `readsf~` plays from disk and needs an `open` message before each play. ELSE `play.file~` is the convenient version: multichannel, and reads MP3, FLAC, WAV, AIF, AAC, OGG and OPUS. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/1.Play/1.[readsf~].[play.file~].pd)`
- **Loading into a table** — Vanilla `soundfiler` needs `read -resize` to size the table. ELSE `sfload` resizes by default and reads the same extra formats, but only reports file information after a load. `sfinfo` only queries a file: channel count, and the `inst` chunk of AIFF files. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/1.Play/2.Buffer.[tabplay~].pd)`
- **`sample~`** — An abstraction on `sfload` that owns its table. It handles multichannel files, reports size in samples, sample rate, length in ms, channels and bit depth, and can also be an empty buffer to record into (`sample~ <name> -ch 2 -size 1500`). `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/1.Play/3.[sample~].[tabplayer~].pd and 4.Record/2.[rec.file~].[tabwriter~].pd)`
- **Sample-rate mismatch trap** — `tabplay~`, `readsf~` and `play.file~` play at the wrong speed if the file's sample rate differs from Pd's. One workaround is to put the player in a subpatch that runs upsampled (`block~ 64 1 2` for an 88.2 kHz file at 44.1 kHz). `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/1.Play/4.Upsampling.pd)`
- **Looping with a phasor** — Loop frequency = the file's sample rate ÷ its length in samples. Multiply by a speed ratio (from cents or percent); negative plays backward. With `tabread4~` the phasor is scaled by the length; `tabreader~` takes 0–1 directly. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/1.Play/5.[phasor~].[tabread4~].pd and 6.[tabplayer~].[table~].[player~].pd)`
- **Less interpolation noise** — Interpolation adds noise. The tip given is to use a file with a higher sample rate than the session (for example an 88.2 kHz file at 44.1 kHz), upsampled beforehand with a good resampler. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/1.Play/5.[phasor~].[tabread4~].pd)`
- **`tabplayer~` and `player~`** — `tabplayer~` plays a table with variable speed, looping, crossfade, multichannel, and can be triggered by a signal (`pulse~`). It must be told the file's sample rate with an `sr` message if it differs. `player~` wraps `sample~` + `tabplayer~`, loads the file itself and corrects for sample rate automatically. Messages seen: `play <start> <end> <speed %>`, `speed`, `range`, `pause`, `resume`. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/1.Play/6.[tabplayer~].[table~].[player~].pd and 3.[sample~].[tabplayer~].pd)`
- **`ramp~` as a play head** — A low-level counter: increment 1 is normal speed, 0.5 half, 2 double, negative reversed. Multiply the increment by file rate ÷ session rate. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/1.Play/7.[ramp~]..pd)`
- **Random segments** — `envgen~` (or Vanilla `vline~`) drives the read index with start, duration and target, where duration = |end − start| ÷ speed ratio. A second envelope removes clicks. `tabplayer~ -fade 30` with `range` and `speed` messages does the same with a built-in fade. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/1.Play/8.[envgen~].pd)`
- **`susloop~`** — Produces a read index that holds a sustain loop between two sample points (box: `susloop~ 1 10000 50000`) and feeds `tabread~` / `tabread4~`. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/1.Play/9.[susloop~].pd)`
- **Long-file precision limit** — With 32-bit floats, signal-rate indexes are exact only up to 2²⁴ samples, about 6 min 20 s at 44.1 kHz, and fractional precision drops too. This hits `tabread4~` and 0–1 phase readers driven by a signal. Vanilla's workaround is the onset inlet of `tabread4~`. Objects that step through the table themselves (`tabplay~`, `tabplayer~`, `player~`) are not affected. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/2.Large.samples.issue.pd)`
- **Why interpolate at all** — `readsf~` does not interpolate, so it can only play at the session rate or whole multiples of it. Any other speed lands between samples. Linear interpolation: a × (1 − frac) + b × frac. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/3.Interpolation/1.Linear.Interpolation.pd)`
- **Vanilla's 4-point Lagrange** — `tabread4~`, `tabosc4~` and `delread4~` use a 4-point cubic (Lagrange) through points a, b, c, d. Box formula: b + frac × (c − b − 0.5/3 × (1 − frac) × ((d − a − 3(c − b)) × frac + (d + 2a − 3b))). The guard points are index 0 (a copy of the last real point) and the last two (copies of the first two); inputs are clipped to the real range. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/3.Interpolation/2.Cubic.Lagrange.pd)`
- **`tabreader` / `tabreader~` options** — No guard points needed; it makes its own copies. Input is 0–1 by default. Methods: none, linear, cosine (half a cosine between points), Lagrange, spline (the default), cubic, and general Hermite with tension and bias. Flags seen: `-loop`, `-lin`, `-cos`, `-hermite <tension> <bias>`, `-index`. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/3.Interpolation/3.[tabreader].pd, 4.Cosine.[tabreader~].pd and 6.Other.objects.pd)`
- **Lagrange versus Hermite** — Lagrange passes through all four points and has low error against an ideal interpolator, but its slope can jump at sample points (sharp corners); the text says Csound's cubic functions use it too. Hermite passes through b and c only and sets the slope at b to (c − a)/2, so no corners, but curvature can change abruptly. "Spline" (Catmull-Rom) is tension 0, bias 0, the default in ELSE and, the text says, in SuperCollider. "Cubic" is tension −1, which doubles the slope. Slope at b in general = (1 − tension) × (c − a)/2. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/3.Interpolation/5.Cubic.Hermite.pd)`
- **Which ELSE objects interpolate how** — `shaper~`, `del~`, `ffdelay~`, `fbdelay~`: spline. `tabplayer~`: spline by default, or Lagrange. `gendyn~`: none, linear, cosine. `wavetable~`: none, linear, cosine, spline, Lagrange. (The pairing was read from the positions of comments and boxes in the original `.pd` file.) `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/3.Interpolation/6.Other.objects.pd)`
- **Recording** — Vanilla: `writesf~` to disk, `tabwrite~` to a table. ELSE: `rec.file~` wraps `writesf~`, is multichannel and has an `autofade~` inside to avoid clicks. `tabwriter~` adds sample-accurate triggering, a signal-set write index and multichannel tables. `sample~` can save what was recorded into it. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/4.Record/1.[writesf~].[tabwrite~].pd and 2.[rec.file~].[tabwriter~].pd)`
- **Faster-than-real-time rendering** — `batch.rec~` renders a patch to a file as fast as the CPU allows, using Pd's fast-forward feature; `batch.write~` does the same into a table. Warning in the text: do not start it while audio is going to the speakers. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/4.Record/3.Batch.record.pd)`
- **Sampler voice from loop metadata** — `sfinfo` reads the `inst` chunk of an AIFF file to get the reference pitch and sustain-loop points. Playback rate = played frequency ÷ reference frequency, sent to `susloop~`, which loops while the key is held. `glide2~ 0 500` makes the release. A polyphonic version loads the voice in `clone` with `voices 6`. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/5.Sample-Synth/1.Sampler-Synth.pd and 2.Sampler-Synth-clone.pd)`
- **SoundFont players** — `sfont~` plays SoundFont files and `sfz~` plays SFZ. The text notes MuseScore uses both formats. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/5.Sample-Synth/3.[sfont~].[sfz~].pd)`

### 30 — Delay (ring buffer)

- **Vanilla delay objects** — `delwrite~ <name> <ms>` writes a named ring buffer; any number of `delread~` taps read it. `delread~` is control-rate, does not interpolate, and can read at 0 delay. `delread4~` takes a signal and interpolates (Lagrange), and its minimum is 1 sample because the first sample is a guard point. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/1.Delay/1.[delwrite~].[delread~].pd and 3.[delread4~].pd)`
- **Moving a tap shifts pitch** — While the delay time changes, the tap's movement adds to the read speed and the pitch changes. When it stops, pitch returns. This is the basis of the vibrato, chorus, flanger and pitch shifter that follow. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/1.Delay/3.[delread4~].pd)`
- **Delays shorter than a block need forced ordering** — The writer must run before the reader. Pd offers no direct way, so each goes in its own subpatch and a dummy outlet-to-inlet cord between them fixes the order. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/1.Delay/4.Execution.Order.pd)`
- **`del~`** — `del~ in <name> <ms>` writes and `del~ out <name> <ms>` reads. Spline interpolation. Extras: resize the line (`size`), `freeze` (writing stops, the head keeps moving), delay in samples (`-samps`). It has the same ordering issue, but `del~ in` has a dummy signal outlet to help. The text says it also fixes a Vanilla bug that shows when reader and writer run at different block sizes. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/1.Delay/5.[del~].pd)`
- **`ffdelay~`** — A one-object feedforward delay with signal-rate time, spline interpolation, resize and freeze, and no ordering worry. One output only for now; for several taps on one line use a single writer with several readers. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/1.Delay/6.[ffdelay~].pd)`
- **Minimum feedback delay** — A feedback loop costs at least one block (64 samples by default). In a `block~ 1` subpatch that is 1 sample, but `delread4~` adds its own sample, so 2. For a true 1-sample loop use `delread~` at 0 ms, a `send~`/`receive~` pair, or ELSE `del~`. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/1.Delay/7.Feedback.pd)`
- **Negative feedback** — A negative coefficient flips polarity on each repeat. The text says this changes the sound noticeably at very short delay times. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/1.Delay/7.Feedback.pd)`
- **`fbdelay~`** — A feedback delay in one object, minimum 1 sample. By default the feedback amount is a decay time: the ms it takes to fall 60 dB (`fbdelay~ 100 2000`). The `-gain` flag makes it a plain multiplier and `-samps` gives time in samples (`fbdelay~ -samps -gain 1000 0.9`). `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/1.Delay/8.[fbdelay~].pd)`
- **When the one-object delay is not enough** — If anything else must sit inside the loop (a filter, an oscillator), `fbdelay~` cannot be used; you need separate write and read objects. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/1.Delay/8.[fbdelay~].pd)`
- **`comb.rev~`** — A feedforward and a feedback delay line together. The text gives the arguments as delay time (initial and maximum, in ms), gain, feedforward coefficient, feedback coefficient (box: `comb.rev~ 1000 1 1 0.9`). It equals an `ffdelay~` plus an `fbdelay~`. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/1.Delay/9.[comb.rev~].pd)`
- **Ping-pong** — Echoes alternate left and right; the stereo version feeds each channel's delay output into the other channel's line. `ping.pong~ 200 0.8` is the ELSE abstraction built on the first patch. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/2.Ping.Pong/1.PingPong-1.pd and 2.PingPong-2.pd)`
- **Vibrato and chorus from one delay** — An LFO on the time of `ffdelay~` gives vibrato: LFO rate is the rate, LFO amplitude the depth. Mixing it 50/50 with the dry signal (`xfade~`) starts to sound like chorus. ELSE `vibrato~ <rate> <cents>` is built differently, on a granular pitch shifter, with depth in cents. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/3.TimeVariableDelay(Vibrato.Chorus.Flanger)/1.[vibrato~].pd)`
- **Feedback vibrato** — With a feedback delay the pitch shift adds up on every pass, so pitch keeps rising and falling. Depth becomes a minimum and maximum delay time. Some settings give chorus or flanger sounds. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/3.TimeVariableDelay(Vibrato.Chorus.Flanger)/2.Feedback.Vibrato.pd)`
- **Flanger with both lines** — A flanger can be feedforward, feedback, or both. Trap: a negative feedback value can cancel the feedforward line. The patch avoids it by using one coefficient for both, and `flanger~` (rate, depth, coefficient) is built that way. Preset values seen: delay 0.1–8 ms, feedback 0.9. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/3.TimeVariableDelay(Vibrato.Chorus.Flanger)/3.[flanger~].[flanger.m~].pd)`
- **Chorus** — `comb.rev~` with an LFO on its delay time mixes the input with a pitch-wobbled copy. Here negative feedback is used on purpose: because it cancels the feedforward line, at −1 only the dry signal is left, so it works like a dry/wet control. `chorus~` is based on this. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/3.TimeVariableDelay(Vibrato.Chorus.Flanger)/4.[chorus~].[chorus.m~].pd)`
- **Delay arpeggiator** — Drive the delay time with a trapezoid (a `function~` read by a `phasor~`) instead of a sine. Rising ramp: pitch drops. Flat top: original pitch. Falling ramp: pitch rises. Three steady pitches set by rate and depth. With feedback the shifts pile up; `rampnoise~` gives random shifts. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/4.Arpeggiator/1.Arpeggiator.pd and 2.Feedback.pd)`
- **Reverse delay** — Sweep the delay time 0 → line length with a `phasor~`. At a rate of 1 ÷ line length the sweep cancels the write speed, so you hear nothing but a click at each wrap. At twice that rate the audio plays backward at normal speed. Because the tap then covers only half the line per pass, make the line twice as long as the reverse segment you want. The text names the ELSE object `rdelay~`; the box in the patch is `revdelay~`. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/5.Reverse.delay.pd)`
- **Filtered delay that cannot blow up** — The loop holds a resonant `lowpass~`, a DC filter (`hip~ 5`) and a soft clipper (`drive~`). Feedback has no limit and can be negative; the DC filter and clipper contain it. The filter re-filters on every pass, so high resonance builds up like feedback above 1. A `clear` message empties the line. `filterdelay~` is the compiled version, with freeze. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/6.Filtered.delay.pd)`

### 31 — Granulation

- **One grain** — A `phasor~` reads `position + phasor × grain size` from the table and also drives the window (`envelope~`, sine by default). Size and position pass through `samphold~` triggered by the phasor so they change only between grains, which avoids clicks. Grain size and rate together affect the pitch heard. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/1.Introduction/1.Grain.pd)`
- **Two overlapping grains** — One windowed grain is just amplitude modulation and adds a tremolo. Two grains half a cycle apart fix that. With a sine window the two windows are sine and cosine, which is an equal-power crossfade. `pimp~` (a phasor plus an impulse at each wrap) has a phase argument for this: `pimp~ 0 0.5`. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/1.Introduction/2.Overlap.pd)`
- **Negative grain rate trap** — A negative rate reads grains backward, but Vanilla `samphold~` is not triggered by a `phasor~` running backward. The Vanilla fix turns the phasor's jump into a trigger with `fexpr~`. ELSE's `pimp~` outputs an impulse at each wrap in either direction and `sh~` samples on it. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/1.Introduction/3.Negative.Freq.pd)`
- **Random grain parameters** — `noise~` sampled by `sh~` at grain boundaries gives a new random position and size per grain. `stepnoise~` or `rampnoise~` varies the grain rate. `drunkard~` gives a random walk through the file. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/1.Introduction/4.Drunkard.pd and 5.Random1.pd)`
- **Granulating live input** — Swap `tabread4~` for `delread4~` on a 5-second `delwrite~`. The big difference is that the buffer's read head is always moving. The writer and the grain readers sit in separate subpatches joined by a dummy cord to fix the order. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/1.Introduction/7.Ring.buffer(delay).pd)`
- **Independent pitch and speed, block-size method** — Grain length is tied to the block size of a subpatch, so only powers of 2 are possible. A step (a percentage of grain size) sets where the next grain starts, which sets speed. The transposition ratio sets how much audio each grain reads ("new size"), which sets pitch. Two overlapped grains. The text says this is the basis of its later phase vocoder. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/2.Pitch.Shift&Time-Stretch/1.Buffer(array)/1.Strech.shift.pd)`
- **Independent pitch and speed, any grain size** — A `phasor~` at file rate × speed ratio moves through the file. A `pimp~` at the grain rate adds a ramp of one grain length on top. That ramp's rate is (transposition ratio − speed ratio) × grain frequency, where grain frequency = 1000 ÷ grain ms. Two grains, the second half a cycle out. `gran.player~` is based on this. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/2.Pitch.Shift&Time-Stretch/1.Buffer(array)/2.[gran.player~].pd)`
- **Delay-line pitch shifter** — A `phasor~` ramps the delay time over one grain length. Its frequency = (1 − ratio) × (1000 ÷ grain ms). The "1 −" covers two things: the line is already moving at speed 1, and a rising delay ramp lowers pitch. Two overlapped windowed grains. Grain size (5–200 ms here) matters little unless extreme, so it is usually fixed. `pitch.shift~` is built this way; `vibrato~` is the same idea with an LFO. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/2.Pitch.Shift&Time-Stretch/2.Ring.buffer(delay)/1.[pitch.shift~].pd and 2.[vibrato~].pd)`
- **Time stretch on a delay line** — A `phasor~` spanning the whole buffer runs at a rate scaled by (1 − speed). `sh~` samples it at each grain start, so each grain begins a little further along and then plays at normal speed. Resetting the phasor's phase jumps back to the start. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/2.Pitch.Shift&Time-Stretch/2.Ring.buffer(delay)/3.Time.stretch.pd)`
- **`stretch.shift~`** — Combines the last two. The transposition is applied to the grain's phase, not its frequency, and goes through its own sample-and-hold, so it changes only at grain boundaries and does not disturb the read speed in the middle of a grain. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/2.Pitch.Shift&Time-Stretch/2.Ring.buffer(delay)/4.[stretch.shift~].pd)`
- **Block-size method on live input** — The same as the table version but reading a delay line. Times are in ms, not samples; speed and transposition both subtract the line's own speed (1 − x); and the second grain's offset is added, not subtracted, because larger delay means further back. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/2.Pitch.Shift&Time-Stretch/2.Ring.buffer(delay)/5.Stretch-shift-2.pd)`
- **Grain clouds with `clone`** — 16 voices fire inside a 1-second event from one bang. Asynchronous mode gives each voice a random start delay within the event, except voice 0, which starts at once. Synchronous mode delays voice n by n × (1000 ÷ 16) ms. A `limit` object ignores new triggers until the event is over. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/3.Cloud.granulation/1.[grain.synth~].pd and grain.synth.pd)`
- **Turning idle grain voices off** — Each voice's `envelope~` reports its status from its right outlet, and that switches the voice's DSP on and off with `switch~`, to save CPU. Each grain gets a random size, amplitude, pan and pitch. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/3.Cloud.granulation/grain.synth.pd)`
- **Cloud from a sample** — Each voice plays with `tabplayer~ -loop` (looping in case a grain starts near the end). It gets a random start position, a random transposition of ±1200 cents converted to a speed, and a 50% chance (`chance 50`) of a negative speed for reverse. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/3.Cloud.granulation/grain.sampler.pd)`
- **Cloud from live input** — Each voice reads a 5000 ms delay line with `delread4~`, using the delay pitch-shifter ramp for transposition plus a random position, wrapped with `wrap2~ 0 5000`. The `delwrite~` sits in a subpatch in the parent, connected to the `clone`, to fix the order. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/3.Cloud.granulation/3.[grain.live~].pd and grain.live.pd)`
- **Ready-made cloud objects** — `grain.synth~` (wavetable grains; it adds an `autotune` option and other envelope shapes), `grain.sampler~` and `grain.live~` are the ELSE abstractions built on these three patches. `(source: Part.07-Sampling.Delay.Granulation/31-Granulation/3.Cloud.granulation/1.[grain.synth~].pd, 2.[grain.sampler~].pd and 3.[grain.live~].pd)`

## Part 08 — FFT and complex signals

### 32-FFT-IFFT

- **A tone of any phase is one cosine plus one sine** — A sinusoid with any starting phase equals a cosine of amplitude `a` plus a sine of amplitude `b` at the same frequency. Its amplitude is `sqrt(a² + b²)` and its phase is the arctangent of `b/a`. This is the whole reason an FFT bin has two numbers. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/1.Introduction/1.Pure.Tone-Decomposition.pd)`
- **Cartesian/polar helpers** — The tutorial converts with `car2pol` / `pol2car` and the signal versions `car2pol~` / `pol2car~`. `mag` and `mag~` give only the magnitude from real and imaginary parts. `rad2deg` and `deg2rad` convert the angle; the text names those two as ELSE objects. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/1.Introduction/2.Complex.Numbers.pd)`
- **`circle` is a 2-D slider** — ELSE's `circle` GUI outputs an (x, y) pair. It has a polar display mode (`mode 2`), but the output is still cartesian, so `car2pol` is needed after it. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/1.Introduction/3.[circle].pd)`
- **Bin spacing and what "stable" means** — Bin spacing is sample rate divided by block size, and the bins are a harmonic series of that value. A sine gives a steady analysis only when its frequency sits exactly on a bin. `blocksize~` reports the block size, and `blocksize~ -hz` reports the matching frequency. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/2.FFT/1.[fft~].pd)`
- **`fft~` versus `rfft~`** — `fft~` is the complex transform: two inlets (real, imaginary), and for a real input it shows mirrored bins above Nyquist. `rfft~` takes one real input and outputs bins only up to Nyquist, which costs less CPU. The tutorial uses `rfft~` for almost everything. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/2.FFT/2.[rfft~].pd)`
- **Raw FFT amplitude scale** — Without a window, a bin's amplitude can reach half the block size. Phase comes out in radians. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/2.FFT/1.[fft~].pd)`
- **Hann window from an oscillator** — Run a cosine oscillator at exactly one cycle per block (the frequency from `blocksize~ -hz`), invert it, and rescale to 0..1. ELSE's `hann~` applies a Hann window to its input directly; the text says it computes the curve a different way. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/2.FFT/3.Windowing.pd)`
- **Overlap and hop size** — Window 2048 with 4 overlaps gives a hop of 512 samples. In Pd the overlap is the second argument of `block~` (`block~ 2048 4`), and the subpatch's `inlet~` / `outlet~` do the overlapping and the summing automatically. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/2.FFT/4.Overlap.pd; Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/2.FFT/5.[block~].pd)`
- **Hann changes the amplitude scale** — With a Hann window the largest bin amplitude is block size / 4 (512 for a 2048 window), not block size / 2. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/2.FFT/5.[block~].pd)`
- **dB spectrum recipe** — `rfft~` → `mag~` → divide by block size / 4 → `lin2db~` → floor at −100 with `max~ -100`. Upper harmonics of a saw are much easier to see this way than on a linear scale. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/2.FFT/6.dB.pd)`
- **Log-frequency display** — Send the amplitudes to a table, then read that table with a second table of log-spaced indexes (`pow(1023, i/1022)`) using an interpolating read. The text warns that this only changes the picture: the FFT is still linear and still has poor resolution at low frequencies. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/2.FFT/7.Log_Freq.pd)`
- **`spectrograph~`** — ELSE abstraction that plots spectral amplitude. Messages shown: `size`, `db` (linear or dB amplitude), `log` (linear or log frequency). `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/2.FFT/8.[specgtrograph~].pd)`
- **Zero padding** — To analyse a 16384-sample sound with a 32768-point FFT, multiply the input by a table that is 1 for the first half and 0 after. The longer window gives finer frequency resolution. The same trick is reused later for convolution. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/2.FFT/9.Zero.padding.pd)`
- **Resynthesis normalization** — Without windows, divide the inverse transform by block size × overlaps. With a Hann window before the FFT and another after the inverse FFT, also divide by 0.375 (3/8), which is the average of the Hann curve squared. For overlap 4 this is 1.5 × block size: the patches use `/~ 3072` for 2048, `/~ 1536` for 1024 and `/~ 768` for 512. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/3.IFFT/1.iFFT.pd; Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/3.IFFT/2.Normalization.Other.Windows.pd)`
- **A second Hann window is needed after the inverse FFT** — The text says so explicitly; every later spectral patch windows on both sides. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/3.IFFT/1.iFFT.pd)`
- **Latency** — FFT analysis plus resynthesis delays the signal by one hop size. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/3.IFFT/1.iFFT.pd)`
- **FFT resynthesis is granular, not additive** — A single frame can only rebuild sounds made of the FFT's own bin frequencies. A partial that falls between bins is encoded by the phase of each bin changing from frame to frame, and the overlapped grains rebuild it. The author calls the "bank of sine oscillators" picture misleading. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/3.IFFT/1.iFFT.pd)`
- **Other window formulas** — Hamming: `0.54 + 0.46·cos(x)`. Blackman: `0.42 − 0.5·cos(x) + 0.08·cos(2x)`. Cosine: half a sine cycle. Welch: appears to be `1 − (X/A)²` with `X = i − N/2` and `A = N/2` (the extracted text is fragmented). Connes: Welch squared. Lanczos: `sin(x)/x` over −pi..pi. Also triangular, Gaussian and Kaiser. `tabgen` can generate them. Each window needs its own normalization factor, taken from its average. `(source: Part.08-FFT.&.Complex.Signals/32-FFT-IFFT/3.IFFT/2.Normalization.Other.Windows.pd)`

### 33-Complex.Signals

- **Complex sinusoid recipe** — `phasor~` into `cos~` (real part) and into `sin~` (imaginary part). Converting that pair to polar gives the amplitude and the running phase at every sample, which a plain real sine cannot give. `(source: Part.08-FFT.&.Complex.Signals/33-Complex.Signals/1.Complex.Sine/2.Complex.Sinusoid-2.pd)`
- **Time-domain complex is not FFT complex** — The text stresses that a complex signal in time (two signals 90° apart) is a different thing from the complex output of an FFT. `(source: Part.08-FFT.&.Complex.Signals/33-Complex.Signals/1.Complex.Sine/1.Complex.Sinusoid-1.pd)`
- **`hilbert~`** — A Pd Vanilla "extra" abstraction. It turns a real signal into two outputs 90° apart, using two allpass filters. Trap: the "real" output is not the same as the input signal. `(source: Part.08-FFT.&.Complex.Signals/33-Complex.Signals/2.Hilbert.Transform.pd)`
- **No mirror for complex input** — A real signal into `fft~` gives mirrored components above Nyquist. A complex signal (from `hilbert~`) does not. `(source: Part.08-FFT.&.Complex.Signals/33-Complex.Signals/3.Complex-FFT.pd)`
- **Complex multiply and divide** — Multiply: `Re = Re1·Re2 − Im1·Im2`, `Im = Im1·Re2 + Re1·Im2`; in polar terms, amplitudes multiply and phases add. Divide: `Re = (Re1·Re2 + Im1·Im2)/norm`, `Im = (Im1·Re2 − Re1·Im2)/norm`, `norm = Re2² + Im2²`; amplitudes divide and phases subtract. The text says the cartesian form is more accurate and cheaper than going through polar. `(source: Part.08-FFT.&.Complex.Signals/33-Complex.Signals/4.Complex.Math.pd)`
- **Frequency shifter (single sideband)** — Make the input complex with `hilbert~`, multiply by a complex sinusoid, keep only the real part: `Re1·Re2 − Im1·Im2`. It is ring modulation with one sideband instead of two. `(source: Part.08-FFT.&.Complex.Signals/33-Complex.Signals/5.Complex-Modulation/1.Freq-Shifting.pd)`
- **Frequency shift is not pitch shift** — Every partial moves by the same number of hertz, so a harmonic sound becomes inharmonic. Shifting up squeezes the ratios; shifting down stretches them. `(source: Part.08-FFT.&.Complex.Signals/33-Complex.Signals/5.Complex-Modulation/1.Freq-Shifting.pd)`
- **`freq.shift~` versus `complex-mod~`** — Vanilla's `complex-mod~` needs a complex input (so `hilbert~` first) and a shift frequency. ELSE's `freq.shift~` takes a real input and does the Hilbert step inside. Its second outlet is the opposite sideband, shifted the other way. `(source: Part.08-FFT.&.Complex.Signals/33-Complex.Signals/5.Complex-Modulation/2.Objects.pd)`
- **FM or PM applied to any signal** — Two ways. Modulate the shift frequency of `freq.shift~` with an oscillator. Or: `hilbert~` → `car2pol~` → add a modulator to the phase → `pol2car~`. The text notes this is only true FM for a sine; on a saw it is not the same as changing the oscillator's pitch. `(source: Part.08-FFT.&.Complex.Signals/33-Complex.Signals/5.Complex-Modulation/3.Signal.FM.PM.pd)`

## Part 09 — Spectral processing

### 34-Basic

- **Spectral filter from a table** — Inside the FFT subpatch, multiply both the real and the imaginary output by one value per bin, read from a table with `tabreceive~`. The table is the frequency response, so it can be drawn by hand. Low/high/band-pass tables are made by writing 0 or 1 per bin number. `(source: Part.09-Spectral.Processing/34-Basic/1.Filters/1.Array.pd)`
- **Crossover** — Two complementary 0/1 tables (one low-pass, one high-pass), each followed by its own `rifft~`, give a two-band crossover. `(source: Part.09-Spectral.Processing/34-Basic/1.Filters/2.Crossover.pd)`
- **Spectral envelope from an envelope generator** — A `function~` breakpoint envelope is swept by a `phasor~` and written to the filter table with `tabsend~`. That writing subpatch runs at half the FFT size, because `rfft~` only has bins up to Nyquist. `(source: Part.09-Spectral.Processing/34-Basic/1.Filters/3.Envelope.pd)`
- **Zeroing the phase** — Convert to polar, replace all phases with zero, convert back. The pitch of the source disappears and only the FFT's own bin series is heard. Offered as proof that phase carries the tonal information. `(source: Part.09-Spectral.Processing/34-Basic/2.Zeroing.Phase.pd)`
- **Spectral normalizer** — Divide the real and imaginary parts of each bin by that bin's magnitude, so every bin has the same amplitude and only phase is kept. The noise floor rises a lot, but the pitch is still clear. `(source: Part.09-Spectral.Processing/34-Basic/3.Normalizer.pd)`
- **Spectral compressor** — The same patch with a knob that morphs between the original and the fully normalized spectrum, using `clip~`. The comments do not spell out the exact math. `(source: Part.09-Spectral.Processing/34-Basic/4.Compressor.pd)`
- **Spectral gate, three thresholds** — Compare each bin's magnitude with a threshold to make a 0/1 mask; the mask keeps the "signal", and `1 − mask` keeps the "noise floor". The threshold can be a fixed value, a running average of the magnitudes (`mov.avg~ 512`) times a level, or a running median (`median~ 32`). The text says the median works better for pulling out tonal peaks. `(source: Part.09-Spectral.Processing/34-Basic/5.Gate.pd)`
- **Bin shifting** — Moving all bins up or down sounds inharmonic; it is not a pitch shifter. ELSE's `bin.shift~` can change the shift amount while running and can wrap bins around. Native `lrshift~` has a fixed amount, shifts in the opposite direction for the same sign (positive is left), and fills with zeros. `(source: Part.09-Spectral.Processing/34-Basic/6.Bin.shifting.pd)`
- **Spectral delay** — Put a delay (`ffdelay~`) between `rfft~` and `rifft~`. The delay time must be a whole multiple of the block length, or the bins get scrambled like a bin shift. Because each sample in the block is one bin, a table of delay times read with `tabreceive~` gives every bin its own delay. The patch rounds the table with `rint~` and multiplies by `blocksize~ -ms`. `(source: Part.09-Spectral.Processing/34-Basic/7.Delay/1.Feedforward.pd)`
- **Spectral feedback delay** — Same idea with `comb.rev~` for feedforward and feedback lines, plus a second table that gives each bin its own feedback amount. `(source: Part.09-Spectral.Processing/34-Basic/7.Delay/2.Feedback.pd)`
- **Spectral phaser** — Convert to polar, add a sine LFO (times a depth, scaled by pi) to the phase of every bin, convert back, and sum with the dry signal. A fixed phase offset does not change the sound; a continuously moving one acts like phase modulation and shifts pitch. `(source: Part.09-Spectral.Processing/34-Basic/8.Phaser.pd)`

### 35-Advanced

- **Cross synthesis by FFT** — Take phases from source A (a tonal sound) and magnitudes from source B (speech). B's magnitudes act as a filter on A. `(source: Part.09-Spectral.Processing/35-Advanced/1.Cross.Synthesis/1.Cross.Synthesis.pd)`
- **Cross synthesis without atan2** — Divide A's real and imaginary parts by A's magnitude (so A has amplitude 1 in every bin), then multiply both by B's magnitude. This avoids the polar conversion and is described as a bit more efficient and accurate. `(source: Part.09-Spectral.Processing/35-Advanced/1.Cross.Synthesis/1.Cross.Synthesis.pd)`
- **Morphing** — A simple version crossfades (`xfade~`) between A's own magnitudes and B's, keeping A's phases. ELSE's `morph~` crossfades both magnitudes and phases, so it can cross-synthesize in either direction or morph fully. Its default is amplitudes from B and phases from A. `(source: Part.09-Spectral.Processing/35-Advanced/1.Cross.Synthesis/2.Morph.pd; Part.09-Spectral.Processing/35-Advanced/1.Cross.Synthesis/3.[morph~].pd)`
- **Circular convolution** — Complex-multiply the FFTs of two live signals (Hann windowed) and inverse transform. The result mixes amplitude and phase of both. Order does not matter. `(source: Part.09-Spectral.Processing/35-Advanced/2.Convolution/1.Circular.pd)`
- **Linear convolution reverb, the recipe** — The FFT window must be twice the impulse response length (IR 16384 samples, window 32768), with the second half zero. The patch uses `block~ 32768 2`: overlap 2 and no Hann window. The input is multiplied by a table that zeroes its second half; the overlap of 2 means that half is picked up by the next frame. Divide by the window size. `(source: Part.09-Spectral.Processing/35-Advanced/2.Convolution/2.Linear(Reverb).pd)`
- **Precompute the IR's FFT** — The IR is transformed once and its real and imaginary parts are stored in two tables, read with `tabreceive~` every frame. This avoids repeating the same FFT. `(source: Part.09-Spectral.Processing/35-Advanced/2.Convolution/2.Linear(Reverb).pd)`
- **Convolution output length and latency** — Convolving lists of length 2 and 3 gives 4 values (sum of lengths minus one). A whole-IR FFT means a very large window and clear latency. `(source: Part.09-Spectral.Processing/35-Advanced/2.Convolution/2.Linear(Reverb).pd)`
- **Partitioned convolution** — Cut the IR into short partitions, convolve the input with each one separately, and delay each result by its position. Latency drops to the partition size. The teaching abstraction `conv.abs~` (arguments: partition size, file name) does this with one `clone` instance per partition. `(source: Part.09-Spectral.Processing/35-Advanced/2.Convolution/3.Partitioned.pd; Part.09-Spectral.Processing/35-Advanced/2.Convolution/conv.abs~.pd; Part.09-Spectral.Processing/35-Advanced/2.Convolution/convpartition.pd)`
- **`conv~` is the real object** — ELSE's compiled `conv~` replaces the abstraction and is much cheaper. It is based on William Brent's `convolve~`. It takes an array name for the IR: `[conv~ $0-IR 1024]`. Note that one later patch shows `[conv~ 128 ../files/IR.wav]`, a different argument order; the text does not explain the difference. `(source: Part.09-Spectral.Processing/35-Advanced/2.Convolution/3.Partitioned.pd; Part.10-Filters&Reverb/36-Filters(Advanced)/2.Filter.Response/4.IR.Convolution.pd)`
- **Any sound can be the "IR"** — The examples use a clap, a voice sample and a chaotic oscillator. Since convolution is commutative, either input can be thought of as the IR. The text warns it can get very loud. `(source: Part.09-Spectral.Processing/35-Advanced/2.Convolution/3.Partitioned.pd)`
- **"Phase vocoder" is an umbrella term** — The text says it names many spectral processes, and that SuperCollider's FFT objects all start with `PV_` for that reason. `(source: Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/1.TimeStretch-PitchShift/1.Polar.pd)`
- **Phase vocoder time-stretch and pitch-shift, polar form** — Fixed window 2048, overlap 4. Each block, read two grains from the buffer: a "front" one and a "back" one that sits one hop earlier. Transposition changes how many samples a grain reads (and so the hop between front and back); speed changes how far the read point steps each block. Then per bin: output phase = previous output phase + (front phase − back phase), with the front grain's magnitude. The previous output phase is kept in a table through `tabsend~` / `tabreceive~`. `(source: Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/1.TimeStretch-PitchShift/1.Polar.pd)`
- **Why phase accumulation is needed** — When the step through the file is not the same as the hop between grains, neighbouring grains no longer line up and their phases jump. Accumulating the measured phase advance removes the jumps. `(source: Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/1.TimeStretch-PitchShift/1.Polar.pd)`
- **Phase accumulation without computing phases** — Phase difference = complex division of front by back, after scaling the back frame to magnitude 1 (so the front's magnitudes are untouched and no division normalization is needed). Adding to the last output's phase = complex multiplication by the last output, also scaled to magnitude 1. Guard the 0/0 case: if both parts are zero, set the real part to 1. `(source: Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/1.TimeStretch-PitchShift/2.Cartesian.[pvoc.player~].pd)`
- **Phase locking** — Puckette's "phase-locked" method. For each bin, add in the neighbouring bins on each side (`lrshift~ 1` and `lrshift~ -1`), which forces neighbours to stay in phase. The order of operations changes: first divide the last output by the back frame, apply the lock, then multiply by the front frame. It is more stable at very slow speeds and when frozen at speed 0. Needs the cartesian form. `(source: Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/1.TimeStretch-PitchShift/2.Cartesian.[pvoc.player~].pd)`
- **`pvoc.player~` and `pvoc.live~`** — ELSE's `pvoc.player~` is based on the buffer patch above (which equals Pd's I07.phase.vocoder example). `pvoc.live~` is the same on a live ring buffer, shown as `[pvoc.live~ 6000]`. `(source: Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/1.TimeStretch-PitchShift/2.Cartesian.[pvoc.player~].pd; Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/1.TimeStretch-PitchShift/4.Ring.Buffer(Shift-Stretch).pd)`
- **Trap: overlap changes time inside the subpatch** — In Pd an overlapped subpatch runs at a higher sample rate under the hood. Delay objects and `vline~` therefore behave differently, and the patch divides their times by the overlap (4) in several places. `(source: Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/1.TimeStretch-PitchShift/3.Ring-Buffer-Pitch.Shift.pd)`
- **`brane.m~`** — A sampler with two phase-vocoder players that share one speed, so it works as a two-voice harmonizer. It is an extra MERDA module. `(source: Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/1.TimeStretch-PitchShift/5.[brane.m~].pd)`
- **Resynthesis with tracked partials** — `[sigmund~ -npts 2048 -hop 512 -npeak 50 tracks]` outputs one list per partial: track number, frequency, amplitude, flag. `clone 50 oscillator` routes by track number. The flag is −1 (track ending), 0 (continuing) or 1 (new), and switches each oscillator on or off. Pitch shifting is just a multiply on each oscillator's frequency. `(source: Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/2.Resynthesis[sigmund~].pd; Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/oscillator.pd)`
- **Freeze by stopping the data** — Close a gate (`spigot`) on the `sigmund~` output and the oscillator bank holds the last snapshot. ELSE's `freeze~` is based on this. `(source: Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/3.[freeze~].pd)`
- **Phase-vocoder freeze** — Write the input into two tables as front and back grains (the back one is the input delayed by one hop, `ffdelay~ 512`) and run the phase accumulation on them, which is a time stretch at speed 0. The frozen output is always running; freeze and unfreeze are a crossfade. ELSE's `pvoc.freeze~` is based on this. `(source: Part.09-Spectral.Processing/35-Advanced/3.Phase.Vocoder/4.[pvoc.freeze~].pd)`

## Part 10 — Advanced filters and reverberation

### 36-Filters (Advanced)

- **`fexpr~` for difference equations** — `$x1[-1]` is the left input one sample ago; `$y1[-1]` is the first output one sample ago. So `fexpr~ $x1[0] + $x2[0] * $y1[-1]` is a one-pole filter with a signal-rate coefficient. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/1.Basic.Theory/2.[fexpr~].diference.equations.pd)`
- **Feedback coefficient limit** — A one-sample feedback of exactly 1 never decays, and anything above 1 blows up fast. The patch limits it to 0.999. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/1.Basic.Theory/3.FIR.IIR.pd)`
- **Order and slope** — First order rolls off 6 dB per octave, second 12, fourth 24. Filters in series add their orders. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/1.Basic.Theory/4.Order.pd)`
- **Pd `biquad~` list order** — Five numbers in this order: `fb1 fb2 ff0 ff1 ff2` (the tutorial's `b1 b2 a0 a1 a2`). The equation is `y = a0·x + a1·x[-1] + a2·x[-2] + b1·y[-1] + b2·y[-2]`, with feedback added. Check order and sign before moving coefficients to another environment. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/1.Basic.Theory/5.[biquad~].pd)`
- **Poles and zeros in one line** — Feedback coefficients are poles (resonances); feedforward coefficients are zeros (anti-resonances). The input gain `a0` is not a zero. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/1.Basic.Theory/7.Poles.Zeros.pd)`
- **`lop~` exactly** — `y = a·x + (1 − a)·y[-1]`, where `a` is the cutoff in radians per sample, clipped to 0..1. Because of the clip, the highest usable cutoff is about 7 kHz at 44.1 kHz. As a biquad list: `(1−a) 0 a 0 0`. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/1.Basic.Theory/8.filter-examples/1.[lop~].pd)`
- **`hip~` exactly** — One pole and one zero: `y = x − x[-1] + a·y[-1]`. The zero is always at 1; the pole coefficient is 1 minus the cutoff in radians per sample (clipped 0..1). As a biquad list: `a 0 1 -1 0`. The zero is −1 in the list because `biquad~` adds where `rzero~` subtracts. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/1.Basic.Theory/8.filter-examples/2.[hip~].pd)`
- **`lop2~` exactly** — One pole and one zero: `y = a·x + a·x[-1] + b·y[-1]`, with `a` = (radians per sample)/2. The radians value is clipped at 2, so the top cutoff is about 15 kHz. The comment says `b = 1 − a`, but the patch's own `expr 1 - $f1; $f1/2` computes `b` as 1 minus the unhalved radians value; the text does not resolve this. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/1.Basic.Theory/8.filter-examples/3.[lop2~].pd; Part.10-Filters&Reverb/36-Filters(Advanced)/2.Filter.Response/2.[biplot].pd)`
- **Frequency response from the equation** — Replace `z^-1` by `cos(w) − i·sin(w)`, where `w` is frequency in radians per sample (`z^-2` uses `2w`). For a one-pole `1/(1 − a·z^-1)`: real = `1 − a·cos(w)`, imaginary = `−a·sin(w)`; convert to polar; the gain is 1 over that amplitude and the phase is its negative. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/2.Filter.Response/1.Filter.Response.pd)`
- **Plotting tools** — ELSE's `biplot` draws amplitude and phase response from a biquad coefficient list. `biquads~` is a cascade of biquads, and `biplot` can plot the whole cascade. `zbiplot` draws the poles and zeros on the z-plane, from coefficients or from pole/zero coordinates. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/2.Filter.Response/2.[biplot].pd; Part.10-Filters&Reverb/36-Filters(Advanced)/2.Filter.Response/3.[biquads~].pd; Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/1.Z.Plane.[zbiplot].pd)`
- **Measure any filter with an impulse** — Send one impulse (`float2imp~`) through the filter and record the output. The FFT of that recording is the filter's amplitude and phase response. Convolving a signal with the recording (`conv~`) reproduces the filter. The text uses this to argue that filters and reverbs are the same kind of thing. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/2.Filter.Response/4.IR.Convolution.pd)`
- **Reading the z-plane** — Angle is frequency (0 at 0 Hz, half a turn at Nyquist); distance from the centre is strength. For `lop~` the pole sits on the 0 Hz axis and moves toward 1, boosting lows, while the gain coefficient pulls the level back down. For `hip~` a zero at 1 removes 0 Hz and the pole wins back the frequencies above the cutoff. Input gain is not shown on the plane. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/1.Z.Plane.[zbiplot].pd)`
- **Pd's raw filters as equations** — `rpole~`: `y = x + a·y[-1]`. `rzero~`: `y = x − a·x[-1]`. `rzero_rev~`: `y = −a·x + x[-1]`. `cpole~`, `czero~` and `czero_rev~` are the complex versions, with two inputs and two outputs. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/2.Raw.Filters.pd)`
- **`bp~` is two conjugate poles** — `y = g·x + a1·y[-1] + a2·y[-2]`. The poles come from the quadratic formula on the feedback coefficients; when `a1² + 4·a2` is negative they are a complex pair. It can be built from two `cpole~` objects, or a `biquad~` with the two zero slots set to 0. Q sets the pole radius and the gain keeps the peak at 0 dB. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/3.[bp~]-1.pd; Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/4.[bp~]-2.[coeff2pz].pd)`
- **`coeff2pz` and `pz2coeff`** — ELSE objects that convert biquad coefficients to poles, zeros and overall gain, and back. To find a pole's frequency: convert its (re, im) to polar and turn the angle from radians per sample into Hz (`rad2hz`). `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/4.[bp~]-2.[coeff2pz].pd; Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/8.Poles.Zeros.[pz2coeff].pd)`
- **`vcf~` cannot be a biquad** — It is one complex pole, not a conjugate pair, so no `biquad~` reproduces it. It is `cpole~` with: `y1 = x1 + ar·y1[-1] − ai·y2[-1]`, `y2 = x2 + ai·y1[-1] + ar·y2[-1]`. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/5.[vcf~].pd)`
- **`resonator2~`** — Also one complex pole. The coefficient is simply (cos w, sin w) times a radius, where the radius comes from a ring time (t60 in ms) instead of Q. There is no gain compensation. Hit with an impulse, the left outlet rings as a cosine and the right as a sine. It is meant to be excited by impulses, not fed a steady sound. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/6.[resonator2~].pd)`
- **Cookbook biquad formulas, in the tutorial's naming** — Based on Robert Bristow-Johnson's EQ cookbook. For all types: `alphaQ = sin(w)/(2Q)`. Lowpass: `b0 = 1 + alphaQ`, `b1 = 2cos(w)/b0`, `b2 = (alphaQ − 1)/b0`, `a0 = a2 = (1 − cos w)/(2·b0)`, `a1 = (1 − cos w)/b0`. Highpass is the same with `(1 + cos w)` and a negative `a1`. Bandpass: `a0 = alphaQ/b0`, `a1 = 0`, `a2 = −alphaQ/b0`. The "resonant" type is bandpass with `a0` and `a2` multiplied by Q. The patch also lists notch, peak, allpass and both shelves. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/7.[bicoeff].EQCookbook..pd)`
- **`bicoeff` / `bicoeff2` and the single-filter objects** — `bicoeff2` makes a coefficient list from type, frequency, Q and gain, for example `[bicoeff2 eq 500 10 24]` or `[bicoeff2 lowpass 500 10]`. Types: lowpass, highpass, bandpass, bandstop, resonant, allpass, eq, lowshelf, highshelf. ELSE also has one object per type (`lowpass~`, `highpass~`, `resonant~`, `bandstop~`, `eq~`, `lowshelf~`, `highshelf~`, `allpass.2nd~`) that take signal-rate parameters. Only `eq~`, `lowshelf~` and `highshelf~` have a gain input. Shelves take a slope from 0 to 1 instead of Q. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/7.[bicoeff].EQCookbook..pd)`
- **Filter types as pole/zero layouts** — Resonant lowpass: both zeros at −1 plus a conjugate pole pair. Resonant highpass: zeros at 1. Bandpass: one zero at −1 and one at 1. Peak or dip: poles and zeros at the same angle; it is a peak when the poles are farther out than the zeros. Each still needs a gain adjustment. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/3.Z-Plane/8.Poles.Zeros.[pz2coeff].pd)`
- **First-order allpass** — `y = −a·x + x[-1] + a·y[-1]`. In Pd it is `rzero_rev~` followed by `rpole~` with the same coefficient. Amplitude is untouched; phase goes from 0° at 0 Hz to 180° at Nyquist, and the coefficient sets how the curve bends. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/4.Allpass.Phaser/1.Allpass.pd)`
- **Second-order allpass makes a notch** — `allpass.2nd~` turns the phase through a full 360°. Its centre frequency is where the shift is 180°. Adding the filtered signal to the dry signal cancels there, which gives a band-stop. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/4.Allpass.Phaser/2.[allpass.2nd~].pd)`
- **What is inside `hilbert~`** — Two branches, each a pair of `biquad~` allpasses in series (so fourth order each), tuned so the two outputs stay 90° apart. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/4.Allpass.Phaser/3.[hilbert~].pd)`
- **`allpass.filt~`** — ELSE abstraction that stacks `allpass.2nd~` stages. The order must be even, the maximum is 64, and it can only be set when the object is created. Summed with the dry signal, order N gives N/2 notches (order 8 gives 4). `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/4.Allpass.Phaser/4.[allpass.filt~].pd)`
- **Phaser recipe** — A chain of first-order allpasses (`rzero_rev~` + `rpole~`) all sharing one coefficient, summed with the input. A slow triangle LFO (`tri~ 0.1`) rescaled to 0.62..0.98 sweeps the coefficient. The stereo version uses 16 stages on one side and 14 on the other. One variant also sums the output of every stage and tames the level with `drive~`. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/4.Allpass.Phaser/5.Phaser.pd)`
- **`phaser~`** — ELSE abstraction built on `allpass.filt~`; the argument is the number of stages (`phaser~ 12`), with a `wet` message. `phaser.m~` is the MERDA version, fixed at 6 stages with a dry/wet knob. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/4.Allpass.Phaser/6.[phaser~].pd)`
- **t60 and bandwidth** — A resonator's ring time is given as t60: the time to fall 60 dB after being hit. The patch converts between bandwidth in Hz and t60 in seconds with the same formula both ways: `log(1000) / (value × pi)`. `resonator~` takes frequency and t60 in ms (`[resonator~ 1000 3000]`) and has `lop`, `bp` and `hip` modes, bandpass by default. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/5.Resonators/1.[resonator~].pd)`
- **Damped oscillators and banks** — `damp.osc~` is `resonator2~` reshaped to act like an oscillator. `resonbank~` is a bank of `resonator~` and `resonbank2~` a bank of `resonator2~`; both take flags with lists, as in `[resonbank~ -freq 220 -ratio 1 2 2.803 … -decay 1000 205 … -amp 1 0.044 …]`. `bpbank~` is a bank of `bandpass~` filters that takes absolute frequencies: `[bpbank~ -freq 200 500 900 1700 -q 1.5 5 20 9 -amp 2 1.5 2 1]`. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/5.Resonators/2.[resonator2~].[damp.osc~].pd; Part.10-Filters&Reverb/36-Filters(Advanced)/5.Resonators/3.Resonator.banks.pd)`
- **Comb filter and its decay formula** — `comb.filt~`: `y = x + a·x[n−D] + a·y[n−D]`, with D the period of the frequency (1000/Hz in ms). From a ring time: `a = exp(log(0.001) × D / t60)`. The feedback makes the peaks and the feedforward makes the dips. Trap: with a fixed gain instead of t60, the ring time changes with pitch. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/5.Resonators/4.[comb.filt~].pd)`
- **Where a moving average puts its zeros** — Averaging 2 samples puts a zero at Nyquist. 3 samples: at 2/3 of Nyquist. 4: at 1/2 and at Nyquist. 5: at 2/5 and 4/5. 6: at 1/3, 2/3 and Nyquist. An even count always has a zero at Nyquist. As biquad lists: `0 0 0.5 0.5 0` (2 samples) and `0 0 0.333333 0.333333 0.333333` (3 samples). ELSE's `mov.avg~` does this (`mov.avg~ -size 20 2`). `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/6.Moving.Average/1.[rzero~].[biquad~].pd; Part.10-Filters&Reverb/36-Filters(Advanced)/6.Moving.Average/2.[mov.avg~].pd; Part.10-Filters&Reverb/36-Filters(Advanced)/1.Basic.Theory/1.Delay.Diagrams.pd)`
- **Butterworth pole angles** — Flat passband, steep fall after the cutoff. Pole angles are fractions of pi/2: 3 poles use 0 and 2/3; 4 poles 1/4 and 3/4; 5 poles 0, 2/5, 4/5; 6 poles 1/6, 3/6, 5/6; 8 poles 1/8, 3/8, 5/8, 7/8. For a lowpass the zeros are at −1. Bessel instead gives the flattest phase, and Chebyshev has ripples. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/7.Butterworth.pd)`
- **Butterworth objects** — ELSE's `lop.bw~` and `hip.bw~` are abstractions built on `biquads~` (shown as `[hip.bw~ 1500 10]`). `brickwall~` is a 10th-order lowpass. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/7.Butterworth.pd)`
- **Lag is a one-pole filter** — `lag~` smooths with a curve, not a straight line. Its time is how long the output takes to get within a small fraction of the target (the text says 0.01%; the formula uses 0.001). Coefficient: `a = exp(log(0.001) / (ms × sr_in_kHz))`, then `y = x + a·(y[-1] − x)`. The same one-pole sits inside ELSE's `decay~` and `adsr~`. With `lop~`, a lag of T ms is roughly a cutoff of 1000/T Hz. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/8.Lag.slew/1.Lag.pd)`
- **`lag2~`** — Separate lag times for rising and falling: pick the up or down coefficient from the sign of (last output − input). Shown as `[lag2~ 125 10]`. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/8.Lag.slew/1.Lag.pd; Part.10-Filters&Reverb/36-Filters(Advanced)/9.[slop~]/3.Lag.pd)`
- **Slew limiting is a straight ramp** — `slew2~` takes a maximum change per second, up and down (`[slew2~ 1 2]`). Per sample: if input minus last output is bigger than the limit, move by the limit; otherwise jump to the target. Divide the per-second limit by the sample rate to get the per-sample one. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/8.Lag.slew/2.[slew~].pd)`
- **`slop~`, the full formula** — A nonlinear one-pole filter by Miller Puckette. With `delta = x − y[-1]`: if `delta > slew_up`, `y = y[-1] + f_up·(delta − slew_up) + f·slew_up`; if `delta < −slew_down`, `y = y[-1] + f_down·(delta + slew_down) − f·slew_down`; else `y = y[-1] + f·delta`. So small changes are filtered at cutoff `f`, and the part of a change beyond the limit is filtered at `f_up` or `f_down`. All three cutoffs are in radians per sample clipped to 1 (about 7.02 kHz at 44.1 kHz). `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/9.[slop~]/1.General.formula.pd)`
- **`slop~` inlets** — The text says the 3rd and 5th inlets set the slew limits and the 4th and 6th set the up and down filtering. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/9.[slop~]/1.General.formula.pd)`
- **`slop~` as a plain lowpass** — Set the limits so high they are never reached (2 is enough, the peak-to-peak range of audio): `[slop~ 0 2 0 2 0]`. Then it is exactly `lop~`. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/9.[slop~]/2.Filter.pd)`
- **`slop~` as an up/down lag** — Set both slew limits to 0. Now only `f_up` and `f_down` act: a `lop~` with one cutoff for rising and another for falling. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/9.[slop~]/3.Lag.pd)`
- **`slop~` as a slew limiter** — Set `f` very high so it clips to 1 (`[slop~ 1e+09]`) and set the up and down cutoffs to 0. The limits are in amplitude per sample, where `slew2~` uses per second. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/9.[slop~]/4.Slew.pd)`
- **`slop~` as a de-jitter (dead band)** — `[slop~ 0 0 1e+09 0 1e+09]`: `f` is 0 and the up and down cutoffs are very high. Changes smaller than the limit are ignored, so the output holds still. Bigger changes pass through minus the limit. This removes small noise riding on a control signal. `(source: Part.10-Filters&Reverb/36-Filters(Advanced)/9.[slop~]/5.Unjitter.pd)`

### 37-Reverberation

- **Convolution reverb check** — `[conv~ $0-IR 2048]` with a church impulse response loaded into an array. Sending it a single impulse should play back the impulse response itself. `(source: Part.10-Filters&Reverb/37-Reverberation/1.Convolution.pd)`
- **Early reflections from feedforward delays only** — A chain of stages. Each stage delays one of two signals, then outputs their sum and their difference (a rotation; the difference is one `-~`). Each stage doubles the number of echoes: 6 stages give 64, 8 stages give 256. Mono in, stereo out, with a gain cut at the end (`/~ 12`, `/~ 16`). `(source: Part.10-Filters&Reverb/37-Reverberation/2.[echo.rev~].pd)`
- **Choosing the delay times** — Never use times that are multiples of each other. The 6-stage example uses Fibonacci numbers with odd fractions added (5.123, 8.437, 13.321, 21.789, 34.987, 55.567 ms). The 8-stage one uses primes (5, 7, 11, 13, 17, 19, 23, 29 ms). `(source: Part.10-Filters&Reverb/37-Reverberation/2.[echo.rev~].pd)`
- **`echo.rev~`** — ELSE abstraction of that patch: first argument is the number of stages, second is room size (`[echo.rev~ 8 1]`). It uses a prime series, and size stretches the delay times. `(source: Part.10-Filters&Reverb/37-Reverberation/2.[echo.rev~].pd)`
- **Feedback delay network, minimum version** — Four delay lines (60, 71.9345, 86.7545 and 95.945 ms). Their outputs are mixed through sums and differences before being written back. The stereo input goes into two of the four lines. The mixing has a gain of 2, so the feedback amount is divided by 2. The early-reflection chain feeds the network. This is Puckette's G08.reverb example. `(source: Part.10-Filters&Reverb/37-Reverberation/3.FDN/1.FDN.pd)`
- **How many lines** — The text says a feedback delay network usually has 4 to 16 lines, and that this replaces the thousands of delays a literal room model would need. `(source: Part.10-Filters&Reverb/37-Reverberation/3.FDN/1.FDN.pd)`
- **Vanilla `rev2~` and `rev3~`** — `rev2~` is the network above plus a lowpass in the feedback loop for high-frequency damping. Four arguments: output level, decay, crossover frequency, damping (`[rev2~ 100 90 3000 20]`). `rev3~` is the same idea with 16 delay lines. `(source: Part.10-Filters&Reverb/37-Reverberation/3.FDN/2.[rev2~].[rev3~].pd)`
- **`mono.rev~` and `stereo.rev~`** — ELSE's `mono.rev~` is like `rev3~` plus a `size` control that changes the delay lengths. A typical size is 0.5; small sizes sound like comb filtering and large ones like echoes. Trap: moving size while sound plays causes pitch-shift artifacts. `stereo.rev~` has two independent channels, each with its own matrix. `(source: Part.10-Filters&Reverb/37-Reverberation/3.FDN/3.[mono.rev~].pd; Part.10-Filters&Reverb/37-Reverberation/3.FDN/4.[stereo.rev~].pd)`
- **`giga.rev~`** — ELSE abstraction of the open-source "gigaverb": feedforward early reflections into a feedback delay network. The text calls it a building block, not a friendly finished reverb. Flags shown: `-size 40 -decay 4 -damp 0.9 -bw 0.75 -dry 1 -early 0.795 -late 0.04`. `(source: Part.10-Filters&Reverb/37-Reverberation/3.FDN/5.[giga.rev~].pd)`
- **`fdn.rev~`** — ELSE's compiled low-level network for experiments: the number of delay lines and their lengths can be set. Shown as `[fdn.rev~ -time 4 -damping 50]`. `(source: Part.10-Filters&Reverb/37-Reverberation/3.FDN/6.[fdn.rev~].pd)`
- **Allpass reverberator** — Same shape as the first-order allpass, but with a delay of d samples instead of one: `y = −g·x + x[n−d] + g·y[n−d]`. A steady sound is not coloured, but echo density rises. After the input stops, the ringing is coloured, so drums and noise bursts show it most. ELSE object: `[allpass.rev~ 100 0.8 1]`. Built from native objects it needs a `block~ 1` subpatch. `(source: Part.10-Filters&Reverb/37-Reverberation/4.Allpass/1.[allpass.rev~].pd)`
- **`rev1~`** — Vanilla abstraction: 10 allpass stages in series, with only a decay control. `(source: Part.10-Filters&Reverb/37-Reverberation/4.Allpass/2.[rev1~].pd)`
- **Comb reverberator** — `comb.rev~`: `y = a·x + b·x[n−d] + c·y[n−d]`, with separate input, feedforward and feedback gains and a delay in ms (`[comb.rev~ 100 0.8 0.5 0.9]`). Unlike the allpass it colours the input: noise becomes pitched at the delay period. `comb.filt~` is the same thing with b = c from one decay value and a = 1. `(source: Part.10-Filters&Reverb/37-Reverberation/5.Comb/1.[comb.rev~].pd)`
- **`fbdelay~`** — Only the feedback half: `y = x + a·y[n−d]`. By default its feedback is given as a t60 time; the `-gain` flag switches it to a plain coefficient (`[fbdelay~ -gain 100 0.8]`). `(source: Part.10-Filters&Reverb/37-Reverberation/5.Comb/2.[fbdelay~].pd)`
- **Schroeder/Moorer layouts** — Two classic layouts: allpass reverberators in series (as in `rev1~`); or comb reverberators in parallel feeding allpasses in series. The patch's values: combs `[comb.rev~ 80 1 0 0.7]`, `70 … 0.6`, `50 … 0.5`, `30 … 0.4`, and allpasses of 45 to 95 ms with gains 0.66 to 0.99. The text admits the delay lengths are arbitrary. `(source: Part.10-Filters&Reverb/37-Reverberation/6.Schroeder-Moorer/1.Schroeder-Moorer.pd)`
- **`free.rev~`** — ELSE abstraction of "freeverb": 8 parallel combs into 4 allpass stages. `decay` sets the combs' feedback, `damp` sets an internal lowpass, `width` sets how much the two inputs are mixed (stereo spread), plus `wet`. `(source: Part.10-Filters&Reverb/37-Reverberation/6.Schroeder-Moorer/2.[free.rev~].pd)`
- **`plate.rev~`** — ELSE abstraction of the Dattorro plate reverb, from a patch by Tom Erbe. It combines allpass filters with a feedback network, and modulates some allpasses with LFOs so the tail keeps moving. Mono in, stereo out. `plate.rev.m~` is the MERDA version. `(source: Part.10-Filters&Reverb/37-Reverberation/7.[plate.rev~].[plate.rev.m~].pd)`

## Part 11 — Advanced synthesis

- **`gendyn~`** — ELSE's version of Xenakis' GenDyn stochastic synthesis: a waveform whose breakpoints and reading speed both move by Brownian random walk. Points can be joined with no, linear or cosine interpolation. Besides the original frequency range, it accepts a centre frequency with a bandwidth in cents (`[gendyn~ -bw 100]`). `gendyn.m~` is a simpler MERDA version. `(source: Part.11-Synthesis(Advanced)/38-Stochastic/1.gendyn~.pd)`
- **Modal synthesis recipe** — Describe an object as a list of modes, each with a frequency ratio, an amplitude and a decay time, and hit a bank of resonant filters with a short excitation. The example: a clipped noise burst (`white~ -clip` shaped by `decay~`) into `resonbank~` in its default bandpass mode, with lists `1 2 2.803 3.871 5.074 7.81 10.948 14.421` (ratios), `1000 205 1000 196 339 47 58 47` (t60 in ms) and `1 0.044 0.891 0.0891 0.794 0.1 0.281 0.079` (amplitudes). `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/1.modal/1.introduction.[resonbak~].pd)`
- **Flag name differs between patches** — The ratio list is given as `-partial` in one patch, `-ratio` in its near-duplicate, and `-freq 220 -ratio …` in Part 10. The text does not say which is current. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/1.modal/1.introduction.[resonbak~].pd; Part.11-Synthesis(Advanced)/39-Physical-Modeling/1.modal/1.introduction.pd; Part.10-Filters&Reverb/36-Filters(Advanced)/5.Resonators/3.Resonator.banks.pd)`
- **Where mode values come from** — From the maths of the vibrating shape (a round drumhead follows Bessel functions), or from measuring a recording, for example with `sigmund~`. Where the object is struck changes the amplitudes: the centre of a drum excites the lowest mode more, off-centre excites the higher ones. `plaits~` is named as having a modal engine. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/1.modal/1.introduction.pd)`
- **`resonbank2~` for pitched percussion** — A bank of damped sine oscillators (cosine on the left outlet, sine on the right). The partial list can be ratios times the input frequency, or absolute frequencies with the input as a multiplier. The decay list can likewise be ratios times a decay input: with the same lists, a multiplier of 9000 sounds like a tubular bell or glockenspiel and 1000 like a marimba. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/1.modal/2.[resonbank2~].pd)`
- **Trap: excite `resonbank2~` with impulses only** — Its output is louder than `resonbank~`. The patch drives it with `float2imp~`; noise bursts make it much louder. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/1.modal/2.[resonbank2~].pd)`
- **Four mode sets given** — Partials `1 2 3 4 5 6 7 8` with decays 2000 down to 600 ms; `1 2.756 5.404 8.933 13.34` with amps `1 0.7 0.5 0.3 0.2` and decays 1200 to 400; `1 2.01 2.73 3.8 4.9 5.8 7.2 8.7` with decays 4000 to 1000; `1 1.59 2.14 2.3 2.65 2.92 3.6 4.1` with decays 1000 to 250. The labels "string like, marimba like, bell like, drum/tom like" appear in that same order, but the extracted text does not tie each label to a message, so the pairing is a likely reading, not a certain one. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/1.modal/2.[resonbank2~].pd)`
- **Karplus-Strong, the core idea** — Repeat a short piece of noise once per period and it becomes pitched. In practice: a noise burst one period long into a feedback delay whose time is that period (`1000/Hz` ms, or `sr/Hz` samples). The feedback amount sets the decay. Shown with `[fbdelay~ -gain 25 0.98]`. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/1.Introduction.pd)`
- **Fixed buffer versus live noise** — Reading the same stored noise every time repeats the same grain. Using a live noise input gives a slightly different pluck on each note. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/1.Introduction.pd)`
- **The original algorithm** — The excitation is noise holding only +1 or −1 (`white~ -clip`). Inside the feedback loop sits a two-sample average (`mov.avg~ 2`), a gentle lowpass that makes high partials die first. The text classes it as waveguide synthesis and as a "wavetable modification" method. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/2.Original.Algorithm.pd)`
- **The "blend" control** — At 1 the feedback is normal. At 0 the feedback is negative: polarity flips each pass, which sounds an octave lower and changes the harmonics. Near 0.5 the sign is chosen at random each sample, which turns the sound to noise; this was meant for drum-like sounds. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/2.Original.Algorithm.pd)`
- **High notes need a one-sample block** — The feedback loop should run in a subpatch with `block~ 1`, otherwise very high frequencies (very short delays) cannot be reached. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/2.Original.Algorithm.pd; Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/3.Variations.pd)`
- **Karplus-Strong variations** — Swap the average for `lop~` to get a cutoff control. Hold the excitation open for the note's length to add sustain, with an attack/release fade. Use pink noise (`pink~`) as excitation. Use ELSE's two-pole `lowpass~` in the loop. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/3.Variations.pd)`
- **Trap: filter outside the loop is not Karplus-Strong** — A `comb.filt~` followed by a lowpass looks similar but leaves the filter outside the feedback path, so partials do not darken as they ring. The patch includes it only for comparison. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/3.Variations.pd)`
- **Strummed chords** — Six voices in `clone`, each picking its note by instance number and starting after a random delay (up to 500 ms) with a random velocity. `lop2~` or `lowpass~` with Q 0.5 is the loop filter, and `drive~` is on the output. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/4.Example-1.pd; Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/5.Example-2.pd; Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/karplus-voice-1.pd)`
- **Reaching the parent's `$0` from inside a clone** — Either pass `$0` as an argument to `clone`, or use ELSE's `dollsym` inside the voice to expand the parent's `$0`. Settable receive names then need ELSE's `receiver`. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/5.Example-2.pd; Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/karplus-voice-2.pd)`
- **`pluck~`** — ELSE's Karplus-Strong object. It has its own white noise, is triggered by an impulse, and shapes the noise to one period by itself. Decay is a t60 time in ms. The loop holds a first-order lowpass like `lop2~`; its default cutoff equals the original two-sample average. Shown as `[pluck~ -midi 0 4000 10000]`; a list input triggers it at control rate. `pluck.m~` is the MERDA version. `(source: Part.11-Synthesis(Advanced)/39-Physical-Modeling/2.Karplus-Strong/6.[pluck~].pd)`

## Pd itself — points that came up along the way

Another scan covers Pd vanilla, so these are kept brief.

- `$0` in an object box is a number unique to each patch, used for local names (`[tabplay~ $0-hann]`, `[throw~ $0-voice]`). `(source: Part.04-Control/17-Envelopes/4.Tables/1.Tables.[tabgen].pd)`
- `[clone]` loads N copies of an abstraction and routes a list by its first number to that copy; it is Pd's polyphony container. `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/3.Monophony.Polyphony/2.Polyphonic.pd)`
- Voices use `[switch~]` to turn their own DSP off. (Seen in the voice boxes; the text only says "turn window on/off".) `(source: Part.04-Control/18-MIDI-CV-OSC-Net/1.MIDI/3.Monophony.Polyphony/voice-abs.pd)`
- Some vanilla signal objects take a parameter as control messages only, for example `[bp~]`'s frequency. `(source: Part.04-Control/14-Trigger-LFO-LFNoise/3.LFO.pd)`
- `[expr]` can read arrays by name (`sequencer[i]`), assign to `[value]` variables, and has a `random(lo, hi)` function. `(source: Part.04-Control/19-Sequencing/3.[list].[array].[text].text/2.Array-Sequencer.pd; 20-Stochastic/1.Random.pd)`
- ELSE flag convention: options are typed as `-name` before the positional arguments (`[tempo~ -on 120 100]`, `[adsr~ -lin …]`, `[sh~ -tr]`, `[envgen~ -suspoint 1 -curve 1 …]`). `(source: many, e.g. Part.04-Control/17-Envelopes/2.Classic.Types/03.ASR/2.gate.pd)`
- **Per-subpatch block size and resampling** — `block~` in a subpatch sets that subpatch's block size (`block~ 1` for one-sample feedback) and can run it upsampled (`block~ 64 1 2`). Block sizes are powers of 2 only. `(source: Part.05-Synthesis(Basic)/24-Modulation.Synthesis/2.FM_PM/7.Feedback.Cross.Modulation/1.Feedback.pd; Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/1.Play/4.Upsampling.pd; Part.07-Sampling.Delay.Granulation/31-Granulation/2.Pitch.Shift&Time-Stretch/1.Buffer(array)/1.Strech.shift.pd)`
- **DSP order is set by cords** — There is no setting for which object runs first. The tutorial forces order with dummy signal cords between subpatches, in every delay patch where it matters. `(source: Part.07-Sampling.Delay.Granulation/30-Delay(Ring-Buffer)/1.Delay/4.Execution.Order.pd)`
- **`clone` for copies of a voice** — Additive voices, vocoder bands, sampler voices and grains are all an abstraction loaded N times by `clone`, addressed with messages such as `all <msg>` or `<n> <msg>`. `(source: Part.05-Synthesis(Basic)/23-Additive.Synthesis/2.Example2.pd; Part.06-Filters(Basic)/28-Filter.FX/2.Multiband-Processing/5.Vocoder/2.Vocoder.pd)`
- **Multichannel signals** — One cord can carry several channels; ELSE oscillators, banks, `fold~`, `wrap2~`, players and recorders use this. `(source: Part.05-Synthesis(Basic)/23-Additive.Synthesis/7.[sine~].and.others.pd)`
- **32-bit float limit** — See "Long-file precision limit" above. The text says 64-bit Pd builds remove it. `(source: Part.07-Sampling.Delay.Granulation/29-Sampling(buffer)/2.Large.samples.issue.pd)`

### Data structures (Part 12)

- **What they are** — A data structure is a record with named fields that Pd can also draw. Four field types: float, symbol, text, array. Uses named: showing data, graphical scores that drive a patch, and home-made GUI objects. `(source: Part.12-Advanced.Pd/40-Data.Structures/1.Introduction.pd)`
- **Three places for three jobs** — One subpatch holds the template: one `struct` (only one per window) plus the drawing instructions. Another subpatch is the canvas where instances appear. `pointer` (with `traverse pd-<name>` then `bang`) finds the canvas, and `append` adds an instance there. `(source: Part.12-Advanced.Pd/40-Data.Structures/1.Introduction.pd)`
- **`x` and `y` are special** — Fields named `x` and `y` are the instance's position. An instance can only be dragged if they are declared. The whole canvas can be saved to and reloaded from a text file. `(source: Part.12-Advanced.Pd/40-Data.Structures/1.Introduction.pd)`
- **Reading and writing fields** — `get` and `set` take a pointer plus the template and field names. Symbols need their own `set -symbol …`; one `set` cannot handle floats and symbols together, and `append` cannot set a symbol. `(source: Part.12-Advanced.Pd/40-Data.Structures/2.[get]-[set].pd; Part.12-Advanced.Pd/40-Data.Structures/5.Symbol.pd)`
- **Drawing instructions** — `drawpolygon`, `filledpolygon`, `drawcurve`, `filledcurve` (bezier) for shapes; `drawnumber`, `drawsymbol`, `drawtext` for values (the text says these three are one object under three names). A colour argument can be a field name, so changing the field changes the colour. `(source: Part.12-Advanced.Pd/40-Data.Structures/3.Polygons.pd; Part.12-Advanced.Pd/40-Data.Structures/4.Curved-Polygons.pd; Part.12-Advanced.Pd/40-Data.Structures/5.Symbol.pd; Part.12-Advanced.Pd/40-Data.Structures/6.Text.pd)`
- **Arrays inside a structure** — `plot` draws an array field. A new array has one element; `setsize` / `getsize` or `array size -s …` change and read its size. Elements can have their own template with `x`, `y`, `w` (line width) or any other field, including another array. `element` gives a pointer to one element. `(source: Part.12-Advanced.Pd/40-Data.Structures/7.Array/1.Array-1.pd; Part.12-Advanced.Pd/40-Data.Structures/7.Array/3.[element].pd; Part.12-Advanced.Pd/40-Data.Structures/7.Array/7.x-y-w.pd; Part.12-Advanced.Pd/40-Data.Structures/7.Array/8.Other.elements/4.Array.pd)`
- **Traps** — A new subpatch has "Y units per pixel" at −1, which draws arrays upside down; set it to 1. The element template's name must match its subpatch's name. With `plot curve` the real points can sit off the drawn curve and are hard to grab, because there is no jump-on-click. `(source: Part.12-Advanced.Pd/40-Data.Structures/7.Array/1.Array-1.pd; Part.12-Advanced.Pd/40-Data.Structures/7.Array/2.Array-2.pd; Part.12-Advanced.Pd/40-Data.Structures/7.Array/4.Curve.pd)`
- **The full object list** — Templates and drawing: `struct`, `drawpolygon`, `filledpolygon`, `drawcurve`, `filledcurve`, `plot`, `drawnumber`, `drawsymbol`, `drawtext`. Access: `pointer`, `append`, `get`, `set`, `element`, `getsize`, `setsize`, `array`, `text`. `scalar` exists but is called experimental. `(source: Part.12-Advanced.Pd/40-Data.Structures/8.Review.pd)`
