# Tutorial Package Insights — Delicious Tutorials and Jitter Recipes

Patching insights read out of two tutorial packages installed in
`~/Documents/Max 9/Packages/`. Every entry comes from parsing the `.maxpat`
files (boxes, cords and comments, including subpatchers and gen code), not only
the tutorial prose. Object, attribute and message names were checked against
`obj-qlookup.json` and the refpages of the installed Max 9.

Entry shape, as in `scans/cookbook/cookbook_insights.md`:

a bold title, the insight in 1–3 sentences, *Source* (episode or recipe name and the patch path inside the package), and *Why it matters*.

Most of these patches were saved by Max 6 or 7. Where a patch uses an object
or idiom that Max 9 or the repo's binding rules have replaced, the entry says
so. Entries marked **[PROMOTION-CANDIDATE]** could become a rule in
`patching/MAX_PATCHING.md` or a Jitter / MSP reference doc.

Already covered elsewhere, so not repeated here: `adsr~ → thispoly~` voice
muting and `ddg.mono` / `poly` / `poly~` choice (`MAX_PATCHING.md` §
Polyphony), `jit.world` over `jit.gl.render` (`MAX_PATCHING.md` § Jitter),
`@usedstdim` sub-rectangles and per-cell feedback matrices
(`JIT_GEN_PATCHING.md`), `jit.gl.node` as a texture cache and matrix → gen →
matrix trails (`forum_insights.md`), `comb~` as a Karplus-Strong primitive
(`forum_insights.md`).

## Delicious Tutorials (Sam Tarakajian, "Delicious Max")

> **[PROMOTION-CANDIDATE]** **A `tapin~` / `tapout~` feedback loop cannot be shorter than one signal vector, so a delay-line Karplus-Strong string goes flat on high notes.** The `tapout~` refpage: "The minimum delay time that can be used is determined by the current signal vector size." At a vector of 64 samples and 44.1 kHz, the shortest loop is about 1.45 ms, so no note above about 690 Hz plays in tune. Tutorial 1 computes the delay as `mtof → !/ 1000.` (period in ms) and sends it to `tapout~` through `line~`, which is correct only below that limit.
> *Source*: Karplus Strong — `Delicious Tutorials/patchers/01-karplus_strong.maxpat`, voice version `patchers/sjt.karplus_poly.maxpat`.
> *Why it matters*: for a plucked string that must reach high notes, build the loop in `gen~` (per-sample feedback) or lower the signal vector size. Worth a line in the MSP section next to the existing `comb~` note.

> **For a string whose decay time does not depend on pitch, set the loop gain to `pow(0.5, period_ms / halflife_ms)`.** A fixed gain such as 0.99 makes high notes die much faster than low ones, because a short loop passes the gain many more times per second. The patch computes `[expr "pow(0.5, $f1/$f2)"]` from the period and a "half-life" in ms and sends it to the `*~` inside the loop, with `onepole~` in the loop for brightness. The comment reads "This math makes sure that high notes fade at the same rate as low notes."
> *Source*: Karplus Strong — `Delicious Tutorials/patchers/01-karplus_strong.maxpat`.
> *Why it matters*: the same formula applies to any recirculating delay (`comb~`, `tapin~`/`tapout~`, gen~ `delay`) where the operator sets a decay time rather than a raw feedback amount.

> **`adsr~` plus the message `maxsustain <ms>` and then `1` gives a one-shot envelope that releases by itself.** The `adsr~` refpage: `maxsustain` "sets the maximum amount of time that the envelope will remain in the sustain stage", and `maxsustain 0.0` makes a sustainless ADR. The tutorials use it for the noise burst that excites the string (`adsr~ 1 0 1. 1` with `maxsustain <impulse ms>`) and for sequencer steps that never send a note-off.
> *Source*: Karplus Strong — `patchers/01-karplus_strong.maxpat`; Step Sequencer voice — `patchers/02-saw_note.maxpat`.
> *Why it matters*: a trigger-only source (a step sequencer, a drum pad, a `bang`) can drive `adsr~` directly, with no `pipe` or `delay` to generate a note-off.

> **[PROMOTION-CANDIDATE]** **`poly~` remembers the last `target`, so set `target 0` before any message meant for every voice.** The tutorials address one voice with `target N` followed by the message, and broadcast with `target 0`. Every parameter control goes through `[t s b]` (or `[t i b i]`): the right outlet fires `target 0` first, then the left outlet sends the parameter, so a note sent earlier to voice 5 cannot capture it. The `poly~` refpage adds that a message whose first word is itself `target` must be prefixed with `list` to reach the voices.
> *Source*: Step Sequencer — `patchers/02-sequencer.maxpat`; TB-303 device — `patchers/tb-303.amxd`; Pitch Shifting — `patchers/07-pitch_shift.maxpat`; Multicube 40 — `patchers/40-multicube/patchers/main.maxpat`.
> *Why it matters*: a patch that mixes per-voice and all-voice messages silently sends parameter changes to one voice only if `target 0` is not reasserted. Belongs in `MAX_PATCHING.md` § Polyphony.

> **When each row of a grid is its own sound, route rows to fixed `poly~` voices with `target row+1` instead of voice allocation.** The step sequencer reads a `matrixctrl` column (`getcolumn <step>`, values out the right outlet), iterates the cells with `zl iter 1`, and for each lit row sends `target <row+1>` then the note `row+48`. No `poly`, no busy tracking: voice N always plays row N, so a chord is just several voices at once.
> *Source*: Step Sequencer — `patchers/02-sequencer.maxpat` (voice `patchers/02-saw_note.maxpat`).
> *Why it matters*: for drum grids and chord step sequencers, fixed voice-per-row is simpler and more predictable than MIDI-style allocation.

> **A `poly~` voice can compute its own offset from its instance number: `thispoly~` bang gives the index (from 1), and `args` passes per-patch settings into `#1`, `#2`, …** The pitch shifter spreads its delay-line windows by dividing the instance number by the voice count (`loadbang → thispoly~ → [pak f f] → [/ 0.]` added to a shared phasor). The circular sequencer loads one sample file three ways with `poly~ simple-sampler 12 @args jongo 0 96`, where `#1` is the `buffer~` name and `#2` / `#3` the start and end in ms. The refpage documents the word `args` and says it must come last in the box text. Multicube 40 writes each voice's result into row `instance - 1` of a shared matrix.
> *Source*: Pitch Shifting — `patchers/sjt.doppler_poly.maxpat`; Circular Sequencer — `patchers/08-circular-sequencer/08-circle_master.maxpat` with `patchers/simple-sampler.maxpat`; Multicube — `patchers/40-multicube/patchers/polycube.maxpat`.
> *Why it matters*: per-voice variation (phase spread, detune, matrix row) needs no messages from the parent, and one abstraction serves several `poly~` boxes with different settings.

> **A monophonic synth with glide: `borax` counts held notes, and a count above 1 turns the glide on.** `borax`'s third outlet is "Number of Notes Currently Active". The patch packs that count with pitch and velocity, sends `[> 1] → [* 125.]` as the ramp time, and packs it with `mtof` into `line~ → saw~`. `poly 1 1` (one voice, voice steal) plus `stripnote` makes a new note replace the old one, and `adsr~ @legato 1` keeps the envelope from restarting on overlapping notes. The tutorial's errata says to use `borax`, `poly` and `ddg.mono` instead of the hand-built note tracking shown in the video.
> *Source*: TB-303 — `patchers/06-tb-303/06-tb-303.maxpat`; Wobble Bass — `patchers/10-wobble.maxpat`, `patchers/10-wobble/patchers/WobbleBassRedux.maxpat`; errata in `docs/06tb303.maxtut.xml`.
> *Why it matters*: legato-glide is the defining behavior of an acid or wobble bass, and this is the shortest native way to get it. The voice version uses a `[tosymbol] → [pipe 5] → [fromsymbol]` detour to delay a two-item list; the `pipe` refpage says its arguments set the list length, so a plain `pipe` with one argument per item does the same.

> **[PROMOTION-CANDIDATE]** **To sweep a filter with an envelope or LFO at audio rate, drive `filtercoeff~` with a signal and wire its five outlets into `biquad~`'s five coefficient inlets.** `filtergraph~` outputs coefficients as messages, so it cannot follow an audio-rate envelope. The TB-303 multiplies the `adsr~` signal into the cutoff and feeds `filtercoeff~ lowpass` into two `biquad~` in series for a steeper slope. The wobble bass adds an LFO into `filtercoeff~ bandpass`. It also shows the moving cutoff on screen: `snapshot~ 30 → [edit_freq $1] → filtergraph~` (`edit_freq` is a `filtergraph~` attribute).
> *Source*: TB-303 — `patchers/06-tb-303/06-tb-303.maxpat`; Wobble Bass — `patchers/10-wobble.maxpat`.
> *Why it matters*: the repo's preferred filter row (`biquad~` + `filtergraph~`) covers a static filter. For an envelope-swept or LFO-swept filter, `filtercoeff~` → `biquad~` is the native answer, and `edit_freq` keeps the display honest.

> **Retrigger an LFO on every note by driving `cycle~` from a `phasor~` and sending a phase value to the `phasor~`'s right inlet.** `cycle~`'s right inlet takes phase (0–1), and `phasor~`'s right inlet resets its phase. The wobble bass sends `0.5` to `phasor~` on each note-on (from `stripnote`), so the wobble always starts at the same point in its cycle. The phasor's rate is a tempo-relative value (`phasor~ 4n`, chosen from a `umenu` of `1n`…`32n`) that follows `[tempo $1] → [transport]`.
> *Source*: Wobble Bass — `patchers/10-wobble.maxpat` (comments: "Using a phasor like this, we can set the phase using a message, retriggering the LFO").
> *Why it matters*: a free-running LFO lands at a random phase on each note, which is the usual cause of an uneven wobble.

> **Even harmonics from a square wave: frequency-shift `rect~` up by its own fundamental and blend.** `rect~` has only odd harmonics (f, 3f, 5f…). Sending it through `freqshift~` with the shift set to the same frequency moves every partial up by f, giving 2f, 4f, 6f… A slider crossfades the two (`*~ x` and `*~ (1 - x)`) for an even/odd timbre control.
> *Source*: Wobble Bass — `patchers/10-wobble/patchers/WobbleBassRedux.maxpat` (comments "rect~ provides only odd partials", "shifting up by one fundamental gives us only even partials").
> *Why it matters*: a two-object timbre control for a classic oscillator, where the obvious alternatives are a wavetable or additive synthesis.

> **A loop window over a sound file can live entirely at signal rate: `phasor~ → %~ length → +~ offset → %~ 1. → *~ duration_ms → play~`.** The phasor runs at `1000 / duration_ms` Hz (one pass per file length). `%~` restricts it to the loop length and `+~` shifts the start, both as fractions of the file, and `play~` takes position in ms. Loading uses `buffer~`'s `replace <file>` message, whose right outlet bangs when the read is done; that bang asks `info~` for the file duration. The playhead is shown with `snapshot~ 10 → [line $1] → waveform~`.
> *Source*: Stutter — `patchers/03-stutter.maxpat`.
> *Why it matters*: key presses change loop length and start with sample accuracy and no clicks from message timing. Note: the patch uses the `key` object's second outlet, which the refpage calls "the platform-specific key code" derived from Apple's key codes, so its `sel 18 19 20 …` only works on a Mac. Use the first outlet (the character) or the fourth outlet ("platform-independent key code").

> **[PROMOTION-CANDIDATE]** **An overdub looper: one `count~` drives both `index~` (read) and `poke~` (write) on the same `buffer~`, and the write input sums the mic with what was just read.** Two cords into `poke~`'s left inlet add the live input to the `index~` output, so each pass layers on top. The errata explains the reader: `index~` ("no interpolation") replaced `play~` because interpolating while writing the same buffer smears. The loop length comes from `dspstate~`'s sampling-rate outlet `* 4.` into `count~`'s count limit (four seconds at any rate). A click on each second is `%~ 1000. → delta~ → <~ 0.`, which fires when the ramp wraps. The mic is opened with `key`/`keyup` on space through `[$1 40] → line~` for a 40 ms fade.
> *Source*: Boomerang — `patchers/05-boomerang.maxpat`; errata in `docs/05boomerang.maxtut.xml`.
> *Why it matters*: the canonical record-over-itself structure, plus the rule "read with `index~` when the same buffer is being written."

> **An FFT vocoder needs no polar conversion: multiply the carrier's real and imaginary parts by the modulator's magnitude, `sqrt~(re*re + im*im)`.** `robot_pfft.maxpat` converts both inputs with `cartopol~`, multiplies amplitudes and converts back. `robot_pfft_efficient.maxpat` computes the modulator magnitude directly and scales the carrier's `fftin~` pair, with the comment "if you scale x and y by the same amount then you've effectively scaled the amplitude without changing phase." The parent patch also switches the carrier to noise for consonants: `zerox~ → >~ 8 → +~ 1 → selector~`. The `zerox~` refpage says its count is "per signal vector", so that threshold of 8 is tied to the vector size.
> *Source*: Vocoder — `patchers/04-vocoder.maxpat`, `patchers/robot_pfft.maxpat`, `patchers/robot_pfft_efficient.maxpat`.
> *Why it matters*: half the objects per bin, and a voiced/unvoiced switch that makes the robot voice intelligible. Retune the zero-crossing threshold if the vector size changes.

> **`vectral~` is the per-bin smoother inside `pfft~`: wire `fftin~`'s bin-index outlet to its left and middle inlets and a value to its right inlet.** With `slide <up> <down>`, each bin's magnitude slides across frames, which smears or freezes a spectrum. Its vector size must equal the frame size, so the patches send `fftinfo~`'s size as `size $1`. The spectral gate compares each bin's amplitude with `<~ threshold`, smooths that 0/1 mask with `vectral~`, and sends the passed part to `fftout~ 1` and the rejected part (mask through `!-~ 1.`) to `fftout~ 2`.
> *Source*: Pfft, your friend — `patchers/12-pfft/patchers/sjt.freq_amp_slide.maxpat`, `sjt.freq_gate.maxpat`, `sjt.freq_range.maxpat`.
> *Why it matters*: spectral smoothing, gating and band isolation are one or two objects per bin once `vectral~` is wired this way.

> **A delay-line pitch shifter is a `phasor~` sweeping `tapout~`'s delay under a raised-cosine window, with several overlapping copies.** The phasor frequency is `(1 - ratio) * 1000 / window_ms`; its ramp times the window length is the delay; `cos~` of `(phase - 0.5) / 2` fades each copy to silence where the delay jumps. Each copy lives in a `poly~` voice with a different phase offset, and a `voices $1` message changes how many overlap. Max 9 also ships `pitchshift~` and `retune~` (both "Ztx-based" in the registry), which do the whole job in one object.
> *Source*: Pitch Shifting — `patchers/07-pitch_shift.maxpat`, `patchers/sjt.doppler_poly.maxpat`.
> *Why it matters*: use `pitchshift~` for a pitch shifter in a patch; build the delay version when the point is to teach how windowed delay-line shifting works or to modulate the window itself.

> **[PROMOTION-CANDIDATE]** **A scripting object tracked only in a JavaScript variable leaks when the script reloads; give every scripted box a `varname` and delete by name.** `circseq.js` creates toggles with `patcher.newobject` and names them `toggle0…`, then removes them with `getnamed`. The `funnel` it creates is kept only in `var myFunnel`. When `@autowatch 1` recompiles the script, that variable resets, the old funnel is never removed, and the saved patch carries seven orphan `funnel` boxes. The script also wires with `hiddenconnect`, which the repo's *Never Hide Patchcords or Boxes* rule forbids; the Patcher API also has `connect`.
> *Source*: Circular Sequencer — `patchers/08-circular-sequencer/circseq.js` and the saved `circle_sequencer.maxpat`.
> *Why it matters*: any `v8` or `js` code that builds patch contents must find its own objects again after a reload. Outdated here: the patch uses `js` (registry: "Legacy Engine"); the repo prefers `v8`.

> **A message into a `bpatcher`'s inlet reaches the patch inside it, not the box. To scroll the view, send `script sendbox <varname> offset <x> <y>` to `thispatcher`.** The `thispatcher` refpage documents `script sendbox <variable-name> <message>`, and the `bpatcher` refpage documents `offset`. The tutorial doc spells out the trap: "you can't control the bpatcher with messages the same way you can other objects, since the inlets of the bpatcher are connected to the objects inside of it."
> *Source*: Bpatcher — `patchers/09-bpatcher.maxpat`; `docs/09bpatcher.maxtut.xml`.
> *Why it matters*: complements the existing `sendbox` pitfall in `MAX_PATCHING.md`, which covers ordinary objects; a bpatcher has no inlet of its own to receive it.

> **A CC mapping table: a `coll` of `<cc> <parameter> <min> <max>` lines feeding one `pattr` whose target is set at runtime with `bindto <name>`.** On each control change, the CC number looks up its line, `scale 0 127 <min> <max>` maps the value, `bindto $1` points the `pattr` at the named control, and the value goes in. The `pattr` refpage documents a double-colon path for binding to an attribute (`object::attribute`), which the patch uses to read each dial's `size` and `min`. One mapping patch then serves every control.
> *Source*: Wobble Bass (redux) — `patchers/10-wobble/patchers/WobbleBassRedux.maxpat`, `patchers/10-wobble/data/mappings.txt`.
> *Why it matters*: a data-driven MIDI map instead of one `ctlin` chain per knob. Conflicts: the patch uses `dial` (repo prefers `live.dial`) and puts `#0-` in scripting names, which was not verified here.

> **Percussion envelopes from `function` → `line~` → `scale~` with an exponent.** A `function` drawn per parameter outputs a `line~`-ready list when banged (refpage: "formatted for use by the line~ object"). `scale~ 0. 1. 40. 220. 2.` bends each ramp into a curve and maps it to a cutoff, amplitude or drive. The kick layers `noise~` and two detuned `saw~` through `reson~`, each with its own drawn pitch sweep, and sends an envelope into `overdrive~`'s drive. One `s #0trigger` bangs every `function`. The Autechre chirp does the same with `curve~` (`3000, 200 50` with curve −0.9) into `cycle~`.
> *Source*: Kick Drum Synthesis — `patchers/20-kick/kick.maxpat`; Faux Autechre — `patchers/14-faux_autechre/patchers/autechre_chrip.maxpat`.
> *Why it matters*: drawn envelopes the operator can see and edit, with exponential shape from one argument, instead of `line~` segment lists typed into message boxes.

> **Video to sound: collapse each video column to one value and play the row as a wavetable.** `jit.grab @type float32` → `jit.rgb2luma` → `jit.dimop @op avg @step 1 240` (averages each 240-pixel column) → a 320-cell matrix → `jit.normalize` → `jit.map @map 0. 1. -1. 1.` → `jit.buffer~ jitbuf 15 1`. `jit.buffer~` (refpage: "Access an MSP buffer~ in matrix form") writes the matrix into a `buffer~` that audio objects read. The patch reads it with `phasor~ 100 → *~ 320. → sampstoms~ → play~`. In Max 9, `wave~` does the same from the phasor directly (refpage: "The output of a phasor~ can be used to control wave~ as an oscillator").
> *Source*: Video to Audio — `patchers/33-videoaudio.maxpat`.
> *Why it matters*: the shortest native bridge from a Jitter matrix to an audio wavetable. Use `phasor~ → wave~ <buffer>` rather than the three-object position chain.

> **[PROMOTION-CANDIDATE]** **Animate video parameters with MSP ramps sampled once per frame: `function → line~ → snapshot~`, with the render clock banging the `snapshot~`.** A MIDI note bangs a drawn `function`; `line~` plays it; a `snapshot~` with no interval is banged by the same trigger that renders the frame (`[t b b] → [s readParams]`), and its value sets `saturation` on `jit.brcosa`. Slow `phasor~` LFOs drive `jit.bfg`'s `offset` the same way. Because these are signal objects, audio must be on: tutorial 29 adds `[loadmess 1] → ezdac~`.
> *Source*: Live Visuals — `patchers/27-live_viz.maxpat`; Bespoke Noise — `patchers/29-bespoke.maxpat`; Gantz Graf 1 — `patchers/31-gg_1.maxpat`.
> *Why it matters*: envelopes stay exactly on the frame grid and reuse MSP's envelope tools. The silent failure is audio being off: every sampled value stays frozen. Say so in the patch, and give the operator the DSP control.

> **`jit.matrix @thru 0` is sample-and-hold for matrices: it stores what arrives and outputs only when banged.** The `jit.matrix` refpage: with the thru flag on (default 1), "a matrix is output when another one is received". Cell Pump makes new noise at a slow `speedlim` rate, holds it in `jit.matrix @thru 0 @adapt 1` banged every frame, and smooths the jump with `jit.slide` before adding it to a mesh's z-plane. Video Wax and Live Visuals use `@thru 0` named matrices as the one-frame store in a feedback loop.
> *Source*: Cell Pump — `patchers/25-cellpump.maxpat`; Video Wax — `patchers/30-video_wax.maxpat`; Live Visuals — `patchers/27-live_viz.maxpat`.
> *Why it matters*: decouples "how often a new target appears" from "how often a frame renders", which is what makes random motion look smooth.

> **Move work out of per-voice GL objects: let `poly~` voices animate, write results into a shared matrix, and draw everything with one `jit.gl.multiple`.** Multicube 35 puts a `jit.gl.gridshape @drawto #1` in each of 100 `poly~` voices. By Multicube 40, each voice only runs `jit.anim.drive` into `jit.anim.node`, asks it for `getposition, getrotatexyz`, and writes the answers as `setcell <instance-1> val x y z` into two matrices; one `jit.gl.multiple 3 @glparams position rotatexyz color` then draws 125 cubes. Motion is eased with `jit.anim.drive`'s `moveto x y z <seconds>` and `easefunc cubic` (refpage: "Easing in and out is applied to the movement based on the easefunc attribute").
> *Source*: Gantz Graf Style series — `patchers/35-multicube/patchers/polycube.maxpat` through `patchers/40-multicube/patchers/main.maxpat` and `polycube.maxpat`.
> *Why it matters*: a worked migration from N GL objects to one instanced draw, keeping per-object eased animation. Complements the forum entry on point clouds in `jit.gl.multiple`.

> **Additive synthesis from a drawn spectrum: `oscbank~` takes `set f1 a1 f2 a2 …`.** The `oscbank~` refpage: "The word set, followed by pairs of floating-point values, sets the frequency and amplitude". The patch builds the frequencies with `[vexpr $f1 * $f2 @scalarmode 1]` (fundamental times the list `1 2 … 32`), interleaves them with the `multislider` amplitudes using `zl lace`, and prepends `set`. In the lava-lamp version, physics bodies set the 32 amplitudes: `jit.phys.multiple` → `jit.spill @plane 1` → `scale` → `multislider`.
> *Source*: Lava Lamp — `patchers/26-lava/patchers/26-lava.maxpat` (build steps `lava-1` … `lava-6`).
> *Why it matters*: a one-object additive synth driven by a list, with no `poly~` of sine voices.

> **Hit detection from an accelerometer over OSC: sum the recent change, threshold it, then lock out repeats for 100 ms.** `udpreceive 9000` output goes straight into a plain `route /wii/1/accel/xyz`, since each OSC message arrives with its address as the message selector. `zl stream 3` keeps the last three values, their differences are split into positive and negative sums, and `> 0.25` fires a hit. The lockout is `[t b 0]`: close a `gate`, then `delay 100` sends `1` to reopen it.
> *Source*: Wii Drums — `patchers/11-wii/patchers/11-wii.maxpat` (OSCulator document `other/wii_all.oscd`).
> *Why it matters*: gesture triggers from any sensor stream need a derivative, a threshold and a lockout, or one swing fires ten notes. For exact addresses a plain `route` is enough; the repo's `o.route` preference applies to pattern matching.

> **`urn N` is a shuffle bag: each number once, then a bang from its right outlet to refill with `clear`.** The Japanese-syllables patch plays sound files in random order without repeats: `urn 5` picks an index, and its right outlet bangs `clear` when all five have played. The file list comes from a dropped folder: `dropfile` → `prefix <folder>` into a `umenu`, which the refpage says re-populates "based on the current contents of the specified path". The `urn` refpage warns the order repeats after `clear` unless it also gets `seed 0`.
> *Source*: Learning Japanese — `patchers/38-japanese/patchers/Japanese.maxpat`.
> *Why it matters*: non-repeating random choice without a `coll` and a list-removal chain. For playback itself the repo prefers `playlist~` to `sfplay~` with `open`.

> **What is outdated or will not load in Max 9.** `jit.gl.slab.gauss6x` (Bloom) is not in Max 9's object registry, so that patch opens with a missing object; `jit.gl.pass @fxname bloom-hq` is the current built-in bloom. `jit.boids2d` and `xray.jit.boidsrender` (Boids) and `bonk~` (Bump It) are third-party externals that are not installed; `dada.boids` is installed but was not tested as a replacement. Episodes 16–40 use the `qmetro → [t b b erase] → jit.gl.render` + `jit.window` chain and `jit.qt.grab`; see the Jitter Recipes entry on `jit.world`'s draw outlet for the modern form. `lcd` (Bouncy) is marked "deprecated" in the registry. Faux Autechre's `Autechre_Powmod.maxpat` is a Max 4 patch with nearly every box set hidden, the opposite of the repo's rule. Throughout: `pack`/`pak`/`unpack`, `slider`, `dial`, `gain~` and `js` where the repo now prefers `join`/`unjoin`, `multislider`, `live.dial`, `live.gain~` and `v8`. `docs/` holds real tutorials only for episodes 1–10; every file in `future-docs/` has the Karplus-Strong text as a placeholder body, and `19-2dwave` and `26-lava/lava-0` are empty patches.
> *Source*: package-wide — `Delicious Tutorials/patchers/`, `docs/`, `future-docs/`.
> *Why it matters*: use these patches as technique references, not as templates to copy box for box.

## Jitter Recipes (Andrew Benson)

> **[PROMOTION-CANDIDATE]** **`jit.world`'s middle outlet is the frame clock: send it to `s draw` and let everything that must update each frame listen on `r draw`.** The refpage calls it the "middle-outlet draw bang", sent before rendering by default. The recipes use it to bang feedback matrices, random generators, counters and `jit.gen` state, replacing the old `qmetro → [t b b erase] → jit.gl.render` trio whose middle bang did the same job. `2VideoSynths` also rate-limits a slower event from it with `qlim 1000`.
> *Source*: Particle Rave — `Jitter Recipes/patchers/ParticleRave.maxpat`; 2 Video Synths — `patchers/2VideoSynths.maxpat`; Scene Warp — `patchers/SceneWarp.maxpat`; Debris HD — `patchers/DebrisHD.maxpat`; Tiny Video — `patchers/TinyVideo.maxpat`.
> *Why it matters*: `MAX_PATCHING.md` already prefers `jit.world`, but not how to clock per-frame matrix work from it. This is the one-cord translation of every older render chain, including all of Delicious Tutorials 16–40.

> **A matrix particle system is four operators in a feedback loop: noise velocities, smoothed, added to positions, damped back toward the origin.** Positions live in `jit.matrix soundgrid 4 float32 6` (reset with `setall 0. 0. 0. 1.`). Each frame, `jit.noise 4 float32 6` is centered and scaled (`jit.op @op * * * pass @val 0.1`, then `- - - pass @val 0.05`), smoothed with `jit.slide`, added with `jit.op @op +`, and multiplied by `@val 0.97` ("gravity–lower values draw particles back to origin") before being written back. The recipe doc: "you can easily generate your own particle physics using simple matrix operations."
> *Source*: Particle Rave-a-Delic — `patchers/ParticleRave.maxpat`; `docs/01jrparticlerave.maxtut.xml`.
> *Why it matters*: a complete particle system with no JS and no shader, which keeps working when the count grows from 36 to thousands of cells.

> **[PROMOTION-CANDIDATE]** **`jit.op` takes one operator per plane, so one box can transform x, y and z while passing the fourth plane untouched.** The `jit.op` refpage: "If multiple operators are specified, they are applied on a plane by plane basis." The recipes write `@op * * * pass` and `@op - - - pass`, and Bespoke Noise gives each plane its own decay with `@op * * * * @val 0.9 0.85 0.82 0.89` for colour-shifting trails. To split planes, `jit.unpack 2 @jump 3 1 @offset 0 3` sends planes 0–2 out one outlet and plane 3 out the other; `jit.pack 2 @jump 3 2` joins a 3-plane and a 2-plane matrix.
> *Source*: Particle Rave — `patchers/ParticleRave.maxpat`; Tiny Video — `patchers/TinyVideo.maxpat`; Delicious Tutorials Bespoke Noise — `Delicious Tutorials/patchers/29-bespoke.maxpat`.
> *Why it matters*: removes the usual `jit.unpack` → N × `jit.op` → `jit.pack` chain. The `@jump`/`@offset` split feeds `jit.gl.multiple` its position and scale inputs from one 4-plane matrix.

> **Soft random sprites without image files: tiny noise, upsampled with interpolation, colorized with `jit.charmap`, and masked with an upsampled 4×4 alpha.** `jit.noise 1 char 6 6` into `jit.matrix 4 char 128 128 @interp 1` gives smooth blobs. A second noise matrix upsampled to 256 cells is the `jit.charmap` colour table. A 4×4 mask filled by `jit.fill mask1` (`0 0 0 0 0 255 255 0 …`) and upsampled the same way softens the alpha edge. The result goes to a `jit.gl.texture` used by `jit.gl.gridshape @shape plane` in `jit.gl.multiple`.
> *Source*: Particle Rave — `patchers/ParticleRave.maxpat`, subpatcher `p particle-texture`.
> *Why it matters*: `@interp 1` on an upsampling `jit.matrix` is the cheapest blur and gradient generator in Jitter; a click makes a new sprite palette.

> **Draw into a matrix at audio rate with `jit.poke~`, then let a feedback transform smear the strokes.** `jit.poke~ <matrix> 2 <plane>` writes its left signal into one plane at the x/y given by its other signal inlets (refpage arguments: name, dimension count, plane). Three of them write red, green and blue from `phasor~`, `cycle~` and `rand~` scribbles. Each frame the named matrix passes through `jit.rota` (random `anchor_x`/`anchor_y`, slow `theta`) or `jit.repos @mode 1` (relative offsets from another poked matrix) and back into itself. A mirror is `jit.dimmap @invert 1 0` glued beside the original with `jit.glue @columns 2`.
> *Source*: 2 Video Synths — `patchers/2VideoSynths.maxpat`, subpatchers `p writengine`, `p pokes`, `p bot`, `p bot2`; `docs/02jr2videosynths.maxtut.xml`.
> *Why it matters*: the classic analog-video-synth look from about a dozen MSP objects. Signal generators become drawing gestures with no conversion to messages.

> **[PROMOTION-CANDIDATE]** **Compare a frame with the previous one using only trigger order: `[t l l]` into a two-inlet operator.** The right outlet fires first and sends the new frame into the hot left inlet of `jit.op @op absdiff`, whose right inlet still holds the last frame. The left outlet then stores the new frame in the right inlet for next time. Debris thresholds the difference (`jit.op @op >`, operator chosen from a `umenu`), packs it as alpha with `jit.pack 4`, and `jit.alphablend`s the live image over a held named matrix. The HD version does the same on textures with `jit.gl.pix`, using `jit.gl.slab` as the one-frame texture store.
> *Source*: Debris — `patchers/DebrisClassic.maxpat`, `patchers/DebrisHD.maxpat`; `docs/03jrdebris.maxtut.xml`. Also Delicious Tutorials Video Feedback — `Delicious Tutorials/patchers/22-video_feedback.maxpat`.
> *Why it matters*: frame differencing (motion masks, change detection) needs no extra delay object. The same right-to-left rule gives "current minus previous" for plain numbers.

> **[PROMOTION-CANDIDATE]** **In OpenGL feedback, never render into the texture you are reading; put a `jit.gl.pix` or `jit.gl.slab` in the loop to copy it.** The Scene Warp patch comment: "Both jit.gl.pix and jit.gl.slab do a texture copy, an essential ingredient in OpenGL feedback", and the recipe doc says reading the capture texture directly causes "errors and glitches". The loop is `jit.gl.node @capture 1` (left outlet: the captured texture) → `jit.gl.pix` (hue and contrast shift) → a warped `jit.gl.mesh` drawn inside that same node, behind the live camera plane. Objects join the node through its middle outlet (refpage: "Any objects connected to the jit.gl.node middle outlet are added to the sub-context").
> *Source*: Scene Warp — `patchers/SceneWarp.maxpat`; `docs/05jrscenewarp.maxtut.xml`. Same structure in Delicious Tutorials Video Feedback — `patchers/22-video_feedback.maxpat`.
> *Why it matters*: the forum entries cover matrix feedback and `jit.gl.node` capture separately; the texture-copy step is what makes GPU feedback stable.

> **Draw order with transparency: turn off depth, turn on blending, and number the layers.** Every object in Scene Warp has `@depth_enable 0` and an explicit `@layer` (mesh 1, camera plane 2, nurbs overlay 3), with `@blend_enable 1` where it is see-through. The GL group refpage: in automatic mode, "the layer number determines the rendering order (low to high)". Full-window planes use `@transform_reset 2`; the refpage describes `transform_reset` as a flag that resets the modelview and projection transforms, and the value 2 was not looked up further. Each layer's visibility is toggled with an `automatic $1` message.
> *Source*: Scene Warp — `patchers/SceneWarp.maxpat`; Delicious Tutorials Video Feedback — `patchers/22-video_feedback.maxpat`.
> *Why it matters*: without explicit layers, transparent GL objects composite in no guaranteed order. The forum entry on `@layer` covers a 3D scene with depth on; this is the flat 2D compositing case.

> **Animate a sprite sheet: paste frames into one big matrix with `@usedstdim`, then move each quad's texture coordinates.** `jit.matrix 4 char 1600 1200 @usedstdim 1` receives 100 frames of 160×120 video, each placed by `dstdimstart $1 $2, dstdimend $3 $4` computed from a `counter 0 99` (`% 10` for column, `* 0.1` for row). One `jit.gl.texture` holds the sheet. `jit.gen` builds four vertices per cell of a 40×10, 5-plane matrix (x, y, z plus two texture coordinates) using `cell` modulo 4. A 10×10 frame-index matrix advances with `jit.op @op + @val 1.` and `% @val 100.`, and `jit.gl.mesh @draw_mode quads` draws all 100 animated quads with one texture.
> *Source*: Tiny Video — `patchers/TinyVideo.maxpat`, subpatchers `p gen_quads`, `p animate_frames`; `docs/04jrtinyvideo.maxtut.xml`.
> *Why it matters*: many independently animated video tiles cost one texture upload and one draw call. The same atlas method works for any sprite animation.

> **Per-cell state in a `jit.gen` with two outlets: feed out 2 through a `jit.matrix` back into in 2, and use rare noise to fire sparse events.** In the warp-mesh generators, `noise > 0.992` picks about one cell in 125 per frame, and `mix` with that 0/1 value replaces that cell's stored offset with fresh noise while the rest keep theirs. Out 1 adds the offsets (scaled by `param warp`) to a `snorm` grid, and `jit.slide` smooths it before `prepend ctlmatrix` into `jit.gl.nurbs` or straight into `jit.gl.mesh`.
> *Source*: Scene Warp — `patchers/SceneWarp.maxpat`, subpatchers `p gen-nurbs` and `p gen-warp-mesh`.
> *Why it matters*: `JIT_GEN_PATCHING.md` describes the feedback-matrix pattern in general. The sparse-event trick (`noise > threshold` into `mix`) is how to get occasional, independent jumps per cell without any per-cell timers.

> **Small `jit.gl.pix` recipes: luma key, block pixelation, and hue shift.** Luma is `dot` of the colour with `param lumcoeff 0.299 0.587 0.114 0.`, and `smoothstep` between the two values of `param range 0.3 0.8` turns it into a soft alpha. Pixelation samples at a quantized coordinate: `norm * blocks → floor → / blocks → nearest`, with `blocks` re-randomized from `jit.world`'s draw bang. Hue and saturation shift is `rgb2hsl → + vec(hue, sat) → hsl2rgb`. In gen, a `param` name can also be the argument of an operator box (`[* amp]`, `[pow expo]`, used in Delicious Tutorials Fisheye), and `[>p thresh]` "returns in1 if in1 is greater than in2, else returns zero".
> *Source*: Scene Warp — `patchers/SceneWarp.maxpat`; Debris HD — `patchers/DebrisHD.maxpat`; Delicious Tutorials Fisheye — `patchers/17-fisheye/patchers/17-fisheye.maxpat`, Video Feedback — `patchers/22-video_feedback.maxpat`.
> *Why it matters*: each is three to six operators in a shader, where the matrix versions need several `jit.*` objects and run on the CPU.

> **What is outdated.** `DebrisClassic.maxpat` still uses `jit.qt.grab 640 480`, `metro 33` and `jit.window`; the `jit.qt.grab` refpage in Max 9 now describes `jit.grab`, and `DebrisHD.maxpat` shows the replacement (`jit.grab @output_texture 1` into `jit.gl.pix`, displayed by `jit.world`). The particle recipe still uses `pak` for its velocity scale. The other recipes were rewritten for Max 7 and already use `jit.world`, `jit.gl.node`, `jit.gl.pix` and `jit.grab`, so they are close to current practice. Scene Warp's `jit.world` gets its enable from a toggle; `MAX_PATCHING.md` notes that `jit.world @enable` defaults to 0.
