# How Max's General Approach Differs From Other Tools

Generated by `build_system_differences.py`. Edit the JSON files it names, not this file.

Each tool's column was written from that tool's own documentation; Max's from Max's
userguide and refpages. The comparison and advice lines are written by hand in
`system_differences_notes.json`. Nothing here was run in any of the tools.

## Main differences in approach

1. What makes work happen. Max pushes: an event fires and the message runs down the cords. TouchDesigner pulls: a node computes only when an output asks for it and something it depends on changed. MadMapper, cables.gl and Gem run a frame loop. Isadora pulls from the end of each chain. So in the other tools unwatched work often costs nothing, while in Max it runs until something upstream stops it.
2. What decides order. In Max, several cords from one outlet fire right to left by where their destinations sit on screen. No other tool lets position decide that: Pd uses the order the cords were made, which the patch does not show; TouchDesigner orders by dependency, cables.gl by the trigger graph, MadMapper by its lists. Isadora uses position only where several links meet one input. Only Max and Pd need trigger as the everyday way to say what happens first.
3. Data and timing. In Max one message is both the data and the moment, and hot and cold inlets decide which inputs act. cables.gl puts data and 'run now' on two different kinds of cable. In TouchDesigner a wire carries no data at all; it only says where to fetch it.
4. What a file keeps. Max and Pd save the structure of a patch, not its current values, so every Max patch needs a storage choice. TouchDesigner, MadMapper, Isadora and cables.gl save every setting's value as part of the file, and a reopened project looks as it did.
5. Settings as parameters. In TouchDesigner, MadMapper, Isadora and cables.gl every setting is a named parameter with a range and a control. In Max that layer is opt-in: attributes everywhere, Parameter Mode on top for the objects that need it. Pd has none. Only TouchDesigner lets a setting be an expression, an export from a channel, or a two-way binding.
6. Names. Max and Pd names are global unless a prefix makes them local. TouchDesigner names are paths in a hierarchy, and every reference is drawn as a line. Isadora keeps each Scene sealed, with numbered channels between them. MadMapper's names form one tree that is also the OSC address of every parameter.
7. The shape of a show. Isadora and MadMapper build scenes, cues and transitions into the program. Max, TouchDesigner, cables.gl and Pd build them out of ordinary parts. A Max theatre or installation patch has to design its own scene layer.
8. Rendering. Jitter joins objects to a named context and orders them with depth testing or a layer number on each object. cables.gl and Gem treat the chain as a render tree: a transform or material applies to everything under it. TouchDesigner makes rendering an operator whose output is just another image. MadMapper and Isadora draw by list order or layer number.
9. Types on the cord. TouchDesigner wires join only one family and every change of kind is a visible converter node. Isadora links check types and rescale numbers on every link. cables.gl colours ports by type with a catch-all Object type. Max sends small values as atoms and big data by name, with converter objects between domains.
10. Errors. TouchDesigner, cables.gl and Isadora show errors on the node, and TouchDesigner repeats the mark on every component that contains it. Max and Pd print to a console that links back to the object. TouchDesigner and cables.gl also show each node's cost; Max shows only whole-patch meters.
11. Using more cores. Most of these tools do the main work on one thread. TouchDesigner (Engine COMP) and Pd ([pd~]) reach for a second process. Max has separate scheduler and audio threads and can spread audio across top-level patchers or poly~ voices.
12. Where the work ends up. plugdata runs the whole patch, editor included, as a plug-in in any DAW, and Heavy compiles patches to C++, plug-ins and Daisy. cables.gl exports a web page. TouchDesigner has a player-only runtime. Max builds standalones, Max for Live devices and RNBO exports. MadMapper and Isadora run only in their own app, with MadMapper's hardware players as the exception.
13. Time as the program. ossia score is the one tool where the timeline drives execution: a process runs only while its interval plays, triggers hold the timeline until an event, conditions choose which branch runs, and seeking replays the latest state. Max has a transport and timed objects, but no score structure that decides what runs.

## 1. Evaluation

**The difference:** Max pushes events and computes DSP every vector while audio is on. TouchDesigner pulls on demand and skips anything nobody watches. MadMapper, cables.gl and Gem draw once per frame, and cables.gl skips any branch the frame trigger does not reach. Isadora pulls from the end of each chain and can stop a whole upstream branch with a gated Gate. Pd works like Max. ossia score is driven by its timeline: a process runs only while its interval is playing.

**Advice for Max:** In Max, unused work keeps running until something upstream stops it, so stop it at the top: turn off the metro or close a gate above the heavy part, and switch whole audio sections off with mute~ or pcontrol. Put the stop above the expensive object, not below it.

### Max

Max is push-based. An event (a click, a MIDI note, a metro tick) hands a message to one object, and that object sends messages on down its cords until the chain ends. Only a hot inlet (usually the left) makes an object compute and output; cold inlets just store a value. Audio is separate: once DSP is on, the signal graph is computed one vector of samples at a time, whether or not anyone listens. Jitter GL drawing is driven by a render context that bangs its clients once per frame.
- *Does well:* The cause of every output is visible: something upstream fired. Cold inlets let you load values first and fire once.
- *Makes hard:* Nothing is lazy. Idle audio and unseen branches still cost CPU unless muted by hand. A value arriving at a cold inlet silently does nothing until the next hot message.
- *Confidence:* high

### TouchDesigner

TouchDesigner is a pull system. Each frame, the outputs that need data (displays, audio devices, network and device outputs, visible viewers) ask for it, and the request travels upstream. An operator cooks only when something asks for its data and something it depends on has changed. A changed value only marks a node dirty; nothing is pushed downstream. A second, push side exists: event operators run Python callbacks, which usually change parameters that are then pulled as normal.
- *Coming from Max:* Nothing runs because a value arrived. You set a value and the result appears only because a viewer, a window or an output is asking for it. Turning a viewer off can stop a chain from computing at all.
- *Confidence:* high

### MadMapper

MadMapper is a frame-loop renderer. Every engine frame it draws the surface stack into each output; there is no event pushed down a graph. Values reach parameters from Controls, cues, timelines and modules, and the next frame simply draws with them. Some work is skipped when nothing uses it: an NDI source is processed only while a visible surface shows it.
- *Coming from Max:* Nothing is triggered. You set values and the next frame shows them. There is no bang, no hot inlet, and no way to make something compute 'now' apart from the frame clock.
- *Confidence:* high

### Isadora

Isadora works from the ends of chains backwards. For each actor at the end of a chain, it executes the actors linked into each input, then passes the result on. Video is rendered at a target frame rate, and time-based actors are serviced at a rate set as a multiple of that frame rate. Work nobody uses can be stopped: a whole Scene stops when it is left, and a closed Gate, Selector or Router set to 'gated' stops everything upstream of it.
- *Coming from Max:* Nothing is pushed by a source the way a message leaves an outlet. A chain does work because something at its end wants a value, so cutting the end off (a closed gated Gate) quietly stops the whole branch above it.
- *Confidence:* medium

### cables.gl

Two mechanisms drive work. Value ports push on change: when an output is set, connected inputs run their onChange, but only if the value really changed. Trigger ports are function calls with no data, and a visual patch hangs everything that draws off the MainLoop op, which fires its trigger once per rendered frame. A branch that no trigger reaches does not run.
- *Coming from Max:* Most visual work is not caused by a message arriving; it happens because the frame trigger walks through it every frame. Values sit on ports and are read when the frame passes, and a repeated identical value causes no work at all.
- *Confidence:* high

### Pd / plugdata

Two engines run side by side. Control work happens only when an event pushes a message down a cord, and each cascade runs to the end, depth first. Audio is not demand-driven: while DSP is on, every tilde object in every open patch (shown or not) is computed every block, and the only way to stop unused audio work is a [switch~] in that window. Gem frames are pushed the same way, as a message sent down from each [gemhead] once per frame.
- *Coming from Max:* The same push model as Max for messages. The difference is that audio work in a patch is never skipped on its own; Max's mute~ (refpage: disable signal processing in a subpatch) has its Pd counterpart in [switch~], which also changes block size.
- *Confidence:* high

### ossia score

Execution is driven by the score's time: while playing, each running interval ticks its processes, and a process only runs while its interval is active. A process outside the running path does nothing, and audio processes stop costing CPU once the playhead leaves their interval. Within a tick, processes form a dataflow graph whose cables carry audio, values, MIDI and textures.
- *Coming from Max:* In Max an object computes whenever a message reaches its hot inlet, at any time (max_system_model.json dimension 1). In score nothing runs unless the playhead is inside its interval, so a 'patch that just runs' has to be placed in an interval held open by a trigger.
- *Confidence:* medium

## 2. Ordering

**The difference:** Max and Pd follow each path to its end before the next. Max orders several cords from one outlet by screen position, right to left. Pd orders them by the order the cords were made, which nobody can see. TouchDesigner orders by dependency, cables.gl by the trigger graph, MadMapper by list order, and Isadora by pull plus top-to-bottom position where several links meet one input.

**Advice for Max:** Whenever one outlet feeds more than one place and the order matters, use trigger. A patch that leans on screen position breaks when someone tidies the layout, and the same patch copied into Pd runs in a different order.

### Max

Within one event, Max is depth-first: each path is followed to its end before the next path starts. Several cords from one outlet fire right to left by the position of their destinations. trigger makes order explicit and is the recommended tool; load order is staged but Max advises not to rely on it.
- *Does well:* Order is deterministic and can be read from layout and trigger arguments. Illustration Mode and the debugger make it visible.
- *Makes hard:* Order depends on screen position, so moving a box can change behaviour silently. Fan-outs without trigger are a classic bug source.
- *Confidence:* high

### TouchDesigner

Within a frame, order is decided by dependency: a node asks its inputs to cook before it cooks, so the graph's shape fixes the order. There is no left-to-right or right-to-left firing rule because nothing fires. Where order between independent scripts matters, the docs give explicit rules, such as several Execute DATs running in the alphanumeric order of their names.
- *Coming from Max:* There is no firing order to manage and no trigger object to enforce one. The question "which happens first?" mostly disappears inside the graph and comes back only in scripts.
- *Confidence:* medium

### MadMapper

Within a frame, the lists set the order. The surface list is the draw order, first item in front, and DMX fixture lists work the same way. When several things try to set the same value, the docs give specific rules rather than a general one: a new cue on a parameter cancels the earlier transition, a new item in a grid row stops the one playing, and between two schedulers the one lower in the module list wins.
- *Coming from Max:* There is no message order to reason about, because there are no messages. Order means draw order, and you see it as the list. Conflicts between two sources are settled by fixed rules, not by which cord fired last.
- *Confidence:* high

### Isadora

Order comes from the pull: upstream actors run before the input that needs them. Where several links meet one input, the upstream actors run from top to bottom by their position on screen, and the last new value wins. There is no trigger-style object for ordering, and no ordering rule was found for one output fanning out to many inputs.
- *Coming from Max:* Moving an actor up or down can change which value an input ends up with. The order question is "which upstream actors run first", not "which outlet fires first".
- *Confidence:* medium

### cables.gl

Order is set by the trigger graph. A trigger output calls its children at once, depth first, and ops like Sequence give numbered outputs that fire in order. The op guidelines ask every op with a trigger in to also pass a trigger out, so chains run in series without many Sequence ops. The docs read never tie order to screen position.
- *Coming from Max:* Order is not read off where boxes sit; it comes from which trigger output a chain hangs from and the Sequence outputs. The usual shape is a long vertical chain of trigger-in, trigger-out ops, closer to a call stack than to fanning out from one outlet.
- *Confidence:* medium

### Pd / plugdata

Outlets fire right to left and cascades run depth first, as in Max. When one outlet feeds several inlets, Pd sends in the order the cords were made, which cannot be seen in the patch, so [trigger] is the only safe way to fix an order. Signal order is decided by sorting the DSP graph, and a signal sent to an object sorted earlier arrives one block late.
- *Coming from Max:* A fan-out that is safe in Max because of box positions can run in any order in Pd, and moving boxes changes nothing. Pd patches therefore use [t] far more often.
- *Confidence:* high

### ossia score

Within a tick, the order follows the dataflow graph of cables between processes, and the timeline decides which processes are active. The docs do not describe an explicit ordering tool like a trigger object; libossia parameters carry a priority attribute meant to say which nodes execute first.
- *Coming from Max:* Max users manage right-to-left and depth-first order inside one event (max_system_model.json dimension 2). score's docs say little about message order within a tick; ordering is mostly a matter of time position and graph shape.
- *Confidence:* low

## 3. Time

**The difference:** Max has several clocks side by side: the millisecond scheduler, the sample clock, the render frame and the transport. TouchDesigner is frame-based with local timelines per component. MadMapper has an engine frame rate, a global BPM, timelines and a Master Speed. Isadora has a frame clock and no global timeline. cables.gl has the frame plus one timeline. Pd has one logical clock for messages and audio. ossia score makes the timeline the master clock, counted in flicks, with speed, tempo and quantisation passed down nested intervals.

**Advice for Max:** Choose the clock that matches what the result is for. Animation that ends up on screen should step with the render frame (jit.line, which loads as jit.mo.time, ramps in step with the render context) rather than the millisecond scheduler. Musical timing belongs on the transport.

### Max

Max has a millisecond scheduler for timed (high-priority) events, the audio sample clock for DSP, a frame clock for GL rendering, and a tempo-based transport. Time values can be fixed (ms, hh:mm:ss, samples, hz) or tempo-relative (ticks, note values, bars.beats.units at 480 PPQ). Scheduler in Audio Interrupt ties scheduler time to the sample clock. The NonRealTime audio driver runs audio as fast as possible.
- *Does well:* Musical time is built in and shared by name. SIAI gives sample-accurate control events when needed.
- *Makes hard:* Several clocks coexist and the user must pick the right one for each job. Scheduler, audio and frame timing drift relative to each other unless deliberately linked.
- *Confidence:* high

### TouchDesigner

Time is frame-based. A timeline with a frame rate (default 60), start and end range, tempo and time signature drives the project. Any component can have its own local timeline, which everything inside inherits, and it can run independently of its parents. Absolute time counts up from launch and never loops. CHOPs that need continuity are time-sliced: each cook covers exactly the samples since the last cooked frame.
- *Coming from Max:* There is one clock tick, the frame, and everything happens on it. Time is also scoped like a variable: a subpatch can carry its own clock, its own range and loop, and be paused while the rest plays.
- *Confidence:* high

### MadMapper

Several clocks sit side by side: the engine frame rate, a Global BPM, timelines with their own FPS and BPM setup, wall-clock schedules, and external timecode. Master Speed scales every animation and the audio at once, and Freeze stops them. Timelines can follow their own clock, a set speed, the Global BPM or external sync. Export can render a timeline slower than real time.
- *Coming from Max:* Time is a set of named global settings, not objects you place. One Master Speed fader changes the pace of everything, which a patch only gets if every animation reads one shared clock.
- *Confidence:* high

### Isadora

There is a frame clock (the Target Frame Rate), a service rate for time-based actors tied to it, and an internal clock that the recorder can slow down. Time-based actors each run on their own while their Scene is active; there is no global timeline or transport. Times are in seconds, movie positions in percent of the file, and timecode is its own data type.
- *Coming from Max:* There is no scheduler with millisecond events to reason about. Each envelope, timer or movie keeps its own time while its Scene runs, and the only global knob is how fast the whole engine's clock goes.
- *Confidence:* medium

### cables.gl

There are several clocks. MainLoop gives the frame. The timeline is one keyframe time line for the whole patch, in seconds, with a set frame rate. Animation ops without the timeline take the frame trigger and compute their own progress, and Timer, TimeDelta and the browser's millisecond clock give elapsed and delta time. RenderAnim steps the patch at a fixed rate to render out of real time.
- *Coming from Max:* Time is mostly frames and a document-wide timeline in seconds, not a scheduler of timed messages. A keyframe curve lives on the port itself, so 'animate this setting' needs no extra objects.
- *Confidence:* medium

### Pd / plugdata

One logical clock, kept as a 64-bit float in milliseconds, drives both messages and audio. Audio runs in blocks of 64 samples, and messages run only between blocks, so a cascade's changes all land on the same block. Scheduled events always run in order even when Pd falls behind real time, and the patch can render faster than real time with fast-forward or batch mode.
- *Coming from Max:* There is one scheduler, not a high-priority scheduler plus a low-priority queue as in Max's scheduler topic, so there is no overdrive setting to think about. Offline rendering is a message from inside the patch rather than a choice of audio driver.
- *Confidence:* high

### ossia score

The timeline is the master clock. Model time is counted in flicks (705,600,000 per second) and is affected by speed controls; physical time is counted in audio samples. Each interval can run at its own speed, and tempo, time signature and quantisation pass down the hierarchy, so different sections can have different tempos. Transport can follow or drive JACK transport.
- *Coming from Max:* Max has one scheduler, the sample clock and flat named transports at 480 PPQ (max_system_model.json dimension 3). score's time is a tree: a section can be slowed, paused or given its own tempo without touching the rest, and seeking replays state.
- *Confidence:* high

## 4. Data types

**The difference:** Max sends atoms and lists, and passes big data (matrices, textures, dicts, buffers) by name. TouchDesigner has operator families that only join their own kind. Isadora types every port and converts numbers on links. cables.gl colours ports by type, with one Object type for textures, geometry and the rest. Pd has no int type: 1 and 1. are the same.

**Advice for Max:** Because a Max cord often carries a name rather than the data, the cord does not show you the content. Look at it with a probe or a display object in the path. Keep each change of kind as a visible converter object, as TouchDesigner forces you to.

### Max

Messages are made of atoms: bang, int, float, symbol, and lists of them. Larger data is never sent itself: a cord carries a name (jit_matrix u123, jit_gl_texture name, dict name, string, array) that points at storage. Signals, MC signals, matrices, GL textures and half-edge geometry each have their own cord style. Conversion is done by dedicated objects.
- *Does well:* Passing names instead of data makes big data cheap to route and lets many objects share one store. Cords show their type by colour.
- *Makes hard:* Symbols vs lists vs selectors and int vs float are subtle and cause silent misbehaviour. Data carries no metadata beyond its type; units and meaning live in the patcher's head.
- *Confidence:* high

### TouchDesigner

Data types are operator families. TOPs carry GPU images, CHOPs named channels of float samples, SOPs and POPs geometry, DATs text or tables, MATs materials, and COMPs hold networks. A wire can only join two operators of the same family, so each family is a separate typed graph. Crossing families needs a named converter operator, a parameter that names another operator, or a CHOP or DAT export to a parameter.
- *Coming from Max:* There is no universal message that every node accepts. The editor will not let you connect an image to a channel operator; every change of kind is a visible converter node.
- *Confidence:* high

### MadMapper

The user never sees typed data on a wire. Instead there are kinds of thing: media (pixels, from files, generators, live inputs, loopbacks), vector paths for lasers, DMX channel values, and parameter values. Parameters have a small set of types, the same ones used by OSC. Conversion between domains happens at fixed points: a fixture samples pixels into DMX, a Laser Quad traces pixels into paths, a loopback turns an output back into media.
- *Coming from Max:* You choose what something is (a media item, a fixture, a laser surface) and the type follows. There is nothing like a message, a signal or a matrix travelling between parts, and no conversion objects to place.
- *Confidence:* high

### Isadora

Every port has a declared type: integer, float, boolean, range, text, trigger, video, sound, blob, timecode, skeleton, and since 4.5 audio. Numeric types and triggers connect freely and are converted; video and sound connect only to their own kind. Mutable ports take the type of the first link. There is no list type, and media files are referred to by index numbers.
- *Coming from Max:* Each link carries one value of one known type, and the type is checked when you draw the link. Several values travel as several links, not as one list.
- *Confidence:* high

### cables.gl

Ports are typed, and each type has a colour: Trigger, Number, String, Boolean, Array and Object. Textures, geometry, shaders, audio nodes and HTML elements all travel on Object ports, so an Object port accepts anything unless the op checks the link itself. Conversion between types is done by named ops whose name carries both types.
- *Coming from Max:* Cables refuse to connect where types do not match, and conversions are visible ops. There are no symbol-headed messages with a selector; a port holds one plain value or one JavaScript object.
- *Confidence:* high

### Pd / plugdata

Messages carry floats, symbols and pointers; there is no int, so 1 and 1. are the same. Signals are blocks of 32-bit floats and, since 0.54, any signal cord may hold several channels. Stored data lives in named arrays (shared by control and signal objects), [text] (lists of messages), and data structures: scalars built from templates, read through pointers, and drawn by drawing instructions.
- *Coming from Max:* Max's messages topic lists int as its own atom type; Pd has none, so integer division and int/float typing never come up. There is no dict; nested data is done with data structures, which Max has no equivalent for.
- *Confidence:* high

### ossia score

Ports carry audio (any number of channels), values, MIDI, textures and geometry. Values are typed: int, float, bool, char, string, vec2/vec3/vec4, list (tuple) and impulse. Values can also be nested lists and maps, which processes like Object filter query with jq syntax.
- *Coming from Max:* Max messages are atoms and lists, with big data passed by name (max_system_model.json dimension 4). score has typed vectors and an impulse type as first-class values, and a value can carry a unit.
- *Confidence:* medium

## 5. Rates and channels

**The difference:** Max and Pd keep control, audio and frame rates apart. Pd sets block size, overlap and resampling per window with [block~]. TouchDesigner makes rate a property of each CHOP's data, with everything cooking on the frame. Isadora and cables.gl have one frame rate and handle audio separately. Many channels are one MC cord in Max, one cord in Pd, a channel bundle in TouchDesigner.

**Advice for Max:** MC is Max's version of channels on one cord, and its wrapper messages give each channel its own value. For control data shared with visuals there is no message-rate equivalent (see 'Many channels from one generator' in the gap list).

### Max

Max keeps control rate (events), audio rate (signal vectors) and frame rate (render loop) apart, with explicit converter objects between them. poly~ voices can up- or down-sample locally; pfft~ runs a spectral sub-rate. Many channels travel in one MC cord, and MC wrapper objects hold one copy of an MSP object per channel.
- *Does well:* Each domain runs at its natural rate and the boundaries are explicit objects. MC makes N-channel and polyphonic work one cord wide.
- *Makes hard:* Crossing rates is manual and easy to get wrong (stepping, backlog, lost timing). MC channel topology (interleaved vs separate) has to be managed by hand.
- *Confidence:* high

### TouchDesigner

Everything cooks on the frame. Rate is a property of CHOP data, not of a separate graph: each CHOP has its own sample rate, and an audio CHOP at 44100 Hz simply delivers a slice of many samples per frame. Many channels are the normal case: a CHOP is a bundle of named channels, and operators act on all of them or on a name pattern (Scope).
- *Coming from Max:* There is no separate signal world with its own thread. Audio and a slider live in the same kind of node, and a slow frame affects both.
- *Confidence:* high

### MadMapper

Rates are tied to output domains, not chosen per part. Video runs at the engine frame rate. DMX output has its own maximum frame rate. A laser output has its own points per second and desired FPS. Audio is played and analysed by its own engine. Many channels are handled as a count on one thing: many DMX universes, many audio channels to one interface, many outputs.
- *Coming from Max:* There is no choice between control rate and audio rate. Audio only enters the visual side as a handful of analysed values at frame rate.
- *Confidence:* medium

### Isadora

The patch does not split into control-rate and audio-rate cords. Rates are set globally: video at the frame rate, time-based actors at the service rate, movies at the movie service rate. Channels live inside an audio link, with routing strings and a channel editor deciding which channel goes where.
- *Coming from Max:* There is no choice of rate per cord or per object; the engine owns the rates. A multichannel sound is one link, and its channels are routed by a setting on the actor.
- *Confidence:* medium

### cables.gl

There is one control rate: the frame, set by MainLoop, plus whatever event triggers arrive. Audio is a graph of browser Web Audio nodes passed on Object ports; there is no per-sample patching. Many copies are made by trigger loops (Repeat) or by GPU instancing, not by multichannel cables.
- *Coming from Max:* There is no separate signal world with its own cords. Audio nodes are wired as objects and the browser runs them; everything else runs at frame rate or on events.
- *Confidence:* high

### Pd / plugdata

Control and audio are split as in Max, with control running between audio blocks. Each window can set its own block size, overlap and resampling factor with [block~], and [inlet~]/[outlet~] convert at the boundary, so FFT size, one-sample feedback and oversampling are all just block settings. Multichannel is a property of the cord: stateless objects handle any channel count unchanged, and [clone] spreads channels over copies.
- *Coming from Max:* Max uses separate mc. objects (mc.pack~ refpage) and a pfft~ manager (refpage: spectral processing manager for patchers); Pd has neither and does both by settings on the cord and the window.
- *Confidence:* high

### ossia score

Audio runs at the sound card rate with a buffer size; value and MIDI ports carry timestamped messages within each tick; video renders in a separate thread at the output's rate. Channels travel together in one audio port, and mono effects fed N channels run N times.
- *Coming from Max:* Max separates event, signal and frame domains with converter objects (max_system_model.json dimension 5). In score a value port inside an audio tick already carries sample-position timestamps, and the multichannel idea matches Max's MC.
- *Confidence:* medium

## 6. State and saving

**The difference:** Max and Pd save structure, not values: a slider position is gone on reopen unless something stores it. Pd does this on purpose and has no preset system. TouchDesigner, MadMapper, Isadora and cables.gl save every setting's value in the file, and MadMapper and Isadora add scenes or snapshots as built-in presets. ossia score saves the timeline and the values stored in its states, not live device values, and rebuilds state on a seek.

**Advice for Max:** Decide how a Max patch keeps its state before building it: Snapshots, pattrstorage with autopattr, or initial values in Parameter Mode. Without one, every control reopens at its default, and the operator sees a patch that has forgotten everything.

### Max

A .maxpat saves structure, not state: objects, cords, arguments and frozen attributes. Slider positions and number values are lost on reopen unless a storage system keeps them. Max offers several: Snapshots (embedded, all parameters), preset and pattrstorage (slots, interpolation, JSON files), per-object embed flags (dict, coll, table, v8 script text), and initial values on parameters. Loading runs in fixed phases.
- *Does well:* Several storage systems fit different needs, and pattrstorage adds interpolation and a readable JSON file. Load order is staged and documented.
- *Makes hard:* The default is to lose state, so every patch needs a deliberate storage choice. Several overlapping systems (snapshots, preset, pattr, embed, initial values) make 'what will reopen?' hard to answer.
- *Confidence:* high

### TouchDesigner

A project saves as a .toe file and a component as a .tox. The file holds the network, every parameter in whatever mode it is in, flags, and per-operator Python storage. Node outputs are not saved unless the node's Lock flag is on, which freezes its data into the file. Components can load their contents from an external .tox at start. The Presets palette component was dropped in 2022, so there is no built-in preset system.
- *Coming from Max:* Saving keeps settings, not results. A node's output comes back only by cooking again, unless you lock it. Presets are something you build from parameters and storage.
- *Confidence:* high

### MadMapper

The project file holds the whole document: surfaces, fixtures, outputs, media references, cues, timelines and controls. What you see when you save is what reopens, since parameters are document fields. Preferences are split: Application settings belong to the machine, Project settings travel with the file. Scenes and Cues are the preset system and live in the project.
- *Coming from Max:* Every value you can see is saved, because the project is a document, not a program. There is no load-time initialisation to write; what matters is choosing which values a cue owns.
- *Confidence:* high

### Isadora

Every input always holds a value, and that value is saved with the file. Leaving a Scene remembers all its values, so returning resumes where it left off, unless an input has an Init value, which is applied and executed on each entry. Snapshots store every input of every actor in a Scene. Media is referenced, not stored.
- *Coming from Max:* Values persist by default: what you see on an actor is what reopens. Starting state is a checkbox on the input rather than a loadbang chain, and it runs through the patch when the Scene starts.
- *Confidence:* high

### cables.gl

A patch is saved as JSON on the cables server, holding the ops, their links and every input port's typed value. Values that a cable feeds are not the stored ones; when the cable is removed the port returns to its typed value. Assets are uploaded into the patch, and patch-only ops are saved with it. Presets and frozen values are stored as hidden port values on their ops.
- *Coming from Max:* Every typed setting is kept with the file without any extra storage object, because the setting lives on the port. Runtime values flowing on cables are not saved; only what is typed into ports.
- *Confidence:* medium

### Pd / plugdata

A patch saves only what you see: boxes, their creation text and the cords. Values sent to objects later are lost on reload, by design, so that a patch is 'printable'. The exceptions are subpatch contents, arrays and [text]/[array define] with keep flags, IEM GUIs in init mode, and [savestate] for abstractions; there is deliberately no preset system. plugdata adds [daw_storage] for DAW sessions and an autosave database.
- *Coming from Max:* Max saves object state and offers pattrstorage (refpage: save and recall pattr presets) and Snapshots; a Pd patch reopens with every number box at zero unless the patch itself re-sends values.
- *Confidence:* high

### ossia score

A .score file saves the whole timeline, processes, cables, device definitions and the values stored in states. Live parameter values belong to devices and are not saved unless stored in a cue. On a seek, 'value compilation' rebuilds device state from earlier states.
- *Coming from Max:* A Max patch saves structure and needs pattr, Snapshots or embed flags to keep values (max_system_model.json dimension 6). In score the stored values are the show itself: states on a timeline, and seeking reconstructs them.
- *Confidence:* medium

## 7. Parameters

**The difference:** TouchDesigner, MadMapper, Isadora and cables.gl treat every setting as a named parameter with a range and a control. TouchDesigner adds four modes per parameter: constant, expression, export, bind. MadMapper gives every parameter an OSC address automatically. Max has attributes everywhere and an opt-in Parameter Mode layer that Snapshots, mapping, OSC and Live use. Pd has parameters only at the edges, through plugdata and Heavy. ossia score puts every parameter it controls in one device tree with type, range, clip mode and unit.

**Advice for Max:** Turn on Parameter Mode for the controls an operator or a host should reach, so they gain a range, an initial value, mapping and an OSC address in one step. Max has no expressions on attributes, so a computed setting is an explicit object feeding an attrui or a message, where it can be seen.

### Max

Settings are attributes, set by name with a message or @name in the box. A smaller layer, Parameter Mode, turns an object's state into a named parameter with range, type, unit style, initial value and visibility. Parameters are what Snapshots, MIDI/key mapping, Live automation, OSC addresses and param_connect use. There are no expressions on attributes.
- *Does well:* One parameter definition feeds presets, mapping, OSC, Live and UI links. Attributes make object state readable in the box.
- *Makes hard:* Parameter Mode is opt-in per object, so coverage is patchy. Attributes cannot hold expressions or bindings; any link between values is cords or param_connect.
- *Confidence:* high

### TouchDesigner

Every setting of every operator is a named, typed parameter on a page of the parameter dialog. Each parameter can be in one of four modes: Constant, Expression (Python), Export (a CHOP channel or DAT cell drives it) or Bind (two-way link to another value). Parameters carry label, default, range, clamp, menu entries, enable expression and read-only state. Components get custom parameters, which are their whole outside interface.
- *Coming from Max:* A setting is not set by a message arriving; it is defined. Any setting can be a live formula, an incoming channel or a two-way link, and the dialog colour shows which.
- *Confidence:* high

### MadMapper

Almost every slider, button and menu is a parameter with a fixed OSC address built from the names in the project. Any parameter can also get one Control per source type (MIDI, OSC, DMX, keyboard, audio, gamepad, internal modules) with ranges, a filter and a curve. Parameters are what cues store and timelines keyframe. Shader inputs declared in a header become parameters like the built-in ones.
- *Coming from Max:* Exposure is automatic: nothing has to be wired or published to be reachable from outside. The cost is that a rename changes the address, and mapping logic is limited to range, filter and curve.
- *Confidence:* high

### Isadora

Every actor setting is a typed input property with a minimum, a maximum and help text. Each input can be scaled, given an Init value, and tied to a panel control by number. Values arrive by link, by control, or by typing; there are no expressions or bindings on a parameter.
- *Coming from Max:* Every knob on an actor is already a visible, typed, range-limited input, so there is nothing like turning on a parameter. But a parameter cannot be driven by an expression; it needs a link.
- *Confidence:* high

### cables.gl

Every input port is a parameter. Selecting an op shows all its inputs in a panel as sliders, checkboxes, menus and text fields, and the op's code decides which control is drawn. A typed value is kept; a cable overrides it. Any number port can be keyframed, and a port can be driven from outside through variables.
- *Coming from Max:* An input is not just a hole a cord plugs into: it has a visible, stored value and a control in the panel. Settings are changed in the panel, not by typing arguments into a box.
- *Confidence:* high

### Pd / plugdata

Vanilla Pd has no parameter system. Settings are creation arguments, inlets and messages; IEM GUIs expose every property as a message and can take $1 or $0. Parameters appear only at the edges: plugdata's [param] maps a value to DAW automation, and Heavy turns annotated receives such as [r gain @hv_param 0 1 0.5] into plugin parameters on export.
- *Coming from Max:* Max's parameter mode topic describes parameters with initial values, names, units and modulation shared by presets, Live and MIDI mapping. Pd has nothing in the core, so a 'parameter' is just a named receive.
- *Confidence:* medium

### ossia score

Everything score controls is a parameter in a device tree, addressed as device:/path. Parameters carry a type, range or value set, clip mode, repetition filter, unit and more. Process controls are ports that can be given an address, automated, or cabled. There are no expressions on parameters; math lives in expression processes.
- *Coming from Max:* In Max, settings are attributes and only parameter-enabled objects join the parameter system (max_system_model.json dimension 7). In score the parameter tree is the centre of the program: every external control is one, and the tree, not the patch, is what you browse.
- *Confidence:* high

## 8. Encapsulation and reuse

**The difference:** Max has three forms (p, abstractions, bpatchers) plus poly~ for copies. TouchDesigner makes the component the unit of everything, with clones that follow a master and a Replicator that makes one copy per table row. Isadora's User Actors update every copy on request. cables.gl versions ops in their names. Pd's [clone] replicates an abstraction like poly~. MadMapper has no subpatches at all.

**Advice for Max:** Use abstractions, not copied p boxes, for anything used twice: every copy then follows the one file. Give each a small set of named settings through patcherargs, the way TouchDesigner components are driven by their custom parameters. For many copies, poly~ plays the role of TouchDesigner's Replicator and Pd's [clone].

### Max

Three forms: an embedded subpatcher (p), an abstraction (a .maxpat used by name from the search path) and a bpatcher (a patcher shown as a UI block). Abstractions take arguments via #1–#9 or patcherargs and get a unique #0. poly~ and mc.poly~ replicate one patcher many times. Prototypes, snippets, templates and packages handle styling and sharing.
- *Does well:* Any saved patch is instantly a reusable object, with arguments and help. Replication (poly~, MC) is built in.
- *Makes hard:* Versioning is file-level only: no per-instance version pinning, and editing an abstraction affects every patch that uses it. Port order follows box position, so layout edits can rewire parents.
- *Confidence:* high

### TouchDesigner

The component (COMP) is the unit of structure and reuse. In and Out operators inside become its ports; custom parameters become its arguments; a .tox file saves it. Copies are kept in step by cloning, where clones follow a master's insides while keeping their own top-level parameter values. A Replicator COMP makes one copy per table row or count. Components can load from an external .tox at start, and the Palette is a library of ready components.
- *Coming from Max:* A reusable part is a container with typed parameters, not a file with numbered arguments. Many copies are kept identical by pointing them at one master, and a table can grow or shrink the number of copies while it runs.
- *Confidence:* high

### MadMapper

There is no subpatch or component. Grouping is visual and multiplicative: a group of surfaces or fixtures scales its children's opacity and colour. Reuse happens at the level of whole items and files: duplicate surfaces, share one media on many surfaces, fixture definitions shared by many fixtures, Materials and FX shared through the Library, and Merge Project to bring in another project.
- *Coming from Max:* You cannot package your own logic into a reusable box with arguments and ports. Reuse means copying items, sharing media, or writing a shader.
- *Confidence:* medium

### Isadora

A User Actor wraps actors behind User Input and User Output ports and carries an identifier. Editing one offers Save & Update All, which rewrites every copy in every open document and toolbox while keeping links and hand-set values. A Macro is the same wrapper with no shared identity. User Actors live in a Global folder, or locally in the document.
- *Coming from Max:* Reuse is by identity, not by file name. A copy pasted into a Scene stays linked to its siblings until you choose to update them, so an embedded copy and a shared one are the same thing.
- *Confidence:* high

### cables.gl

A SubPatch groups ops in one box; its ports are made by dragging a cable to a 'create port' port, and PatchInput and PatchOutput are the inside ends. A SubPatchOp is a new named op built by patching, the counterpart of an abstraction, and it lives in a namespace like a coded op. Ops are versioned in their name (_v2), old versions stay loadable, and the editor offers an update.
- *Coming from Max:* Reusable parts are ops with a full namespaced, versioned name and an owner, not files found on a search path. Ports come from dragging cables, so they arrive typed and named.
- *Confidence:* medium

### Pd / plugdata

[pd name] is a one-off subpatch saved inside the parent; an abstraction is any .pd file typed by name. Arguments arrive as $1, $2 in object boxes, $0 is unique per patch, and [pdcontrol] args gives a variable-length list. [clone] replicates an ordinary abstraction N times with the copy number in $1. Graph-on-parent lets the abstraction draw its own face on the parent box.
- *Coming from Max:* One mechanism ($) where Max uses # for arguments and abstractions open read-only, per Pd's own manual. Graph-on-parent replaces the bpatcher (refpage: embed a subpatch with a visible UI), but the face is decided inside the abstraction, not by the box that loads it.
- *Confidence:* high

### ossia score

Reuse happens through nesting and the library. A Scenario process puts a whole score inside an interval, to any depth. Selections of the score can be saved to the library as .scenario files, states as .cues, and JS, Faust, shader and Pd files dropped in become processes. New processes come from plug-ins.
- *Coming from Max:* Max reuses through abstractions with arguments and #0 instance names, and poly~ for many copies (max_system_model.json dimension 8). The docs read describe no equivalent of arguments or replication for a saved .scenario; reuse is by copying a fragment back in.
- *Confidence:* medium

## 9. Names and scope

**The difference:** Max and Pd names are global unless made local by hand (#0, ---, $0, pv). TouchDesigner names are paths in a hierarchy and every reference is drawn as a dashed line. Isadora seals each Scene and passes data on numbered channels. cables.gl variables reach the whole patch. MadMapper's item tree doubles as the OSC address space. ossia score addresses parameters by device and path, with pattern matching over many addresses at once.

**Advice for Max:** A send/receive pair in Max is a link nobody can see, unlike a TouchDesigner reference. Keep such links few, name them clearly in capitals, use a cord when the two ends are close, and give every name inside a copied thing its per-copy prefix.

### Max

Most names are global to the whole Max application: send/receive, value, buffer~, dict, coll, named transports, and the targets of semicolon messages. Narrower scopes exist: pv (one patcher and its children), #0 (one abstraction instance), --- (one Max for Live device), scripting names (one patcher), pattr paths (one root hierarchy). GL objects find their context by name with @drawto.
- *Does well:* Wireless links are one word, and scope can be narrowed when needed. Names make large patches routable without cords.
- *Makes hard:* Global is the default, so two copies of a patch or device collide silently. Each container has a different scoping mechanism to remember.
- *Confidence:* high

### TouchDesigner

Every operator has a path in the component hierarchy, like a file path: absolute from root (/project1/geo1) or relative (../button3). References are paths in parameters, in Python expressions (op('...')) or in exports. Names are therefore scoped by position, not global. Shortcuts make references survive moves: Parent Shortcut, Global OP Shortcut and internal operator shortcuts. References are drawn as dashed lines in the editor.
- *Coming from Max:* A name lives at an address. You point at "the noise inside the component next to me" with a path, and the editor draws a line for each such reference, so wireless links are visible.
- *Confidence:* high

### MadMapper

Things are referred to by their item names in one project-wide tree. The OSC address of a parameter is its path through that tree, so names are global and unique within their list. Media is assigned by picking it; cues and timelines refer to parameters directly. Scope is the project, with banks as a second level for timelines.
- *Coming from Max:* There is one tree of names and every part of it is public. There is nothing like a local name, a per-instance prefix or a private send.
- *Confidence:* medium

### Isadora

Scenes cannot see each other's links. Data crosses only through Broadcaster and Listener on numbered channels, Set and Get Global Values under a text name, or OSC. Both reach only active Scenes. Most other things are addressed by number: Scenes by position or Cue Number, Stages, media, panel controls.
- *Coming from Max:* A wireless send only reaches parts of the show that are running. Most references are numbers, so reordering a list (Scenes, media, Stages) can change what a reference points at.
- *Confidence:* high

### cables.gl

Variables (VarSet/VarGet for numbers, strings, arrays, objects, textures) and named triggers (TriggerSend/TriggerReceive) link parts without cables. Names are case sensitive and reach across the patch and into subpatches. The same variables are the door to the page that embeds the patch.
- *Coming from Max:* Wireless names are typed, and a variable has one value you read anywhere rather than messages broadcast to receivers. No page offers a per-instance name scope.
- *Confidence:* medium

### Pd / plugdata

Names are global by default: [send]/[receive], arrays, [value], [text], [send~], [throw~] and delay lines all meet by name anywhere. Locality is made by hand with $0 in the name. Every window is itself a receiver named pd-<name>, and Pd is the receiver pd, so the same send mechanism reaches objects, windows and the engine.
- *Coming from Max:* Max has pv (refpage: share data within a patch hierarchy) for scoped values; Pd has no scoped name, only $0 prefixes. Sending to a window by name replaces thispatcher (refpage: send messages to a patcher).
- *Confidence:* high

### ossia score

Parameters are reached by path: device name, colon, slash path (OSCdevice:/track/1/volume), optionally followed by @[index] or @[unit]. Paths accept pattern matching. Score objects are found by name or label through the inspector or scripts. Device names are global to the document.
- *Coming from Max:* Max names are mostly global send/receive names with scope tricks like #0 and --- (max_system_model.json dimension 9). In score a name is a full path in a tree, so related controls are grouped by their path and can be addressed together with one pattern.
- *Confidence:* high

## 10. Show structure

**The difference:** Isadora is built as a row of Scenes with transitions handled by the host. MadMapper has a grid of Scenes and Cues and a master timeline. Max, TouchDesigner, cables.gl and Pd have one graph, and scenes and cues are built from parts. ossia score makes the timeline itself interactive: triggers wait for an event, conditions choose a branch, transitions loop or jump.

**Advice for Max:** A Max piece with sections needs its scene layer designed early: what each section turns on and off, how state is stored per section (pattrstorage or Snapshots), how cues are listed (qlist or coll), and how sections fade. Isadora's rule that an inactive section does nothing is worth copying: switch whole sections off, not just their outputs.

### Max

Max has no built-in scene, cue or timeline layer. A work is one patcher graph (often with subpatchers or tabs), and its structure is built from objects: qlist and coll for cue lists, pattrstorage or Snapshots for states, the transport for musical time. Parts are turned on and off with mute~, pcontrol, gate and similar objects.
- *Does well:* Any show logic can be patched exactly as wanted.
- *Makes hard:* Every show rebuilds cueing and section switching from parts; there is no standard cue list or timeline to hand to an operator.
- *Confidence:* medium

### TouchDesigner

A work is one component hierarchy under root, normally /project1, with output windows such as /perform. There are no scenes or cues built in. Parts are switched off by the Cooking flag on a component, by Bypass, by simply not being pulled, or by Load on Demand. Sequencing is built from Timer CHOP segments, local timelines per component, keyframe Animation COMPs and Python callbacks.
- *Coming from Max:* Turning a section off is a flag on a container, and anything not being watched is off by itself. Cues are something you build from timers and local clocks.
- *Confidence:* medium

### MadMapper

A show is a grid of Scenes and Cues organised in banks, plus timelines. A Scene is a full snapshot, a Cue a partial one, and in version 6 either can be animated into a timeline. The Conductor is the master timeline that places scenes and cues in time alongside montage, audio, OSC and MIDI tracks, with markers that pause, loop or jump. Turning things on and off is done by cues, row exclusivity and schedulers.
- *Coming from Max:* Show structure is a built-in layer above the content, not something you build. A cue grid and a timeline exist in every project from the start.
- *Confidence:* high

### Isadora

A document is a row of Scenes, each a complete patch, in running order. Normally one Scene is active; moving along the row is moving through the show. Extra Scenes can be activated alongside and keep running across Scene changes. A Scene that is not active does nothing at all.
- *Coming from Max:* The unit of structure is the Scene, and the host switches them on and off. You do not build a state machine to change sections; you move along a list, and the old section's patch simply stops.
- *Confidence:* high

### cables.gl

A work is one patch with one graph and one timeline. Parts are switched by routing the frame trigger to one branch, or by disabling ops. The docs describe no cue list or scene manager.
- *Coming from Max:* Turning a scene off means cutting off its trigger: an unreached branch costs nothing. A linear piece can be laid out on the timeline instead of sequenced with messages.
- *Confidence:* medium

### Pd / plugdata

A work is one patch graph, with subpatches. There are no scenes, cues or timelines in the core. Sections are turned on and off with [switch~] for audio and [spigot] for messages, and sequences are played from [text sequence] or [qlist], which send timed messages to named receivers.
- *Coming from Max:* Close to Max: both leave show structure to the patch. Pd has fewer helpers for it.
- *Confidence:* medium

### ossia score

A show is one interactive score: intervals (blocks of time holding processes) between states (instants holding cues), joined at synchronisation points. Triggers hold the timeline until an event, conditions choose branches, transitions loop back, and sub-scenarios nest. Scenes are sequences of intervals each holding a sub-scenario.
- *Coming from Max:* Max has no built-in show layer; structure is built from qlist, pattrstorage and the transport (max_system_model.json dimension 10). score is the show layer: its whole interface is a timeline that can wait, branch and loop.
- *Confidence:* high

## 11. Interface

**The difference:** Max places controls in the patch, where each one is part of the dataflow, and gives a second layout in presentation mode. TouchDesigner builds panels as a separate tree of components. Isadora links controls to inputs by number in a separate Control Panel. cables.gl builds its panel from ops. MadMapper's editor is the interface.

**Advice for Max:** Max's strength is that a control sits in the path, so what it shows is what flows. Keep that, and use attrui where a control should be generated from an attribute instead of drawn by hand.

### Max

Controls are UI objects placed in the patcher; each one is a node in the dataflow, so the value it shows is the message it sends. Presentation Mode gives a second, independent layout of chosen objects as the performer view. Parameters can also be mapped to MIDI, keys, OSC, Live, and Mira on an iPad. Custom UI can be drawn with v8ui/jsui or a jspainter file.
- *Does well:* The interface and the program are the same graph, so controls cannot drift from data. Presentation gives a clean performer view without a separate build.
- *Makes hard:* UI is hand-placed; nothing is generated from parameters. Building and keeping two layouts (patching and presentation) is manual work.
- *Confidence:* high

### TouchDesigner

The interface is a separate tree of panel components (Container, Button, Slider, Text, List …) that you build like any network. A panel's look is usually a TOP; its state is a set of panel values. A Window COMP shows a panel or any node viewer in an OS window. Perform Mode shows only one chosen window and closes the editor. Any operator's parameter dialog can also be shown as a panel (Parameter COMP), and autoUI builds widgets from custom parameters.
- *Coming from Max:* The operator's screen is not a view of the patch; it is its own network of panel nodes. The running show and the editor are two modes of the program, not two views of one patch.
- *Confidence:* high

### MadMapper

The editing interface is the interface: lists on the left, an inspector for the selected item, the Input View and Stage Preview in the middle, and tools such as the timeline and Control List at the bottom. There is no separate operator panel to design. Performers work through the cue grid, hardware controllers and Stream Deck, or remote OSC tablets. Shader headers generate their own controls.
- *Coming from Max:* There is no presentation view to build and no UI objects to place. The trade-off is that the operator sees the same dense editor you do, or a hardware grid.
- *Confidence:* high

### Isadora

The operator works in a Control Panel, a separate view from the patch. One panel serves a run of adjacent Scenes and changes when the Scene changes. Controls connect to actor inputs and outputs by Control ID, not by links, and can show the current value of what they control.
- *Coming from Max:* The operator's view is not built from the patch's own boxes. It is a separate layout whose controls reach into the patch by number, and it follows the show from Scene to Scene.
- *Confidence:* high

### cables.gl

Controls for the person using the patch are built with ops, not placed by hand. A Sidebar op starts a panel over the canvas and controls chain from it; HTML ops build page elements styled with CSS. The editor's parameter panel is the author's interface; Viz ops draw readouts on the patch itself.
- *Coming from Max:* There is no second view of the same boxes for the performer. The performer's panel is generated by ops in the graph and laid out automatically, or built as a web page.
- *Confidence:* high

### Pd / plugdata

Vanilla Pd's controls live in the patch itself: atom boxes and the IEM set ([bng], [tgl], [nbx], sliders, radios, [vu], [cnv]). A control binds to a value by cord or by its built-in send/receive names. An abstraction's face is its graph-on-parent area. plugdata adds a presentation mode, a plugin mode that shows the patch with none of plugdata's own UI, an Inspector sidebar for properties, and pdlua objects that paint their own GUIs.
- *Coming from Max:* Vanilla Pd has a small GUI set and no presentation view; plugdata's presentation and plugin modes fill that gap but are not part of the .pd format's documented semantics.
- *Confidence:* medium

### ossia score

One window holds a device explorer and libraries on the left, the timeline (or nodal view) in the centre and an inspector on the right. Controls appear on process nodes and can be right-clicked for exact entry. A separate performer UI can be a QML file passed on the command line, and Control Surface processes generate widgets from parameter metadata.
- *Coming from Max:* In Max the controls are the dataflow and a presentation view is the performer view (max_system_model.json dimension 11). score's editor is a timeline, and a performer interface is a separate QML file that binds to ports and addresses by name.
- *Confidence:* medium

## 12. Editing while running

**The difference:** All six keep running while edited. Isadora adds Blind Mode, editing one Scene while another runs the show. TouchDesigner has wide undo and a Safe Mode for crashed files. In Max and Pd, retyping a box makes a new object and loses its state.

**Advice for Max:** Max has no way to edit one section offline while another plays. Before changing a running show patch, store its state, since any retyped box comes back at its defaults.

### Max

Max is live: the patch keeps running while you edit it, and new objects work the moment they are created. Changing an object's text replaces it with a fresh instance, losing its state. With audio on, an optional mixer crossfades between old and new versions of the DSP graph. The scheduler can be stopped to edit a busy patch.
- *Does well:* No compile-run cycle; you hear and see every edit at once.
- *Makes hard:* Retyping an object loses its state, and some edits briefly glitch audio unless crossfade is on. There is no 'blind' edit mode that keeps changes off the live output.
- *Confidence:* medium

### TouchDesigner

The project keeps running while you edit; the network editor is live, wires animate when upstream nodes cook, and every node's viewer shows its current output. Undo covers node creation and deletion, wiring, renaming, flags, parameter changes, copy and paste, DAT editing and keyframes. Scripts do not create undo steps unless they use the Undo class. Safe Mode opens a crashed file with nothing cooking.
- *Coming from Max:* You build inside the running thing and see each node's result as you go. Wire animation tells you what is computing right now.
- *Confidence:* high

### MadMapper

The project is always live: surfaces are dragged and warped while the output plays. Safety comes from locks and modes, not from a separate run state. Surfaces, fixtures and outputs can be locked, the grid has a Live mode that only triggers, and Edit mode is entered explicitly to change what cues store. Undo exists, and AutoSave counts down so a save does not hit mid-show.
- *Coming from Max:* There is no locked versus unlocked patch; editing and performing happen in the same view at once. Every edit shows on the projector immediately, so safety is about locking things.
- *Confidence:* high

### Isadora

The active Scene runs while you edit it. Blind Mode lets you edit a different Scene while the active one keeps running and keeps answering Go Triggers; the Scene being edited is paused. Pause Engine stops everything for rescuing a patch that jumps away as soon as it starts.
- *Coming from Max:* There is a safe way to prepare the next section during a show: open it blind, and it stays frozen while the running one plays on.
- *Confidence:* high

### cables.gl

The patch keeps rendering in the browser while it is edited; changes to parameters, links and keyframes show at once. Undo exists. Editing an op's code in the web editor needs a save, and the tutorial reloads the patch; the standalone watches op files and reloads on save.
- *Coming from Max:* Same live feel as a running patcher, with the output preview in the same window. Code changes to an op are a save-and-reload step in the browser.
- *Confidence:* medium

### Pd / plugdata

Edit mode and run mode differ only in what a click does; the patch keeps running, audio included, while it is edited. Changing the audio network while DSP is on makes Pd re-sort the tilde objects. Retyping a box destroys the old object and makes a new one, so its state is lost. Compiled externals stay loaded until Pd quits, while abstractions and pdlua classes can be reloaded live.
- *Coming from Max:* Same live-editing feel as Max. Retyping a box loses its state in both; Pd says so as a design rule.
- *Confidence:* high

### ossia score

The score keeps playing while you edit: processes, sounds and shaders can be added, removed or changed during playback, and code processes recompile on Compile or Ctrl+Enter. Invalid code leaves the running version in place. Devices cannot be added during playback, and execution settings need a restart of playback.
- *Coming from Max:* Both run while edited. In Max, retyping an object resets it (max_system_model.json dimension 12); in score a code process keeps running its old version when new code fails to compile.
- *Confidence:* medium

## 13. Scripting

**The difference:** Max has JavaScript in v8 and Node in node.script, both able to script the patcher. TouchDesigner uses Python everywhere, including in parameters. Pd's file is itself a list of messages that can edit a running patch. cables.gl ops are JavaScript files. Isadora runs JavaScript, Python and GLSL inside actors that cannot change the patch. MadMapper has no scripting.

**Advice for Max:** Reach for v8 when logic branches a lot, as the preferred-objects table already says. Scripting the patcher itself is possible in Max, but a patch that rebuilds itself is hard to read; keep it for tools, not shows.

### Max

JavaScript is built in: v8 and v8ui (and older js/jsui) define objects in JS, can query and change the patcher, and run on the low-priority thread. node.script runs full Node.js in a separate process. Lua runs inside jit.gl.lua, Java in mxj, GenExpr in gen codeboxes. The graph itself can be built and rewired by thispatcher messages or the JS patcher API, and the REPL sends text commands.
- *Does well:* Many languages, and scripts behave like ordinary objects in the graph. The patch can program itself.
- *Makes hard:* JS runs at low priority, so it is unsuited to tight timing. Each language has its own API and threading rules to learn.
- *Confidence:* high

### TouchDesigner

Python 3.11 is built in and used everywhere: parameter expressions, callbacks in DATs, extensions on components, Script operators that produce a family's data, and the Textport console. Scripts can build and rewire networks, create custom parameters, and react to events. Scripts live in DATs inside the network. Python runs on the main thread, so slow code drops frames; a Thread Manager exists for background work.
- *Coming from Max:* Scripting is one language spread through the whole system rather than a box you add. Any setting can be a line of Python, and any component can carry a class.
- *Confidence:* high

### MadMapper

There is no general scripting language. Logic is limited to Controls, modules (Oscillator, Macro, Controls Combiner, schedulers), timeline markers with follow actions, and GLSL. GLSL is a real language inside MadMapper, but it computes pixels, laser paths or DMX expression values, not show logic. Outside control goes through the OSC API.
- *Coming from Max:* Conditional logic, counters and state machines have nowhere to live inside MadMapper. They go in an outside program that sends OSC, which is the role the manual gives Max.
- *Confidence:* high

### Isadora

Three languages run inside actors: Javascript (V8, sandboxed), Python through the Pythoner actor (not sandboxed, one interpreter for the whole session), and GLSL fragment shaders. Each script sees only its own inputs and returns values to its outputs. No way for a script to build or change the patch was found.
- *Coming from Max:* A script is a box with inputs and outputs, not a way to drive the patcher. Scripting the patch itself, as patcher scripting does, has no counterpart in what was read.
- *Confidence:* medium

### cables.gl

JavaScript is the language. Every op is one JavaScript file with ports declared in code and callbacks on them; users write their own ops in the browser editor and can read the source of every core op with the e key. Ops can include GLSL, Web Workers, WebAssembly and outside libraries. Pages read show no op that builds or rewires the graph from inside the patch.
- *Coming from Max:* Scripting is not a script object inside the patch; a script becomes a first-class op with typed ports and panel controls, indistinguishable from a built-in one.
- *Confidence:* medium

### Pd / plugdata

The patch file is itself a list of messages to canvases, and the same messages (obj, msg, connect, disconnect, clear, vis, menusave) can be sent to any window at run time, so patches build and edit patches. Inside objects, [expr], [expr~] and [fexpr~] give C-like expressions, and pdlua (shipped with plugdata) lets a .pd_lua file define a new object class with control, signal and graphics methods. There is no JavaScript.
- *Coming from Max:* Dynamic patching uses the same text as the file format, not a separate scripting API, and objects are addressed by creation index rather than by scripting name. Lua takes the place of Max's js and v8 (Max's js refpage now calls js the legacy engine).
- *Confidence:* high

### ossia score

JavaScript (ES7, through QML) is built in at two levels: JS processes that run in the score with ports and a tick function, and a console/script API that edits the score itself, controls transport and devices, opens sockets and runs shell commands. Devices for serial, WebSocket, HTTP and mapping are written in QML. Math expressions (ExprTK), Faust, C++ JIT, bytebeat and Pd patches are other in-score languages.
- *Coming from Max:* Max has v8 objects and thispatcher for patch scripting, plus gen and node.script (max_system_model.json dimension 13). score's script API works on the timeline as a document: creating boxes at a time, automating an address, setting curve points.
- *Confidence:* high

## 14. Errors and debugging

**The difference:** TouchDesigner, cables.gl and Isadora put errors on the node that raised them, and TouchDesigner repeats the mark on every containing component. Max and Pd print to a console that links back to the object. Max adds watchpoints, breakpoints and probes. MadMapper has no console, only monitors.

**Advice for Max:** Since a Max error is only a console line, give script objects a status outlet and show it in the patch, the way many cables.gl ops have a 'has error' output. Missing objects and unknown attributes are mostly silent in Max, so check names before shipping.

### Max

Errors go to the Max Console as text, colour-coded and linked back to the object that posted them. Missing objects load as broken boxes and unknown attributes are mostly silent. The debugger adds watchpoints, breakpoints and stepping on cords; probes show the last message, signal or matrix on a cord; Illustration Mode runs the patch in slow motion.
- *Does well:* Strong cord-level tools: probe any cord, break on any cord, watch the order of events.
- *Makes hard:* Many mistakes produce no error (unknown attributes, cold-inlet values, wrong order). There is no per-object CPU profiler documented.
- *Confidence:* high

### TouchDesigner

Errors and warnings appear on the node that raised them, and the marker also appears on every component that contains it, so a fault deep inside shows at the top. Every node has a built-in viewer of its output. The Errors dialog lists errors and jumps to them; the Error DAT logs them as a table with a callback. Cook times are on every node and in the Performance Monitor and the Probe.
- *Coming from Max:* You rarely add something to see data: every node already shows it. Errors sit on the node and bubble up to the containers, rather than only scrolling past in a console.
- *Confidence:* high

### MadMapper

There is no console or log. Feedback is built into specific tools: monitors, previews and highlight overlays. The DMX Monitor shows channel values, the Audio Data panel shows audio levels, laser vectorization has a Monitor, and 3D calibration reports an RMS error. On the real output, Show Info, test patterns and cursors help see what is happening.
- *Coming from Max:* There is nothing to print and no probe to attach. You debug by looking at the output and at the tool's own monitors.
- *Confidence:* medium

### Isadora

Feedback is mostly visual and on the patch: link colours show whether data flows, hovering a video or audio link previews it, and script errors mark the actor and print to a Monitor window. A Status window and status bar show load. There is no stepping or breakpoint tool in what was read.
- *Coming from Max:* You debug by looking at the patch itself: which links are green, what video is on a link. There is no general message log for ordinary actors.
- *Confidence:* medium

### cables.gl

Errors show on the op itself as a grey hint, orange warning or red error with a red dot. Many ops also report failure as an output port. Flow mode lights cables as data and triggers pass, Viz ops sit on cables as pass-through readouts, and logs go to the browser developer tools.
- *Coming from Max:* Problems are marked where they happen, on the op, instead of in a separate console window. Failure is often a port value the patch can branch on.
- *Confidence:* high

### Pd / plugdata

Errors print in red to the console of the main Pd window, with log levels. Ctrl+click on an error line, or Find Last Error, selects the object that caused it, and a missing-object error can open deken with that name. [trace] prints every message a chosen message causes. plugdata adds hover oscilloscopes on signal cords, an activity overlay and connection activity display.
- *Coming from Max:* Vanilla Pd has no watchpoints, stepping or cord probes like Max's debugging topic describes; [trace] is the nearest tool. plugdata's hover scope covers part of what Max's signal probe does.
- *Confidence:* high

### ossia score

Errors from code processes appear in the editor's log pane. Messages in and out of a selected process can be logged to a messages panel, and a benchmark mode shows each process's relative CPU cost. Monitoring processes (Value Display, Signal Display, LED View, Point2D View) and Teleplot let you watch values.
- *Coming from Max:* Max has a console linked to objects, probes, watchpoints and Illustration Mode (max_system_model.json dimension 14). score's per-process CPU benchmark has no Max equivalent named in max_system_model.json, while Max's stepping debugger has none in score's docs.
- *Confidence:* medium

## 15. Rendering

**The difference:** Jitter joins objects to a named render context and orders them by depth testing, or by a layer number when depth testing is off on those objects. cables.gl and Gem treat the chain as a render tree where state applies to what is under it. TouchDesigner makes rendering an operator that outputs an image. MadMapper and Isadora order by list or layer number.

**Advice for Max:** For 2D layering in Jitter, set @layer on each object and turn depth testing off on those same objects, or use jit.gl.layer, whose defaults are already depth off and blending on. Max's userguide says depth testing overrides the layer value otherwise. This corrects the repo's own forum notes, which put depth_enable on jit.world.

### Max

Jitter GL uses named render contexts (jit.world, jit.pworld, jit.window + jit.gl.render) that objects join by @drawto. Draw order is decided by depth testing by default; @layer orders objects only when @depth_enable is 0 on those objects, and @blend_enable mixes them. jit.gl.node makes offscreen contexts, jit.gl.pass adds post passes, and materials attach via jit.gl.material or jit.gl.pbr. Matrices run on the CPU; textures, slab, pix and pass run on the GPU.
- *Does well:* Contexts are found by name, so GL objects need no cords to draw. CPU and GPU paths both exist, with explicit conversion.
- *Makes hard:* Draw order is implicit (depth or layer 0 is indeterminate) unless the user sets layer and depth_enable on each object. Two pipelines (matrix and texture) must be kept apart deliberately.
- *Confidence:* high

### TouchDesigner

Rendering is an operator: a Render TOP takes a camera, lights and geometry components and outputs an image, which is then just another TOP to composite. 3D objects are components parented by vertical wires. Whether an object is drawn depends on its Render flag, its container's Render flag and being listed in the Render TOP. Image work is GPU-based TOP chains; the graphics API is Vulkan.
- *Coming from Max:* A 3D scene is a node whose output is a picture. What gets drawn is decided by flags and a list on the renderer, not by which objects are in a shared context.
- *Confidence:* medium

### MadMapper

The render model is a fixed pipeline: media is cropped by each surface's input geometry, warped by its output geometry, drawn in list order with opacity and a blend mode, and composited into each output. Draw order is the list. Levels multiply from surface to group to master. A Material is merged into the surface's own shader and drawn straight to the output; Generators and buffers render to textures. Loopbacks and buffers make multi-stage pipelines.
- *Coming from Max:* You never build a render chain or set layer numbers. The pipeline is fixed, and anything more complex is done by rendering into a buffer and using it again as media.
- *Confidence:* high

### Isadora

Video goes to numbered Stages through Projector actors. On one Stage, Projectors stack by a layer number with one of three blend modes, so draw order is a number, not the graph. Processing is on the GPU by default. Whole Scenes are composited during a crossfade.
- *Coming from Max:* Where an image ends up, and above what, is decided by numbers on the final actor, not by the order of a render chain.
- *Confidence:* high

### cables.gl

WebGL (WebGL2 where available) on the GPU, with WebGPU as an extension. The trigger tree is the scene: a state op (transform, blend, material, camera, light) applies its state, triggers its children, and the state holds only for what is under it. Draw order is trigger order. 2D effects run in a shared ImageCompose chain whose size is set once at the top.
- *Coming from Max:* Render state is inherited down the chain instead of set as attributes on each drawn object, so where a box sits in the trigger chain decides what it affects.
- *Confidence:* high

### Pd / plugdata

Gem draws by passing a frame message down chains that start at [gemhead]. Objects on the chain change OpenGL state (transform, colour, texture, shader) for everything below them, and a geo at the bottom draws with whatever has built up, so order on the cord is order of application. Draw order between chains is the number on each [gemhead]. Images are processed on the CPU by pix objects and handed to the GPU by an explicit [pix_texture].
- *Coming from Max:* In Jitter a shape object owns its own transform and colour; in Gem those are boxes above it on the cord, and draw order is a number rather than a layer plus depth test.
- *Confidence:* medium

### ossia score

Video uses Qt RHI over OpenGL, Vulkan, Metal or Direct3D. Video processes form a render graph in its own thread; each writes to a render target, and outputs are Window, Spout, Syphon, NDI or shared-memory devices. Shaders are ISF (fragment), VSA (vertex points), CSF (compute) or raw raster pipelines, all declared by a JSON header.
- *Coming from Max:* Jitter uses named contexts that objects join with @drawto, depth testing and @layer (max_system_model.json dimension 15). In score a video chain ends at an output device chosen on a port, and the docs do not describe a draw-order rule for overlapping images.
- *Confidence:* medium

## 16. Performance and concurrency

**The difference:** TouchDesigner and cables.gl show the cost of every node. Max, Pd, Isadora and MadMapper show whole-engine numbers. More cores come from extra processes in TouchDesigner (Engine COMP) and Pd ([pd~]); Max splits audio across threads by top-level patcher or poly~ voice.

**Advice for Max:** Max has no per-object cost display, so find a slow part by switching sections off one at a time while watching the CPU and frame-rate meters.

### Max

Max runs a main (low-priority) thread for UI, files and JS, an optional separate high-priority scheduler thread (Overdrive), and the audio thread. Audio can be split across threads per top-level patcher (mixer parallel processing) or across poly~ voices (@parallel). Jitter matrices run on the CPU; textures, shaders, gen jit.gl.pix and transform feedback run on the GPU. Gen compiles patches to machine code or GLSL. Cost is shown mainly by the audio CPU meter and the FPS meter.
- *Does well:* Clear priority lanes keep timing-critical work ahead of UI. Gen and GPU paths give compiled speed inside the patch.
- *Makes hard:* Thread behaviour depends on global settings, so the same patch can behave differently on two machines. Cost is not shown per object.
- *Confidence:* high

### TouchDesigner

One main thread cooks the network and runs the interface and Python; the GPU does TOP and POP work. Cost is visible per node (cook time, cook count, GPU time) and per frame. More concurrency comes from more processes: the Engine COMP runs a .tox in a separate TouchDesigner process and exchanges TOPs, CHOPs and DATs with it. Python work can move to threads through the Thread Manager, without touching operators.
- *Coming from Max:* There is no separate audio thread. To split work, you move a component into another process and wire its inputs and outputs as if it were local.
- *Confidence:* high

### MadMapper

The docs talk about performance in terms of hardware, not threads: GPU decoding with HAP, fast storage, GPU sync across outputs, network bandwidth for NDI. Some choices inside the program trade quality for speed: Generator versus Material, Render To Texture, cache sizes, double-buffered previews. No per-part cost display was found.
- *Coming from Max:* You tune by choosing settings and codecs, not by restructuring work across threads. There is no profiler to say which surface is expensive.
- *Confidence:* low

### Isadora

Performance is shown as whole-engine numbers: Cycles, FPS, frame rendering load and video processing overhead. The tools for saving work are switching parts off: Scenes, gated routing, User Actor On/Off, bypass. Media loading runs in the background, and the GPU does the video.
- *Coming from Max:* There is no per-object timing. You see one load figure for the whole show and reduce it by switching whole branches or Scenes off.
- *Confidence:* medium

### cables.gl

The patch runs in the browser's main thread and on the GPU; heavy work can go to a Web Worker from an op attachment. Cost is shown by the Performance op (FPS, CPU and GPU ms per frame, draw and upload counts), the Profiler (CPU per op and subpatch), Flow mode, and timing ops that measure a branch.
- *Coming from Max:* Because work is one frame walk, cost is measured per frame and per branch, and a branch can be timed by putting a measuring op above it.
- *Confidence:* medium

### Pd / plugdata

Pd computes messages and audio in one thread. The GUI is a separate process, and the manual warns that heavy drawing competes with sound. To use another core you start a second Pd as a subprocess with [pd~], exchanging audio and messages. Cost is mostly invisible per object; plugdata adds a CPU meter, and Gem can profile frame time.
- *Coming from Max:* No parallel voices, no separate high-priority thread, and graphics share the audio thread unless split into another process.
- *Confidence:* medium

### ossia score

Audio runs in the audio thread; video renders in a separate thread; a Parallel setting spreads processes over CPU cores. Processes outside the active part of the score cost nothing. Benchmark mode shows each process's share of CPU. Pd patches must not run in Parallel mode.
- *Coming from Max:* Max splits work by thread priority, Overdrive and per-patcher audio threads (max_system_model.json dimension 16). In score the timeline itself limits cost: only what is playing runs.
- *Confidence:* medium

## 17. Several machines

**The difference:** TouchDesigner documents frame-locked sync across machines. MadMapper and Isadora connect through show protocols (OSC, NDI, Art-Net, Link, timecode). cables.gl uses network ops and a server. Pd speaks its own plain-text network format. Max networks through objects: OSC and OSCQuery, jit.net, Node for Max.

**Advice for Max:** For several Max machines, drive them all from one source of time and control over OSC, and keep each patch deterministic from those inputs. Max has no frame lock across machines.

### Max

Max has no built-in multi-machine session. Networking is done with objects: udpsend/udpreceive and integrated OSC (with OSCQuery) for control, jit.net.send/recv for matrices over TCP, Syphon and Spout packages for sharing textures with other apps on one machine, Node for Max for anything web-based, Mira for iPads, and rnbo.remote for exported RNBO devices.
- *Does well:* Open protocols (OSC, UDP, TCP, Node) make Max easy to connect to anything.
- *Makes hard:* Clock sync, state sharing and failover across machines must be built by hand.
- *Confidence:* medium

### TouchDesigner

The docs treat multi-machine work as levels of sync, from none to software sync plus hardware frame lock. The aim is a deterministic project driven by one frame index or one set of control channels. Sync Out CHOP and Sync In CHOP make machines wait for each other each frame (Pro licence); NVIDIA Quadro Sync cards then lock display swaps. Touch In/Out operators move channels, tables and video between processes, and many network protocols are operators.
- *Coming from Max:* Sync is a built-in operator pair that holds machines on the same frame, not a protocol you assemble. The docs push you to design the show so every machine computes the same thing from the same frame number.
- *Confidence:* medium

### MadMapper

MadMapper links to other machines through standard protocols rather than a cluster mode. OSC (with OSCQuery and Bonjour) controls one copy from another. NDI moves video, PONK moves laser paths, Art-Net and sACN move DMX, Ableton Link and timecode share time. MiniMad units on one network play in step with each other.
- *Coming from Max:* Multi-machine work is configuration: pick protocols in the preferences and the outputs. There is no networking code to write, but also no shared state beyond what OSC and timecode carry.
- *Confidence:* medium

### Isadora

Isadora copies on a LAN share numbers by multicast with Net Broadcaster and Listener. Over the internet, IzzyCast carries video, audio and data between copies. Otherwise it talks to other systems through standard show protocols and per-Stage video sharing.
- *Coming from Max:* Machine-to-machine sends reuse the same Listener actor as Scene-to-Scene sends, so a value can come from another Scene or another computer without changing the receiving patch.
- *Confidence:* medium

### cables.gl

Sharing between machines is done with network ops, not a system-wide sync. SocketCluster connects patches through a server by channel and topic; WebSocket client ops are core; OSC needs a bridge in the browser and is native only in standalone. There is no texture sharing.
- *Coming from Max:* Many copies of a piece usually means the same web page opened on many devices, linked by a socket server you patch yourself.
- *Confidence:* medium

### Pd / plugdata

Pd's own network format, FUDI, is plain-text Pd messages ending in a semicolon, sent over TCP or UDP by [netsend] and [netreceive]; command-line pdsend and pdreceive speak it too. OSC is built from [oscformat]/[oscparse] plus raw-byte netsend. The GUI itself talks to the engine over a socket, so it can run on another machine.
- *Coming from Max:* Because files and network share one text format, any program that can write 'freq 440;' to a socket can drive a patch. There is no built-in clock sync between machines.
- *Confidence:* medium

### ossia score

Talking to other machines and programs is the core of score: every protocol is a device in the tree, OSCQuery and Minuit import remote namespaces, and the running score is itself an OSCQuery device. A WebSocket API gives remotes transport and trigger control. Transport sync is JACK only; video moves over NDI, Spout, Syphon or shared memory.
- *Coming from Max:* Max's networking is a set of objects and an OSCQuery server for its own parameters (max_system_model.json dimension 17). score reads other programs' parameter trees as if they were its own, which Max does not do.
- *Confidence:* high

## 18. Deployment

**The difference:** Max builds standalones, Max for Live devices and RNBO exports. plugdata runs the full patch as a plug-in in any DAW, and Heavy compiles patches to C++, plug-ins and Daisy. cables.gl exports a web page. TouchDesigner has a player-only runtime and licence tiers. MadMapper and Isadora run only in their own app. ossia score has no separate player: the same open-source app runs headless or full screen on a Raspberry Pi.

**Advice for Max:** When a patch must run inside a DAW other than Live, or on embedded hardware, RNBO is Max's route. Plan for its narrower object set from the start rather than porting a finished patch.

### Max

A patch can ship as a project (.maxzip archive), a collective, or a standalone application that bundles the Max runtime. Max for Live devices (.amxd) are frozen bundles that run in Live. Plug-ins and Max for Live devices can be hosted in Max with vst~ and amxd~. RNBO exports patches to plug-ins, C++, JavaScript/Web Audio and Raspberry Pi; Gen exports C++ and GLSL.
- *Does well:* Many targets, from a desktop app to a plug-in to embedded hardware via RNBO.
- *Makes hard:* A standalone is a whole Max runtime, not a lean player. Plug-in export goes through RNBO, a separate language and product.
- *Confidence:* medium

### TouchDesigner

TouchPlayer runs any .toe or .tox in Perform Mode only, with no editor. Licence tiers gate features: Non-Commercial is free but limited to 1280×1280 and non-paying work; Commercial and Pro unlock resolution, more operators, sync, privacy and more. Pro can make a project or component private so it runs but cannot be opened. TouchEngine lets other programs run a .tox; Project Packager builds a Windows installer around a project.
- *Coming from Max:* The runtime is the same program in a mode that hides the editor, and what a project may do depends on the licence on the machine it runs on.
- *Confidence:* high

### MadMapper

A project runs in the MadMapper application itself, which needs a licence. For unattended use there are Silent Mode, open fullscreen at startup, schedulers, startup timelines, and OSC commands to quit or restart the computer. The other targets are exports: a MiniMad hardware player (video or DMX), or baked files from timeline export. There is no standalone build.
- *Coming from Max:* The project is a document for one application, not a program you can build into an app. Unattended running is a set of switches in that application.
- *Confidence:* high

### Isadora

There is no build or export: a show is the document plus its media folder, opened in Isadora itself. A document can be locked as run-only with a password. Preferences decide what happens on launch and after a file loads.
- *Coming from Max:* Shipping means handing over the file and folder, optionally locked. There is no separate player build in what was read.
- *Confidence:* medium

### cables.gl

A patch exports as a web page: the core script, only the ops it uses, the patch JSON and an assets folder. Targets include a ZIP, GitHub Pages, Netlify, an iframe, an Electron executable built on the cables servers, a command-line export and a full patch file. Everything needed to run is MIT licensed; a page that loads assets must be served over HTTP.
- *Coming from Max:* The finished piece is a website, and the player is any browser. The page around it can drive the patch.
- *Confidence:* high

### Pd / plugdata

Pd runs as an app, headless from the command line (-nogui, -batch, -send), or embedded through libpd. plugdata runs the same .pd files as a standalone, as VST3/AU/CLAP/LV2 plugins in three flavours, and on iOS. The Heavy compiler, built into plugdata, turns a patch made of supported objects into C/C++, DPF plugins, Daisy firmware, a Pd external, WASM and more, with no Pd runtime.
- *Coming from Max:* The whole editor runs inside the DAW plugin, and a patch can leave Pd entirely as generated code; the catch is that only a subset of objects compiles.
- *Confidence:* high

### ossia score

There is no separate player: the same open-source application runs scores, with command-line flags for no GUI, autoplay, a start delay and no restore dialog. It runs on Windows, macOS, Linux (including Raspberry Pi and other ARM boards, with an EGLFS full-screen mode), FreeBSD and partly the web.
- *Coming from Max:* Max ships standalones and frozen devices on macOS and Windows, with RNBO for Raspberry Pi (max_system_model.json dimension 18). score deploys by installing the editor itself, free, on the target, including small Linux boards.
- *Confidence:* high

## 19. Extending

**The difference:** Every tool lets a new part look like a built-in one: Max externals and abstractions with refpages, TouchDesigner components and Custom Operators, cables.gl user ops with auto-made doc pages, Pd externals and pdlua classes. MadMapper extends only through shader and fixture files.

**Advice for Max:** A Max abstraction or script object becomes a first-class box when it ships with a refpage and a help file, which is what lets tools check its ports and attributes. Butter_tools already works this way.

### Max

New objects can be written in C (Max SDK) or C++ (Min), in JavaScript (v8/v8ui, jspainter), in Java (mxj), in Lua (jit.gl.lua), as GLSL shaders (.jxs for jit.gl.slab), as gen patches (.gendsp/.genjit), or as plain abstractions. All appear as ordinary boxes; externals are found on the search path at launch, and packages bundle them with help and refpages.
- *Does well:* Many ways to add parts, and every one looks like a normal object to the user.
- *Makes hard:* Externals are binary and platform-specific (architecture errors on Apple Silicon/Intel). Python is not a built-in option.
- *Confidence:* high

### TouchDesigner

New parts come in three layers. Components with custom parameters and Python extensions are the everyday way, and they look like any other operator from outside. Script operators produce a family's data from Python. C++ plug-ins load into CPlusPlus operators or install as Custom Operators that appear in the operator menu, with their own parameters and Info CHOP/DAT output. GLSL shaders run in GLSL TOP, MAT and POP.
- *Coming from Max:* Most extending is done by building a component and giving it parameters, not by writing code. A compiled plug-in becomes a new node in a family, with the same parameter dialog as a built-in.
- *Confidence:* high

### MadMapper

The extension points are shader files and data files, not code plug-ins. Materials, Surface FX and Laser Materials are GLSL with an ISF-style JSON header that builds their controls. ISF and Quartz Composer files load as media. Fixture definitions describe new lighting devices. Modules and paid extensions come from the makers. No C/C++ SDK was found.
- *Coming from Max:* A new part is a shader, and it shows up as a media item or an FX choice with generated sliders. You cannot add a new kind of module, input or output yourself.
- *Confidence:* high

### Isadora

New actors come from plugin files in an Isadora Plugins folder (and controls from an Isadora Controls folder), from host formats Isadora loads as actors (FreeFrame, Quartz Composer and Core Image on macOS, Audio Units, VST3), from GLSL text files, and from shared User Actors.
- *Coming from Max:* A text file of shader code can become a toolbox actor with named, ranged inputs, with no wrapper patch.
- *Confidence:* medium

### cables.gl

New parts are JavaScript ops, written in the browser editor or in any editor with the standalone. A user op looks and behaves exactly like a core op, with its own documentation page made automatically. Ops can pull in outside scripts, npm packages (standalone), WebAssembly and GLSL.
- *Coming from Max:* There is no compiled SDK step; extending the tool is writing a small script in the same window, and every built-in op is readable source to start from.
- *Confidence:* high

### Pd / plugdata

New objects are compiled C externals, abstractions, or (in plugdata) pdlua classes; once loaded, an external is indistinguishable from a built-in. A library can be one binary holding many objects or a folder of separate ones, and a later library can override a built-in, which stays reachable as name_aliased. deken, built into vanilla Pd, finds and installs externals. The editor itself is extended with Tcl GUI plugins.
- *Coming from Max:* Lua is the in-app language rather than JavaScript, and an object can be written in Lua with signals and graphics without a wrapper box.
- *Confidence:* high

### ossia score

Every process in score comes from a plug-in. New ones are written in C++ with Avendish (one reflected struct, also exportable to other plug-in formats) or with the full score API. Inside the app, new behaviour also comes from JS, ExprTK, Faust, C++ JIT, ISF/CSF shaders, Pd patches and QML device scripts. Packages are installed through a package manager.
- *Coming from Max:* Max extends through C/C++ externals, JS, gen and abstractions that all appear as boxes (max_system_model.json dimension 19). score's Avendish objects can also be built for other hosts, and a C++ process can be compiled inside the running app.
- *Confidence:* medium

## 20. Media and files

**The difference:** Max finds files by name along a search path, and Projects collect dependencies. MadMapper and TouchDesigner can collect or embed media in the project. Isadora preloads the next Scene's media before a jump. cables.gl uploads assets into the patch. Pd has search paths and no collect step.

**Advice for Max:** For shows, keep media inside a Max Project so it travels and consolidates with the patch, and load clips before they are needed rather than at the moment of the cue.

### Max

Files are found by name through the search path: the patcher's folder, its project, the Max 9 folder, then user paths. Path prefixes (Patcher:, Project:, Package:, ~:) give relative paths. Projects track and consolidate dependencies; standalones and frozen devices bundle them. Some objects load files synchronously at creation and asynchronously later.
- *Does well:* Name-based lookup makes patches portable when files travel together. Projects automate collecting dependencies.
- *Makes hard:* Two files with one name on the path resolve by search order, silently. Missing media show up only as console errors.
- *Confidence:* medium

### TouchDesigner

File-reading operators take a file path parameter, which can be absolute, relative, a URL, or a vfs: path into the Virtual File System embedded in a .toe or .tox. Components can source their contents from external .tox files, with a setting for whether relative paths inside resolve from the .toe or the .tox. Folder DAT lists and watches folders. Text DATs can sync to files on disk. Preloading is a per-operator concern, explained in detail for movies.
- *Coming from Max:* Media can live inside the project file itself. Each component decides where its relative paths start, so a component moved between projects can carry its own media.
- *Confidence:* medium

### MadMapper

Media lives in a Media Bin sorted by kind, with an inspector per item and a count of surfaces using it. Since version 6 a project is a .madproject folder holding the .mad files, auto-saves and a resources folder. Collect External Resources copies all referenced media into it, and Export Project To copies the whole folder. Image folders watch for new files.
- *Coming from Max:* Media is a first-class list you can see, with usage counts, not paths inside object boxes. Packaging a show is one menu command.
- *Confidence:* high

### Isadora

Media lives outside the document. The Media View holds references in typed bins, each with an index number that actors use. Before a jump, Isadora reads the next Scene's players and preloads their media. References can be replaced by hand.
- *Coming from Max:* Media is chosen by number from a project-wide list, so any number source can pick a clip. Loading is the host's job: it reads what the next Scene will play and loads it before the switch.
- *Confidence:* high

### cables.gl

Files are dragged into the editor and uploaded into the patch's assets on the server; some are converted on upload (FBX to GLB, CSV to JSON, MIDI to JSON). Ops refer to files by URL. Exports copy the assets folder, and the standalone keeps assets as local files. Loading is tracked as patch-wide state.
- *Coming from Max:* Media belongs to the patch and is stored with it online, not found on disk by name through a search path.
- *Confidence:* medium

### Pd / plugdata

Files are found along search paths: [declare] paths for this patch, the patch's own folder, the user's paths, then Pd's extra folder. Files are written next to the patch by default, paths use forward slashes everywhere, and ~ expands. Small data can live inside the .pd file (array contents, [text define -k]); there is no collect or project step. plugdata finds patches by their place in its Patches folder when a DAW project moves to another machine.
- *Coming from Max:* The patch says what it needs with [declare]; there is no project window or collective that gathers media.
- *Confidence:* high

### ossia score

Media files are dropped onto the timeline. Relative paths are looked up in the project folder (the folder of the .score file) first; <PROJECT>: and <LIBRARY>: prefixes name the project or user library. A system library in Documents/ossia/score/packages holds shared presets, shaders, fixtures and scripts. Sound files stream from disk when they match the project rate, otherwise load to RAM.
- *Coming from Max:* Max finds files through a search path and projects (max_system_model.json dimension 20). score's lookup is simpler: project folder, then the library, with explicit prefixes.
- *Confidence:* medium

## Dimensions only one tool named

Each scan could add system-level dimensions the shared list lacks. These are
per tool: the same number means different things in different files.

### Max

- **Embedded sub-languages.** Max hosts compiled sub-languages inside boxes. gen~, gen, jit.gen, jit.pix and jit.gl.pix hold gen patchers: no messages, no UI, everything synchronous, all 64-bit floats, compiled to machine code or GLSL. rnbo~ holds a Max-like language made for export. The same box shape therefore hides very different rules.
- **Box text versus live state.** An object box shows its creation arguments and typed attributes, not its current state. Messages change the state without changing the box. Retyping the box makes a new object. Some arguments set structure (inlet counts) that can never change after creation.
  - *For Max:* This is the reason a Max patch needs a storage choice (dimension 6) and loses state when a box is retyped (dimension 12).

### TouchDesigner

- **What a connection is.** A wire does not move data. When a node cooks, the wire only tells the next node where to get its input. There are two kinds of line: wires, which join nodes of one family left to right (plus hierarchy wires for 3D and panel parenting), and links, the dashed lines drawn for every reference by path, expression or export. So the editor shows wireless dependencies as lines too.
  - *For Max:* Max's wireless links (send/receive, value, named buffers) are invisible. Keep them few and named clearly.
- **Flags as a second state layer.** Each node has flags, on/off states that are not parameters: Viewer, Viewer Active, Lock, Bypass, Cooking, Immune, Current, Selected, Expose, and for some families Render, Display, Pickable, Export, Compare, Template. Changing a flag does not itself make a node cook, and you cannot export to a flag. Flags decide much of the system's behaviour: what is shown, what is frozen, what is rendered and what follows its clone master.
- **The network as queryable data.** The project describes itself in its own data types. OP Find DAT lists operators matching type, name, tags or parameter values as a table. Parameter DAT and Parameter CHOP turn any operator's parameters into a table or channels. Info CHOP and Info DAT expose internal state, Error DAT logs errors, and Perform CHOP reports frame timing. These feed Replicators, panels and scripts like any other data.
  - *For Max:* Max patches can be queried by scripting the patcher from v8, but nothing in the patch lists its own objects as data the way OP Find DAT does.

### MadMapper

- **Input space and output space.** Added because it shapes every edit. Each surface has two geometries: an input rectangle or mesh over the source media, and an output shape on the projector. The stage size is independent of the content, and output resolution is set by the projector. Crop and warp are separate edits, and the two meshes can be linked or edited apart.
  - *For Max:* In Jitter the same split is two steps: crop the source, then warp the result onto the output.
- **One composition for video, light and laser.** Added because it decides what an output is. Video surfaces, DMX fixtures and laser surfaces are three kinds of layer in parallel lists, and outputs are objects of three kinds. Fixtures read the video composition, so one layer stack drives projectors and lights together. Master levels for video, DMX, laser and audio hang off one Master.
- **Calibration to the physical room.** Added because the work is defined against real space, not an abstract canvas. Much of the program exists to match virtual geometry to a physical object and room: test patterns, cursors drawn on the projector, background images from camera scans, 3D calibration with a reported error, LED scanning, and soft-edge auto setup. Lasers add arming and safety limits.

### Isadora

- **Link scaling and conversion.** Every numeric link rescales its value: the output's Limit range is mapped onto the input's Scale range. Setting Scale Min above Scale Max inverts it. Types convert on the link too. This is system-level because it is a property of every connection, not of any actor.
  - *For Max:* Max cords never rescale. Ranges are set on the source object where possible, or with scale or zmap, and scale does not clip.
- **Activation lifecycle.** Actors run only while their Scene is active, and many have defined behaviour at the moment of entry and exit. Entry applies Init values, fires Enter Scene actors, outputs global values and starts players. Exit stops media. This is system-level because every actor shares the same start and stop moments, set by the host.
  - *For Max:* Max has one load moment, not per-section entry and exit. A section that must reset when it starts needs its own 'enter' message.
- **Transitions between parts.** Crossfading from one Scene to the next is a host service. Each Scene has fade-in and fade-out times and a crossfade mode, and the fade covers its video and sound together. Patches can read and set a Scene's level. This is system-level because the host, not the patch, mixes whole sections.
  - *For Max:* Crossfading whole sections is something a Max patch builds itself, for video and sound together.

### cables.gl

- **Two kinds of cable: values and triggers.** System-level because every port and every op design follows from it. Values (numbers, strings, arrays, objects) sit on ports and push on change; triggers carry no data and only say 'run now'. Taking a value at a moment needs a trigger form of an op, such as TriggerNumber or TriggerVarGetNumber.
  - *For Max:* Max's hot and cold inlets are its version of this split, inside one cord.
- **The browser as platform.** System-level because it sets limits across every area. The patch is a web page: audio needs a user click to start, data from other servers needs CORS headers, video codecs are whatever the browser plays, sound I/O is two channels, and hardware access goes through web APIs (Web MIDI, WebXR, sensors). The standalone lifts some limits.
- **Patches live online, with owners and permissions.** System-level because it shapes saving, reuse and sharing. Patches are stored on the cables server and are private, unlisted or public; op namespaces carry ownership (patch, user, team, extension) and decide which ops may be published. Several people can join one patch, with one Pilot whose edits everyone sees.
- **Loading is an observable phase.** System-level because start-up is something the patch can watch and wait on. A patch-wide LoadingStatus reports progress and jobs, ops can add their own LoadingJob, op code has an onLoaded callback, and the timeline can start only when loading is done. PreRender draws chosen times ahead to compile shaders and upload assets.
  - *For Max:* Max's load runs in fixed phases, and the Max docs read describe no patch-wide progress report. Start a show only after the objects it depends on have finished loading.

### Pd / plugdata

- **Patch as message script.** Why system-level: it ties the file format, object creation and scripting into one mechanism. A .pd file is a sequence of plain-text Pd messages (#N canvas, #X obj, #X connect, #A for array data), and an object box's text is literally a creation message to Pd. The same messages sent at run time edit a live patch.
- **Behaviour versioning.** Why system-level: it governs how every object's behaviour is kept stable across releases. When a Pd release fixes an object's behaviour, the old behaviour stays selectable with a compatibility version, sent as '; pd compatibility 0.52' or given as -compatibility at startup. Help files document which objects changed.
  - *For Max:* The Max docs read for this comparison describe no such switch. When a patch moves between Max versions, check the refpages of the objects it relies on.
- **Engine and GUI split.** Why system-level: it shapes performance, remote use and how plugdata exists at all. Vanilla Pd's engine and its Tcl GUI are separate processes that talk over a socket, so Pd can run with no GUI, with a GUI on another machine, or with a different GUI. plugdata is exactly that: Pd's engine with minimal changes and a new JUCE interface, which is what lets it run inside a plugin.

### ossia score

- **Units and dataspaces (system-level because the conversion rules apply to every connection).** Values can carry a unit from a family (distance, position, orientation, colour, angle, gain, time...). Whenever a value crosses any connection, whether a cable, a read from a device or a write to one, score converts between units of one family, otherwise maps ranges, and never drops a value because of a unit.
